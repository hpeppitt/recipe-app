## Context

Spec: `docs/design/organic/export/App Spec.dc.html`, "Explore · landing (1b)": "Branching fast
this week (horizontal, scroll-snap, 200px tiles)", emoji at 76px "on a rotating tint
(accent-200, accent-2-200, surface)". Markup: the `explore` block of `App Prototype.dc.html`
(`trending` list; badge `+{{ r.week }} this week`). RL-099 shipped the same row shape as
`RecipeTileRow` filled with the newest roots, titled "New this week" or "Newest", because
ranking needed data the app did not have.

**The data exists.** Every published recipe carries `parentId`, `rootId` and `createdAt` (a
client-clock number, `PublishedRecipe` in `src/services/firestore.ts`; the create rule checks
`createdAt is int` and at most 60 s in the future). So one query for the last 7 days, grouped
by `rootId` on the device, gives each family's new branches this week.

**Index: none needed, so no deploy.** The query is a range filter and `orderBy` on the same
single field, `where('createdAt', '>=', since)`, `orderBy('createdAt', 'desc')`, `limit(100)`.
Firestore serves that from its automatic single-field index (ascending and descending exist for
every field; `firestore.indexes.json` has no `fieldOverrides` disabling `createdAt`). It is the
same index `getAllPublishedRecipes` (`orderBy('createdAt','desc')`) already uses. Filtering on
`parentId` in the query as well would need a composite index and a human deploy, so branches
are filtered on the device instead. The rule is `allow read: if true`; no rules change.

**Reads.** One query per session (page load): billed one read per document returned, at most
100, and one read when it returns nothing. Then one `getDoc` (`getPublishedRecipe`) for each
shown family whose root is neither in the query result nor in Explore's loaded feed, at most 8.
Worst case 108 reads per session. The cap means a week with more than 100 new recipes counts
only the newest 100; leave a `shortcut:` comment saying so (upgrade: a server-side counter).

**Replace, with fallback.** This row replaces RL-099's row in the same slot, between the header
and the chips. When this row has nothing to show (the query failed, timed out, or found no
branches this week), RL-099's Newest row renders exactly as before. While the query is in
flight neither row renders, so they never swap in front of the user. All of RL-099's hide rules
still apply to both (filtering, a tag, local-only, feed loading); in local-only mode no query
is made.

**Token map:** `--color-surface` is `bg-surface-secondary`; neutral-700 text is
`text-text-tertiary`. Light only: no `dark:` classes. 44px targets. Lucide icons at stroke 2.75.

Values to copy (RL-099's row, plus):

- Title "Branching fast this week" in `font-heading` 18px (RL-099's heading row). No "See
  all" (out of scope).
- Tile: RL-099's 200px tile with the root's emoji, title, tint by index (`bg-accent-200`,
  `bg-accent-2-200`, `bg-surface-secondary`), `UserPill` of the root's author and
  `formatTime(totalTime)`. The design's meta "<n> branches" (the family's total) is not shown:
  it needs the whole tree per family.
- Badge in place of RL-099's branch tag, at `top: 12px; left: 12px`: `bg-accent-2-700
  text-accent-2-100`, 600, 11px, `GitBranch` icon, gap 4px, `rounded-full`, padding `3px 10px`,
  `whitespace-nowrap`, text "+<N> this week". Its accessible text is "<N> new branches this
  week" ("1 new branch this week") via a visually hidden span, with the visible "+N" text
  `aria-hidden`.
- Up to 8 tiles, most new branches first, ties broken by the newest branch.

## Acceptance criteria

- [x] `src/services/firestore.ts` exports `getRecentPublishedRecipes(sinceMs: number, max = 100)` running the query above and returning `PublishedRecipe[]`; returns `[]` when Firebase is not configured. `firestore.indexes.json` and `firestore.rules` are unchanged.
- [x] A pure function in `src/lib/library.ts`, `branchingThisWeek(recent, now, max = 8)`, returns `{ rootId, weekCount, newestAt }[]`: only rows with a `parentId` and `createdAt >= now - 7 days` count, grouped by `rootId` (falling back to `id` when absent, as `feedMapper` does), sorted by `weekCount` then `newestAt`, cut to `max`. Branches of any depth count; a new original counts nothing.
- [x] `src/lib/library.test.ts` covers grouping across depths, the 7-day edge (exactly 7 days in, one millisecond out), originals ignored, ordering and the tie-break, the cap, an empty input.
- [x] `src/hooks/useBranchingThisWeek.ts` takes `enabled` and Explore's loaded rows, runs the query once per session (a module-level promise; `withTimeout` 6000 ms; failures go to `reportError(err, 'branching-week')`), resolves each family's root from the query result, then the loaded rows, then `getPublishedRecipe` (bounded the same way), drops a family whose root is missing or failed, and returns `{ status: 'loading' | 'ready' | 'none', tiles }` where `tiles` are `FeedRecipe`s with `weekCount`. No Dexie or Firestore write.
- [x] `useBranchingThisWeek.test.tsx` (mock the service): one query across remounts; known roots cost no `getPublishedRecipe`; unknown roots fetched once each; a deleted root's family dropped; a rejection, a timeout and an empty week give `none`; `enabled` false makes no call.
- [x] `RecipeTileRow` accepts an optional per-tile `weekCount`; when set, the "+N this week" badge replaces the branch tag. `RecipeTileRow.test.tsx` covers the badge and its singular and plural accessible text.
- [x] `ExplorePage` renders this row when `status` is `ready` with at least one tile, RL-099's row when `none`, and neither while `loading`, under RL-099's hide rules. `ExplorePage.test.tsx` covers all three and local-only making no call.
- [x] `docs/capabilities.md`: the Explore row describes Branching fast this week, its fallback and its read cost. `docs/data-model.md`: a short paragraph after "Composite indexes" saying this query uses the automatic single-field `createdAt` index, with its cost and cap.
- [x] A `backlog/QA.md` entry (below).
- [x] `npm test`, `npm run lint`, `npm run build` pass.

## Out of scope

"See all", "Most branched" and its time-range picker, the Pantry card (1c), the family's total
branch count on the tile, server-side counters or Cloud Functions, any new composite index,
photos.

## Verification

`npm test`, `npm run lint`, `npm run build`; `ui-reviewer` (badge contrast on the three tints,
names); `data-integrity-reviewer` (read-only, bounded, no cache writes).

Human, on the preview against the live project at 390x844 and 320px:

- With at least two branches published this week on one family and one on another, Explore
  shows "Branching fast this week" with the busier family first and "+2 this week"; tiles
  swipe and snap on iOS Safari and Android Chrome; Tab reaches each tile.
- The browser console shows no Firestore "requires an index" error (proves no deploy is
  needed); devtools Network shows one `runQuery` for the week and no repeat after switching
  tabs and coming back.
- With no branches this week (check against the emulator with `npm run dev:emulated` if live
  has some), the Newest row from RL-099 shows instead; nothing flashes between the two. The
  failure path is covered by the hook tests.
- VoiceOver reads a tile as its title and "2 new branches this week".

## Notes

Implemented as specified. No index or rules change. The hook keys its effect on the loaded feed's ids and reads rows from a ref, since `buildFeed` returns a new array every render. Caches are module state with `clearBranchingThisWeekCache` for tests. Existing ExplorePage tests now mock the new service calls (empty week, so the Newest row still shows).
