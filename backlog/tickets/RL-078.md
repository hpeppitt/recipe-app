## Context

Read decision 1b in `docs/decisions.md` (RL-076) first. This ticket makes it true: one
`onSnapshot` on `recipes where createdBy.uid == uid` per session for a verified user, each
server snapshot applied to Dexie with `planOwnRecipeSync` (`src/lib/recipeSync.ts`, RL-076).
Every existing Dexie reader then shows the cloud state with no change of its own: My Recipes
(`useLocalLibrary`), the own profile (`useOwnRecipes`), the detail and edit pages
(`useRecipe` prefers the local row), and the tree (`useRecipeTree` merges local first).
Offline, they show the last copy.

It depends on RL-082 and RL-083 because the snapshot is authoritative: with the old
local-first save and edit, a recipe or edit whose publish failed would be removed or
overwritten by the next snapshot, silently.

Ground truth that shapes it:

- Reads of `recipes` are `allow read: if true` in `firestore.rules`, and an equality-only
  query on `createdBy.uid` needs no composite index (`getUserRecipes` already runs it). So
  no rules or index change.
- `getFirestore` (`src/services/firebase.ts`) uses the default memory cache. A snapshot
  served from cache, or carrying pending local writes, is not the server's answer, and an
  empty one would remove every own row. Only server snapshots are applied.
- The tidy of other accounts' rows needs `getPreviousUids()` from `src/services/storage.ts`;
  read it in the db or hook layer and pass it to the pure plan.
- Auth is in `src/contexts/AuthContext.tsx`; follow RL-043's precedent and keep the trigger
  out of it. `App.tsx` mounts `TermsGate` inside `BrowserRouter`; a render-nothing component
  beside it covers every route, including those outside `AppShell`.
- The status the UI needs (RL-079) is exposed here so that ticket stays UI only. Follow
  `src/hooks/useConsent.ts` (`useSyncExternalStore` over a module-level value).

## Acceptance criteria

- [ ] `subscribeOwnRecipes(uid, onDocs, onError)` in `src/services/firestore.ts` opens one `onSnapshot` on `query(collection('recipes'), where('createdBy.uid', '==', uid))` with no `orderBy`, calls `onDocs` with `{ id, ...data }` for each doc only when `snap.metadata.fromCache` and `snap.metadata.hasPendingWrites` are both false, and returns the unsubscribe function. It is a no-op returning a no-op when Firestore is not configured. A test asserts a `fromCache` snapshot is never passed on.
- [ ] `applyOwnRecipeSync(uid, cloudDocs, previousUids)` in `src/db/recipes.ts` runs one `rw` transaction on `db.recipes`: it reads the rows inside the transaction, calls `planOwnRecipeSync`, then `bulkPut`s `put` and `bulkDelete`s `remove`. Tests in `src/db/recipes.test.ts` (fake-indexeddb) cover: an overwrite, an own row removed by an empty snapshot, a previous account's row removed, and a saved copy of another user's recipe and a `'local'` row left untouched.
- [ ] `src/hooks/useOwnRecipesSync.ts` exports `useOwnRecipesSync()` and `useOwnRecipesSyncStatus()`. The first subscribes only when Firebase is configured, auth has loaded, and the user is verified and not anonymous; it unsubscribes on sign-out, on a uid change and on unmount. A snapshot that resolves after the uid changed writes nothing.
- [ ] Status is one of `off` (no subscription), `waiting` (subscribed, no server snapshot applied yet), `synced` (at least one applied) or `error` (the listener failed), and resets to `waiting` on a new uid.
- [ ] A listener error is logged with `console.error` and reported once per session with `reportError(err, 'recipe-sync')`, and sets `error`. A failed Dexie apply is reported as `recipe-sync-local` and leaves the status as it was. There is no retry loop: Firestore resumes a listener after a network loss by itself.
- [ ] `App.tsx` mounts a component that calls `useOwnRecipesSync()` and renders nothing, inside `AuthProvider` and `BrowserRouter`.
- [ ] The sync never writes to Firestore: `src/hooks/useOwnRecipesSync.test.tsx` mocks the service and asserts no write function is called, and that anonymous, signed-out and unverified users open no listener.
- [ ] `docs/architecture.md` "Dual storage" is rewritten: for a verified user Firestore is authoritative for their own recipes, saves and edits are cloud first and cached in Dexie on success, the listener keeps Dexie in step and the last write wins; anonymous, signed-out and local-only users are Dexie only; the "two stores can disagree" paragraph is narrowed to what is still true (other users' recipes, saved copies, offline). It links decision 1b.
- [ ] `docs/data-model.md` documents the listener's query, that it needs no composite index, its read cost (every own recipe once when the listener attaches, then one read per changed doc), and the tidy rule (rows of other uids that signed in on this device are removed).
- [ ] `docs/capabilities.md` rows for Library tabs (My Recipes), Version tree view and the own profile say a verified user's own recipes appear on every device they sign into, live, and offline from the last copy.
- [ ] A `backlog/QA.md` entry: against the emulators (`npm run emulators` plus `npm run dev:emulated`) or the preview, sign the same verified account into two browser profiles. Save a recipe on A: it appears in B's My Recipes and profile without a reload. Edit it on A: B's open detail page shows the edit. Delete it on A: it leaves B's My Recipes. Set B offline in DevTools and reload: B's My Recipes still lists the remaining recipes. Sign B out: no console errors. On the author's own phone and computer, confirm any pre-wipe recipe from the old uid is gone after the first sync, and note any that remain (their uid was not in the device's list).
- [ ] `npm run build`, `npm run lint` and `npm test` pass.

## Out of scope

Loading and offline states in the UI (RL-079). Delete order (RL-080). Save and edit paths
(RL-082, RL-083). The Created, Branched and Saved split (RL-084 and the rebrand). Clearing
Dexie on sign-out. Recipes the user collaborates on. Favourites. Any change to
`firestore.rules` or `firestore.indexes.json`.

## Verification

`npm test` for the service, db and hook tests. Human: the two-profile walk in the QA entry,
which no agent can do here. The data-integrity-reviewer should check the `fromCache` guard,
that saved copies and `'local'` rows are never removed, and that nothing writes to Firestore.

## Notes

Revised 2026-10-18 after the author's follow-up answers: no `syncedAt`, no unsynced-row
handling (saves and edits are cloud first), last write wins, and the tidy of other accounts'
rows replaces any push of local recipes on sign-in.
