## Context

`suggestions` read (`firestore.rules` line 114) and `suggestions/{id}/messages` read
(line 144) are `allow read: if signedIn()`, anonymous included. The comment on line 112-113
already says to tighten it once the query filters by owner. The UI already hides other
people's suggestions from non-owners (`visibleSuggestions` in `RecipeDetailPage.tsx`), but
the data reaches every signed-in browser, so private two-party threads are effectively
public.

Under the 2026-10-14 decision (RL-040) anonymous accounts hold local bookmarks only and do
not read suggestions at all. RL-003 gates the listener on a signed-in user; it does not
change the rule or the query, and it edits the same hook, so it lands first and this ticket
narrows its gate from signed-in to verified. RL-017 makes `recipeOwnerId` trustworthy, which
the owner-side query below relies on.

Rules on a `list` are authorised from the query's constraints, not the documents (see
"Security rules on a list never see document data" in `docs/decisions.md`), so the query
must carry the filter the rule checks.

## Acceptance criteria

- [ ] `subscribeRecipeSuggestions` takes the viewer's uid and whether they own the recipe. Owner: `where('recipeId','==',id), where('recipeOwnerId','==',uid), orderBy('createdAt','desc')`. Anyone else: `where('recipeId','==',id), where('suggestedBy.uid','==',uid), orderBy('createdAt','desc')`.
- [ ] `firestore.indexes.json` gains the two composite indexes those queries need (`recipeId` ASC + `recipeOwnerId` ASC + `createdAt` DESC, and `recipeId` ASC + `suggestedBy.uid` ASC + `createdAt` DESC).
- [ ] Suggestion read rule: `verified() && (resource.data.recipeOwnerId == request.auth.uid || resource.data.suggestedBy.uid == request.auth.uid)`.
- [ ] Messages read rule: `verified()` plus the same two-party check via `get()` on the parent suggestion, as the create rule already does.
- [ ] `useSuggestions` and `useSuggestionThread` subscribe only when the user has `emailVerified`; anonymous and signed-out users see the page's existing "nothing to show" state with no listener and no error.
- [ ] Ownership for the query comes from the recipe's `createdBy.uid` matching the user, not from `canManageRecipe` (which treats any local copy as owned).
- [ ] `docs/data-model.md` suggestions and messages paragraphs describe the new read rule, the indexes, and that reading a thread now costs one extra document read.
- [ ] A `backlog/QA.md` entry: on the preview build, a third verified account and an anonymous account opening a recipe with suggestions on it see none and the console is clean; the owner still sees all, the suggester sees theirs.

## Out of scope

Signed-out behaviour (RL-003), any change to who may create suggestions or messages, and
the deploy (RL-022). Note for RL-022: the indexes must be built and this client released
before these rules go live, or the old unfiltered query is denied.

## Verification

Emulator probes recorded in Notes: owner query (allow), suggester query (allow), third
party query with either filter set to their own uid returns only their own, unfiltered
query (deny), messages list as a third party (deny), any suggestion or messages read as an
anonymous account (deny). The app against the emulator with
three accounts.

## Notes

This narrows who can see what. It matches what the UI already shows, so no user-facing
privacy copy changes, but call it out in the PR for the author.
