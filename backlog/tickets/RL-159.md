## Context

RL-157 decided 2026-10-20: the recommended answers, plus the moved branches' authors are notified. Today the More
sheet's "Delete" (`RecipeHeader.tsx` ~156) opens "Delete Recipe" / "This will delete "<title>"
and all N variation(s) beneath it" (`RecipeDetailPage.tsx` ~518), and `handleDelete` runs the
cloud subtree delete first, then the local one (RL-080 order; `runCloudDelete`, 10 s bound,
"Couldn't delete this recipe" with Try again). Dexie has no `update()` (data-model.md "Gotcha");
use get then put. RL-158 allows the batch in the repo rules; test against the emulator.

### Design (19a)

Menu row "Delete version" on a branch (danger, accent-700). Dialog: title "Delete this
version?" (heading 22px), body "Its <N> branches stay, and move up to <parent title>." (N =
direct children; 1 branch "Its branch stays, and moves up to ..."; 0 children "This can't be
undone."), buttons Keep it (secondary) and Delete (destructive accent-700), as `ConfirmDialog`.

## Acceptance criteria

- [x] For a branch: `deletePublishedVersion(uid, recipe, childIds)` commits one batch: delete the version, and update each direct child to `{ parentId: recipe.parentId, depth: child.depth - 1 }`. Cloud first within 10 s; on success, local: delete the row and put each local child with the new `parentId` and `depth`; on failure nothing local changes and the existing failure dialog shows.
- [x] The same batch writes one `moved` notification per moved child whose author is not the deleter (recipient the child's author, `recipeId` the child, `message` the deleted version's title), using the existing notification writer and its rate-limit handling. Activity renders it as "**<deleter>** deleted <message>, so **<child title>** now branches from **<new parent title>**" with the branch badge, and it counts as a Branches item for the RL-154 filter when that exists. Deviation: does not name the new parent; needs a parentTitle key in the notification shape; left for the author.
- [x] Local-only and unverified owners do the local half only.
- [x] The original keeps today's whole-family delete when every version is the owner's; when another cook has a version in the family, the menu row reads "Delete" disabled-looking with the line "Other cooks have branches here, so the original stays." (RL-157 answer 3b) and no dialog opens.
- [x] After deleting a version the page goes to its parent (`/recipe/<parentId>`, replace), not to `/`.
- [x] `src/db/recipes.ts` gains `reparentChildren(childIds, parentId)` (get then put) with a test; `deleteRecipeTree` stays for originals.
- [x] Tests: batch contents for a version with own and others' children; local reparent; failure leaves the device untouched; dialog copy for 0, 1 and 3 children; original blocked when others have versions.
- [x] `docs/capabilities.md` "Delete a recipe" row and `docs/architecture.md` describe version delete and the original rule; decisions.md was updated by RL-157.
- [x] A `backlog/QA.md` entry. `npm test`, `npm run lint`, `npm run build` pass.

## Notes

From RL-158 review: count other-cook direct children; above MAX_MOVED_CHILDREN refuse the cloud delete with a clear message (no partial move); one writeBatch: delete P, reparent every direct child (own and others'), and a moved_{childId} notice per other-cook child; mirror the moves in Dexie; on denial re-read children and retry once; never fall back to a plain delete. Descendants keep stale depth; do not rely on stored depth for display.

Render the moved notice message as plain text; it is sender-written, not verified against the deleted title.

Implemented 2026-10-21. `deletePublishedVersion(uid, recipe, childIds)` in `services/firestore.ts`
reads the version (no cloud doc: nothing to do), then its direct children from the cloud
(`where('parentId','==',id)` plus any `childIds` the query missed), refuses with
`TooManyMovedBranchesError` above `MAX_MOVED_CHILDREN` other cooks' children, and commits one
`writeBatch`: delete, `{ parentId, depth: stored depth - 1 }` per child, `moved_{childId}` per
other cook's child. A failed commit re-reads and retries once, then throws; never a plain delete.
The page reparents locally (`reparentChildren`, then `deleteRecipeTree`, which then removes only
the version) and opens the parent with replace. Originals are blocked in the menu while
`family` holds another cook's version.

AC 2 ticked with a deviation (coordinator, 2026-10-21): the `moved` notice has one title field (`recipeTitle`, the moved
child's), so Activity reads "<deleter> deleted <title>, so <child> moved up a level" without the
new parent's title; and the notice cannot go through `notify`/`writeLimited`, because it must ride
in the delete batch and the rules exempt it from the window. Logged in `backlog/DECISIONS.md`.
`moved` is under Branches; it is not behind the branch preference.

Review round 2026-10-21 (ui-reviewer, data-integrity-reviewer findings 1 to 9). After a version
delete the dialog state resets, the page opens the parent and focuses its title (`data-recipe-title`,

deleting nothing, when it finds another cook's document (`skipped`). Notices skip children without
a string author uid. The local half reads the version's children from Dexie. Retry only when the
child set changed. Cloud-returned depths are not written locally (stored depth is not displayed).
