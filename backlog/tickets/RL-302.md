## Context

A fresh dev project (RL-292) and every emulator start are empty, so Explore, the tree, cook
counts, Most cooked and cookbooks show their empty states and QA on dev cannot see the
populated screens. The emulators stay the first stop for writes that cannot be undone
(`docs/operations.md`, "Emulator workflow"); seed data makes them and dev useful for that.

Seeding goes through the Admin SDK (`firebase-admin`, already a dev dependency, as
`scripts/data-request.mjs` does), so it bypasses the rules; the documents must therefore match
what the rules and schemas would accept on their own, or the app will fail on them. The shapes
are in `docs/data-model.md` (collections) and `src/schemas/recipe.schema.ts`; the test factories in
`src/test/factories.ts` are TypeScript and cannot be imported from an `.mjs` script, so the
seed data lives in JSON.

Project handling follows RL-301: an explicit `--project` or `--emulator`, never a default.

## Acceptance criteria

- [ ] `npm run seed -- --emulator` (project `demo-recipe-lab`) and
  `npm run seed -- --project <dev-id>` write: 3 Auth users with verified emails (one named
  for the author's QA), their `profiles` and `termsAcceptance` at the current `TERMS_VERSION`,
  2 recipe families of 3 to 4 versions each with `rootId`, `parentId` and branch prompts,
  favourites and follows between the users, 6 or more `cooks` spread over the last 30 days,
  and 1 public cookbook collection with a follower.
- [ ] It refuses `prod`'s project id from `.firebaserc` and `recipe-lab-3832b` with a clear
  message, before Firebase loads; a test covers it.
- [ ] Re-running it does not duplicate: fixed document ids and Auth uids, written with set.
- [ ] A test parses every recipe in `scripts/seed-data.json` with the schemas in
  `src/schemas/recipe.schema.ts` (Vitest imports TypeScript) and checks the rules' caps listed
  in `docs/data-model.md` (title length, list sizes).
- [ ] `docs/operations.md` documents the command in Commands and in Environments, including
  that seeded users sign in through the emulator's magic links or, on dev, with real email
  links to addresses the author controls (the seed reads them from `--emails a,b,c`; without it,
  dev users get `example.com` addresses that cannot sign in).
- [ ] `backlog/QA.md` gets a line: seed the emulators, open Explore and a family tree, and see
  cooks and branches.
- [ ] `npm test`, `npm run lint` pass.

## Out of scope

- Seeding production, ever.
- Wiping dev (a later ticket if wanted).
- Generating recipes with Gemini.

## Verification

`npm test`; the agent seeds the emulators and reads back the counts with the emulator REST API.
The human opens the seeded app on dev.
