## Context

`firebase.json` hosting headers set only `Cache-Control`. Nothing stops the app being framed
by another site, and nothing stops MIME sniffing. The header blocks carry `"//"` comments
explaining themselves; keep that style.

## Acceptance criteria

- [ ] The `/**` header block adds `X-Frame-Options: DENY` and `X-Content-Type-Options: nosniff`, with a `"//"` comment saying why.
- [ ] The existing cache headers are unchanged.
- [ ] `docs/operations.md` hosting section mentions the security headers.
- [ ] A `backlog/QA.md` entry: on the preview channel (RL-013) or after release, `curl -sI` the site root and an `/assets/` file and confirm both headers; then complete an email-link sign-in end to end, since Firebase Auth helper pages are served under `/__/auth/` on the hosting domain when it is the auth domain.

## Out of scope

A Content-Security-Policy. It needs its own inventory of Firebase, Analytics and App Check
origins.

## Verification

JSON validity (`node -e "JSON.parse(require('fs').readFileSync('firebase.json'))"`) and the
human check above. Headers only take effect on a hosting deploy, which is `/release`.
