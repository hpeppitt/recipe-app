## Context

`firebase.json` hosting headers set only `Cache-Control`. Nothing stops the app being framed
by another site, and nothing stops MIME sniffing. The header blocks carry `"//"` comments
explaining themselves; keep that style.

## Acceptance criteria

- [x] The `/**` header block adds `X-Frame-Options: DENY` and `X-Content-Type-Options: nosniff`, with a `"//"` comment saying why.
- [x] The existing cache headers are unchanged.
- [x] `docs/operations.md` hosting section mentions the security headers.
- [x] A `backlog/QA.md` entry: on the preview channel (RL-013) or after release, `curl -sI` the site root and an `/assets/` file and confirm both headers; then complete an email-link sign-in end to end, since Firebase Auth helper pages are served under `/__/auth/` on the hosting domain when it is the auth domain.

## Out of scope

A Content-Security-Policy. It needs its own inventory of Firebase, Analytics and App Check
origins.

## Verification

JSON validity (`node -e "JSON.parse(require('fs').readFileSync('firebase.json'))"`) and the
human check above. Headers only take effect on a hosting deploy, which is `/release`.

## Notes

- Criteria 1 to 3 met in `firebase.json` (`/**` block) and `docs/operations.md` (hosting section). The `/**` block already had a `"//"` comment, so the reason was added to it rather than a second key; a duplicate key would silently overwrite the first.
- Criterion 4: the QA.md entry is written. The curl check and the email-link sign-in are human steps, left unticked until run on the preview channel or after release.
- The repo does not record the auth domain value, so it does not show whether `VITE_FIREBASE_AUTH_DOMAIN` equals the hosting domain. The `/__/` carve-out in decisions.md assumes it can.
- Headers take effect only on a hosting deploy (`/release`). Not deployed.
