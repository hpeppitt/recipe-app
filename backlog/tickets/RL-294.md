## Context

`.firebaserc` has one project, `default: recipe-lab-3832b`, so any bare `firebase deploy`
from a laptop hits production. The author decided on 2026-10-22 that there are three
environments (local emulators, dev, production) and that the CLI's default must be dev, so a
stray local command cannot reach production.

The emulator workflow is coupled to the production id today: `docs/operations.md`
("Emulator workflow") tells you to set `VITE_FIREBASE_PROJECT_ID=recipe-lab-3832b` in `.env`
to match `.firebaserc` under `singleProjectMode`, and the magic-link curl examples use
`P=recipe-lab-3832b`. A `demo-` project id is Firebase's convention for emulator-only
projects: the emulators never reach a real resource under it. `scripts/data-request.mjs`
already rehearses with `--project demo-rl055`.

Vite gives shell variables priority over `.env` files, so `dev:emulated` can set the demo
project values itself and emulator work no longer needs a hand-made `.env`. Agents never edit
`.env`; every variable is documented per environment in `.env.example`.

`firebase-tools` is run with `npx -y` today, so its version floats. The pipeline needs a
pinned version; a dev dependency is reversible (`backlog/README.md`).

Dev project id: from RL-292's Notes, written `<dev-id>` below.

## Acceptance criteria

- [ ] `.firebaserc` is `{"projects": {"default": "<dev-id>", "dev": "<dev-id>", "prod": "recipe-lab-3832b"}}`.
- [ ] `firebase-tools` is a pinned dev dependency (current major), and `npm run emulators` is
  `firebase emulators:start --only auth,firestore --project demo-recipe-lab`.
- [ ] `npm run dev:emulated` sets `VITE_USE_EMULATORS=true`,
  `VITE_FIREBASE_PROJECT_ID=demo-recipe-lab`, a dummy `VITE_FIREBASE_API_KEY` and
  `VITE_FIREBASE_AUTH_DOMAIN=demo-recipe-lab.firebaseapp.com`, and an empty
  `VITE_RECAPTCHA_SITE_KEY`, so it reaches the emulators with or without a `.env`. The
  console still logs `[firebase] using local emulators; no live data is being touched`.
- [ ] `.env.example` has a short block per environment saying where each value comes from:
  local emulators (nothing needed, `dev:emulated` sets it), local against dev (the dev web
  app config from the Firebase console, the dev reCAPTCHA site key and a dev App Check debug
  token), and dev and production builds (never from `.env`: CI builds from the GitHub
  Environment variables, RL-293). It says a local `.env` should point at dev, never
  production.
- [ ] `docs/operations.md` gains an "Environments" section near the top: a table of the three
  environments (project id, alias, URL, who deploys, from what trigger, which data is real),
  the rule that the CLI default is dev and production is reached only by the production
  workflow (RL-298), and that a staging project can be added later as another project and
  Environment. The "Emulator workflow" section and the magic-link curl examples use
  `demo-recipe-lab` and no longer ask for a `.env`; "Deploying" no longer says the target is
  `.firebaserc`'s only project.
- [ ] `docs/decisions.md` gets an entry "One Firebase project per environment (RL-294,
  2026-10-22)": local emulators, `<dev-id>`, `recipe-lab-3832b`; every merge to `main`
  deploys to dev; production deploys from a release tag after the author approves the run in
  the GitHub Environment `production`; the production order defaults to rules first, a Terms
  bump is always rules first, and client first needs an explicit `deploy-order: client-first`
  tag line or dispatch input; each environment has its own JSON deploy key in its GitHub
  Environment (keyless rejected for now as extra setup); the `qa` preview channel against the production backend
  is retired; staging rejected for now as not needed at this size; rejected alternative: one
  project with preview channels, because channels share the production Auth and Firestore.
- [ ] `backlog/QA.md` gets a line: run `npm run emulators` and `npm run dev:emulated` with no
  `.env` and sign in through the Auth emulator's magic link.
- [ ] `npm run build`, `npm run lint`, `npm test` pass.
