## Context

The Privacy Policy (RL-044) must offer access, export and erasure under the APPs, GDPR and
UK GDPR. Checked on 2026-10-14: the app can honour almost none of it itself. "Export All
Recipes" covers local Dexie recipes only. "Clear All Data" is local-only (product decision
5). There is no account deletion. The rules stop a user deleting their own suggestions,
replies and the notifications they sent. Product decision 2 rules out Cloud Functions.

The honest answer the policy can give today is "email us". This ticket makes that true with a
procedure the author can run within a month of a request. Self-service comes later (RL-056,
RL-057).

A uid's data, from `docs/data-model.md`:
- Profile: `profiles/{uid}`.
- Recipes: `recipes` where `createdBy.uid == uid`, and the uid inside other recipes' `collaborators`.
- Favourites: `favorites` where `uid == uid`.
- Follows: `follows` where `followerId` or `followingId` is the uid.
- Suggestions: `suggestions` where `suggestedBy.uid` or `recipeOwnerId` is the uid, plus their `messages` where `fromUid == uid`.
- Notifications: `notifications` where `recipientUid` or `fromUid` is the uid.
- Other collections: `clientErrors` where `uid == uid`, `termsAcceptance/{uid}` (RL-047), and `writeWindows` (RL-048).
- Auth: the Firebase Auth user.

## Acceptance criteria

- [ ] `scripts/data-request.mjs` uses the Firebase Admin SDK with application default credentials (`firebase-admin` as a dev dependency). It takes `export <uid>` or `erase <uid>`, and the `--emulator` and `--execute` flags.
- [ ] `export` writes one JSON file, outside the repo, with every document above for the uid, including `messages` subcollections.
- [ ] `erase` without `--execute` prints exactly what it would delete or modify and changes nothing. With `--execute` it:
  - deletes the uid's own documents;
  - removes the uid from `collaborators` arrays;
  - deletes notifications sent by or to the uid, and follows on either side;
  - for suggestions and messages the uid wrote on other people's recipes, anonymises them (author decision 2026-10-14): the text is kept, the display name is set to null and the uid fields (`suggestedBy.uid`, `fromUid`) are replaced with the fixed placeholder `deleted-user`, so the other party's thread stays readable and no query or rule finds the old uid;
  - deletes the Auth user.
- [ ] The script refuses to run `--execute` against production unless the uid is passed twice (a typed confirmation), and logs counts.
- [ ] Tested against the emulator with seeded data for two users: export is complete, erase removes or anonymises only the target's data, and the other user's data is untouched. The run is recorded in Notes.
- [ ] `docs/operations.md` gains a "Data requests" runbook covering:
  - how to verify the requester owns the account (reply from the account's email);
  - running export or erase, emulator first;
  - the one-month deadline;
  - recording the request without keeping the exported data.

## Out of scope

Self-service export or deletion (RL-056, RL-057), and running the script against production
(the author does that per request).

## Verification

Emulator run as above. `npm run lint`.
