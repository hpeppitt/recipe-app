## Context

The 4a profile has a Collabs tab: recipes by other cooks that this person contributed to.
Today credit is `collaborators: { uid, displayName }[]`, added with `arrayUnion` by the owner
(`updateSuggestionStatus`, `services/firestore.ts` ~743; RL-148 moves this into
`applySuggestion`). Querying by it needs `array-contains` on the exact object, and
`displayName` changes break the match (capabilities "Download my data" row says the same). A
plain uid list fixes that. No rules change: a verified owner update may change any field but
`createdBy.uid` and `createdAt`, and creates do not restrict keys. `publishRecipe` omits
`collaborators` from a re-publish because a merge replaces arrays (RL-037); the new list must
follow the same rule.

## Acceptance criteria

- [ ] Wherever RL-148's apply path adds a collaborator, the same write adds `collaboratorUids: arrayUnion(uid)`. A Keep as branch that credits the suggester on the new branch writes `collaboratorUids: [suggesterUid]` on that create.
- [ ] `publishRecipe` omits `collaboratorUids` from a re-publish exactly as it omits `collaborators`, and writes `collaboratorUids: []` (or the credited uids) on create.
- [ ] `PublishedRecipe` gains `collaboratorUids?: string[]`; Dexie rows are untouched (the own-recipe sync copies it through if present; no schema version change).
- [ ] No backfill: recipes credited before this ship without the list (the 2026-10-18 wipe left almost none). Say so in docs/data-model.md.
- [ ] Service tests (Firestore mocked): apply writes both fields in one update, re-publish omits both, create includes the list.
- [ ] `docs/data-model.md` recipes row and the suggestions paragraph describe the field.
- [ ] `npm test`, `npm run lint`, `npm run build` pass.

## Out of scope

The Collabs tab (RL-173). Any rules change. A composite index (RL-173 sorts on the client).
