## Context

The 4a profile has a Collabs tab: recipes by other cooks that this person contributed to.
Today credit is `collaborators: { uid, displayName }[]`, added with `arrayUnion` by the owner
(`updateSuggestionStatus`, `services/firestore.ts` ~743; RL-148 moves this into
`applySuggestion`). Querying by it needs `array-contains` on the exact object, and
`displayName` changes break the match (capabilities "Download my data" row says the same). A
plain uid list fixes that. No rules change: a verified owner update may change any field but
`createdBy.uid` and `createdAt`, and creates do not restrict keys. `publishRecipe` omits
`collaborators` from a re-publish because a merge replaces arrays (RL-037); the new list must
follow the same rule.

## Acceptance criteria

- [x] Wherever RL-148's apply path adds a collaborator, the same write adds `collaboratorUids: arrayUnion(uid)`. A Keep as branch that credits the suggester on the new branch writes `collaboratorUids: [suggesterUid]` on that create.
- [x] `publishRecipe` omits `collaboratorUids` from a re-publish exactly as it omits `collaborators`, and writes `collaboratorUids: []` (or the credited uids) on create.
- [x] `PublishedRecipe` gains `collaboratorUids?: string[]`; Dexie rows are untouched (the own-recipe sync copies it through if present; no schema version change).
- [x] No backfill: recipes credited before this ship without the list (the 2026-10-18 wipe left almost none). Say so in docs/data-model.md.
- [x] Service tests (Firestore mocked): apply writes both fields in one update, re-publish omits both, create includes the list.
- [x] `docs/data-model.md` recipes row and the suggestions paragraph describe the field.
- [x] `npm test`, `npm run lint`, `npm run build` pass.

## Out of scope

The Collabs tab (RL-173). Any rules change. A composite index (RL-173 sorts on the client).

## Verification

Service tests, `data-integrity-reviewer`. Emulator: an apply writes `collaboratorUids`; note the probe in Notes.

## Notes
- 2026-10-21 implementer: `applySuggestion` adds `collaboratorUids: arrayUnion(suggesterUid)` in the same `tx.update` as the edits and `collaborators` (skipped when the suggester is the owner; still unioned when the suggester was already in `collaborators`, so pre-RL-172 credit gains the uid). `publishRecipe` writes `collaboratorUids` on create, derived from `collaborators` (`[]` when none), and never on a re-publish; Keep as branch gets `[suggesterUid]` through that create. `PublishedRecipe.collaboratorUids?: string[]`. No rules change, no index, no Dexie version.
- Criterion 3: `collaboratorUids` is deliberately not synced into Dexie; there is no local reader. `Recipe` and `toLocalRecipe` do not carry it, which also keeps a stale local copy out of any re-publish. Logged in backlog/DECISIONS.md.
- Also: `assembleDataExport` aliases `collaboratorUids` like `collaborators` (`lib/dataExport.ts`); without it "Download my data" would carry other cooks' raw uids. Test fixture covers it.
- Emulator probe 2026-10-21 (`firebase emulators:exec --only firestore --project demo-rl172`, scratchpad vitest running the real `services/firestore.ts`, owner token with `email_verified: true`, Terms seeded, repo rules), 4 of 4 passed: Apply wrote `collaborators` [Sam] and `collaboratorUids` ['sam'] with `status: applied`; a stale re-publish (local `collaborators: []`) changed the title and left both fields as they were; Keep as branch created the branch with `collaborators` [Sam], `collaboratorUids` ['sam'] and `branched` landed; a first publish wrote `collaboratorUids: []`.
- Review fixes (data-integrity-reviewer): Apply unions every non-owner uid of the resulting `collaborators`, so legacy docs self-heal; create dedupes the derived list with a Set. `scripts/data-request.mjs`: erase removes the uid from `collaborators` and `collaboratorUids` in one update (the op's `arrayRemove` is now a field-to-values map; `collaboratorUids` named only when the stored list holds the uid, since arrayRemove on a missing field creates it); both export loops alias `collaboratorUids`; contributed recipes are found by `array-contains` on `collaboratorUids` unioned with the old full scan for legacy docs. Rules (repo only, never deployed; the ticket's out-of-scope line said no rules change, the reviewer asked for it): `hasBoundedContent` requires `collaboratorUids` absent or a list of at most 50. RL-160 Notes say the whole file deploys with it; RL-173 Notes ask for defensive rendering.
- Emulator probe round 2, same harness, 6 of 6 passed: the four checks above, plus an owner update with 50 uids accepted, 51, a string and null denied with permission-denied, and a `publishRecipe` create crediting 51 uids denied (no document written). The data-request script changes are covered by `scripts/data-request.test.mjs` only, not run against the emulator.
