## Context

Written for RL-210's recommendations. One `onSnapshot` on `kitchens/{uid}` per session for a
verified user, like the own-recipes listener (RL-078). Mutations are read-modify-write in a
transaction so two devices do not lose each other's lines, using the RL-212 helpers. Cloud
only; offline, mutations fail with a message (no queue, as for recipes, decision 1b).

## Acceptance criteria

- [x] `subscribeKitchen(kitchenId, cb)` and `updateKitchen(kitchenId, fn)` (transaction, creates the document on first write with `memberUids: [uid]`, sets `updatedAt: serverTimestamp()`, bounded at 5 s).
- [x] `useKitchen()` returns `{ kitchen, loading, error, addRecipe(recipe, servings), toggleLine(id), removeSource(recipeId), boughtItAll(), addPantry(name), removePantry(id) }`; verified users only, others get `kitchen: null` without reading. The kitchen id is the user's uid in Phase 2 (RL-238 changes how it is found).
- [x] A write past a cap shows "Your list is full. Clear some lines first." Offline or failed: "Couldn't update your kitchen. Check your connection and try again."
- [x] Tests (Firestore mocked): first write creates, transaction merge, caps, offline error, non-verified does not read.
- [x] `docs/data-model.md` read and write costs; `docs/architecture.md` names the listener.
- [x] `npm test`, `npm run lint`, `npm run build` pass.

## Out of scope

UI. Households.

Tests; emulator walk in Notes; `data-integrity-reviewer`.

## Notes

RL-211 review: before every kitchen write, guard the serialized document size (about 900 KB) and refuse with a clear message rather than letting Firestore fail with a size error. Use the per-item limits from RL-212.

Enforce the 300-item cap (KITCHEN_ITEM_CAP) before writing and tell the user; addedAt and now are epoch ms from the RL-212 helpers.

RL-213 implementation (2026-10-21): `kitchenFits` and `KitchenFullError` in `src/lib/kitchen.ts` guard both caps and a 900 KB JSON size (`KITCHEN_DOC_MAX_BYTES`) inside the transaction, before the write. Create sets exactly the five keys with `memberUids: [uid]` and `ownerUid: uid` from `auth.currentUser`; updates touch only `shopping`, `pantry` and `updatedAt`. The listener is a ref-counted module-level store in `useKitchen.ts`. A verified user with no document sees an empty kitchen (not null); the first write creates it. `addPantry` reuses `boughtItAll` on a one-line list for grouping and duplicate skipping. Offline is detected with `navigator.onLine` before trying. A timed-out transaction may still commit, so a retried `addRecipe` after a timeout can double amounts (same caveat as other 5 s bounds). Emulator walk not run; mocked tests only.

Review fixes (2026-10-21): timeout shows "It may have saved. Check your list before adding again."; a listener error drops the dead subscription, retries once after 2 s (with `getIdToken(true)` first on permission-denied) and the next acquire resubscribes; `kitchen` is null until the first snapshot; `toggleLine(id, done)` sets the state; one write in flight at a time, later calls are dropped (they get the running promise), not serialised; `updateKitchen` refuses a kitchenId other than the caller's uid; `kitchenFits` passes any change that does not grow the lists.
