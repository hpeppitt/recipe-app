## Context

Written for RL-210's recommendations. One `onSnapshot` on `kitchens/{uid}` per session for a
verified user, like the own-recipes listener (RL-078). Mutations are read-modify-write in a
transaction so two devices do not lose each other's lines, using the RL-212 helpers. Cloud
only; offline, mutations fail with a message (no queue, as for recipes, decision 1b).

## Acceptance criteria

- [ ] `subscribeKitchen(kitchenId, cb)` and `updateKitchen(kitchenId, fn)` (transaction, creates the document on first write with `memberUids: [uid]`, sets `updatedAt: serverTimestamp()`, bounded at 5 s).
- [ ] `useKitchen()` returns `{ kitchen, loading, error, addRecipe(recipe, servings), toggleLine(id), removeSource(recipeId), boughtItAll(), addPantry(name), removePantry(id) }`; verified users only, others get `kitchen: null` without reading. The kitchen id is the user's uid in Phase 2 (RL-238 changes how it is found).
- [ ] A write past a cap shows "Your list is full. Clear some lines first." Offline or failed: "Couldn't update your kitchen. Check your connection and try again."
- [ ] Tests (Firestore mocked): first write creates, transaction merge, caps, offline error, non-verified does not read.
- [ ] `docs/data-model.md` read and write costs; `docs/architecture.md` names the listener.
- [ ] `npm test`, `npm run lint`, `npm run build` pass.

## Out of scope

UI. Households.
