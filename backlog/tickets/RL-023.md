## Context

`handleDelete` in `RecipeDetailPage.tsx` (around line 151) deletes the local tree, then
calls `deletePublishedRecipeTree(...).catch(() => {})` without awaiting it, ignores the
`failed` count it returns, and navigates away. Offline, or with the tab closed early, the
recipe stays public at `/shared/:id` and the local copy, which is the user's only handle on
it, is already gone. There is no retry path.

`deletePublishedRecipeTree` counts every rejected delete as failed, including descendants
owned by other users, which the rules deny by design (see its doc comment). Those must not
be reported as a failure of the user's delete.

## Acceptance criteria

- [ ] `deletePublishedRecipeTree` accepts the caller's uid and only attempts deletes on cloud documents whose `createdBy.uid` matches it (ids known only from `extraIds` are still attempted). `failed` therefore counts only the user's own recipes.
- [ ] The cloud delete is attempted only for a user with `emailVerified`. Under the 2026-10-14 decision (RL-040) nobody else can have published anything, so for anonymous and signed-out users the delete is local only and can never show the failure dialog.
- [ ] `handleDelete` awaits the cloud delete, bounded with `withTimeout` from `lib/utils.ts` (10 seconds); a timeout counts as a failure.
- [ ] On success, navigation is unchanged.
- [ ] On failure or timeout, the page does not navigate. It shows a `ConfirmDialog` with the copy "Removed from this device, but {n} published {copy/copies} could not be removed from the shared library." and two actions: "Try again" (re-runs the cloud delete with the same ids) and "Leave anyway" (navigates as today).
- [ ] The button shows a busy state while the cloud delete is in flight and cannot be pressed twice.
- [ ] `docs/capabilities.md` describes the delete behaviour on failure.
- [ ] A `backlog/QA.md` entry: on the preview build, delete a published recipe with the network offline in devtools and confirm the dialog, then go online and "Try again" removes it.

## Out of scope

Reordering to cloud-first deletion, a persistent background retry queue, and deleting other
users' descendants (needs a Cloud Function).

## Verification

Unit test in the mocked-Firestore style of `src/services/firestore.favorites.test.ts`: a
tree with one foreign descendant and one own descendant whose delete rejects reports
`failed: 1`. Browser check as above.
