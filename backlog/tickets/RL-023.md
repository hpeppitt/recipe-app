## Context

`handleDelete` in `RecipeDetailPage.tsx` (around line 151) deletes the local tree, then
calls `deletePublishedRecipeTree(...).catch(() => {})` without awaiting it, ignores the
`failed` count it returns, and navigates away. Offline, or with the tab closed early, the
recipe stays public at `/shared/:id` and the local copy, which is the user's only handle on
it, is already gone. There is no retry path.

`deletePublishedRecipeTree` counts every rejected delete as failed, including descendants
owned by other users, which the rules deny by design (see its doc comment). Those must not
be reported as a failure of the user's delete.

## Acceptance criteria

- [x] `deletePublishedRecipeTree` accepts the caller's uid and only attempts deletes on cloud documents whose `createdBy.uid` matches it (ids known only from `extraIds` are still attempted). `failed` therefore counts only the user's own recipes.
- [x] The cloud delete is attempted only for a user with `emailVerified`. Under the 2026-10-14 decision (RL-040) nobody else can have published anything, so for anonymous and signed-out users the delete is local only and can never show the failure dialog.
- [x] `handleDelete` awaits the cloud delete, bounded with `withTimeout` from `lib/utils.ts` (10 seconds); a timeout counts as a failure.
- [x] On success, navigation is unchanged.
- [x] On failure or timeout, the page does not navigate. It shows a `ConfirmDialog` with the copy "Removed from this device, but {n} published {copy/copies} could not be removed from the shared library." and two actions: "Try again" (re-runs the cloud delete with the same ids) and "Leave anyway" (navigates as today).
- [x] The button shows a busy state while the cloud delete is in flight and cannot be pressed twice.
- [x] `docs/capabilities.md` describes the delete behaviour on failure.
- [x] A `backlog/QA.md` entry: on the preview build, delete a published recipe with the network offline in devtools and confirm the dialog, then go online and "Try again" removes it.

## Out of scope

Reordering to cloud-first deletion, a persistent background retry queue, and deleting other
users' descendants (needs a Cloud Function).

## Verification

Unit test in the mocked-Firestore style of `src/services/firestore.favorites.test.ts`: a
tree with one foreign descendant and one own descendant whose delete rejects reports
`failed: 1`. Browser check as above.

## Notes

- `deletePublishedRecipeTree(uid, id, rootId, extraIds)`: skips docs whose cloud `createdBy.uid` is someone else's; ids with unknown ownership (only in `extraIds`, or after a failed tree query) are still tried. Only caller is `RecipeDetailPage.tsx`.
- `ConfirmDialog` gained optional `cancelLabel` and `busy` props (defaults unchanged) for "Leave anyway" and the in-flight state.
- Ids the tree query did not return are checked with `getDoc`: missing docs are skipped (the rules deny deleting them, which made a phantom failure), foreign docs are skipped, own docs are deleted, and an unreadable doc is still attempted.
- On timeout the count is unknown, so the dialog states no number.
- `deleteRecipeTree` is wrapped in try/catch so a local failure cannot leave the busy state stuck.
- The delete dialogs render in every page branch, because the recipe stops resolving once the local copy is gone.
- Offline, Firestore queues the deletes rather than rejecting, so after the timeout dialog they may still land on reconnect without "Try again".
- Unit test: `src/services/firestore.deleteTree.test.ts` (5 cases, including a missing leftover id whose delete would reject: `failed: 0`). No page test for `handleDelete`: the page pulls Dexie live queries, cloud lookups and several hooks, so it needs a lot of module mocking beyond the RL-002 harness. No browser check was run.
