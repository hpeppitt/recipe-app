## Context

Written for RL-192's recommendations. `createSuggestion` (`services/firestore.ts` ~580) is the
model for a rate-limited create: a transaction reads `writeWindows/{uid}_{action}`, decides with
`nextWindow` (`src/lib/rateLimit.ts`), writes the content and the window together. Errors map
through `src/lib/errors.ts` (`rateLimitMessage`). Cloud only: nothing goes to Dexie.

## Acceptance criteria

- [ ] `logCook({ recipe, vote, note, user })` returns the new cook id; transaction with the `cook` window; `createdAt: serverTimestamp()`; bounded at 5 s; a limit hit throws the rate-limit error ("You've logged a lot of cooks today. Try again tomorrow.").
- [ ] `getRecipeCookSummary(recipeId)`: two `getCountFromServer` calls (all, `vote == 'again'`) plus the newest 20 cooks (`where recipeId == X`, `orderBy createdAt desc`, `limit 20`; if this needs a composite index, add it to `firestore.indexes.json` and `src/lib/indexes.test.ts`, deployed by RL-209). Bounded at 6 s.
- [ ] `subscribeOwnCooks(uid, onChange)`: `where uid == uid`, newest first, `limit 200`, for the cook log and Cooked stat.
- [ ] `setCookBranch(cookId, branchId)`: the one allowed update.
- [ ] `deleteCook(cookId)`.
- [ ] Hooks: `useRecipeCooks(recipeId)` (summary, read once per recipe visit, refreshed after the user logs a cook, reported as `recipe-cooks`) and `useOwnCooks()` (verified users only; others get an empty list without reading).
- [ ] Service tests with Firestore mocked: window and create in one transaction, server timestamp, counts, error mapping, signed-out reads allowed.
- [ ] `docs/data-model.md` read costs (summary: 2 count reads plus up to 20; own log: one per cook); `docs/architecture.md` names the cook writes.
- [ ] `npm test`, `npm run lint`, `npm run build` pass.
