## Context

Written for RL-192's recommendations. `createSuggestion` (`services/firestore.ts` ~580) is the
model for a rate-limited create: a transaction reads `writeWindows/{uid}_{action}`, decides with
`nextWindow` (`src/lib/rateLimit.ts`), writes the content and the window together. Errors map
through `src/lib/errors.ts` (`rateLimitMessage`). Cloud only: nothing goes to Dexie.

## Acceptance criteria

- [x] `logCook({ recipe, vote, note, user })` returns the new cook id; transaction with the `cook` window; `createdAt: serverTimestamp()`; bounded at 5 s; a limit hit throws the rate-limit error ("You've logged a lot of cooks today. Try again tomorrow.").
- [x] `getRecipeCookSummary(recipeId)`: two `getCountFromServer` calls (all, `vote == 'again'`) plus the newest 20 cooks (`where recipeId == X`, `orderBy createdAt desc`, `limit 20`; if this needs a composite index, add it to `firestore.indexes.json` and `src/lib/indexes.test.ts`, deployed by RL-209). Bounded at 6 s.
- [x] `subscribeOwnCooks(uid, onChange)`: `where uid == uid`, newest first, `limit 200`, for the cook log and Cooked stat.
- [x] `setCookBranch(cookId, branchId)`: the one allowed update.
- [x] `deleteCook(cookId)`.
- [x] Hooks: `useRecipeCooks(recipeId)` (summary, read once per recipe visit, refreshed after the user logs a cook, reported as `recipe-cooks`) and `useOwnCooks()` (verified users only; others get an empty list without reading).
- [x] Service tests with Firestore mocked: window and create in one transaction, server timestamp, counts, error mapping, signed-out reads allowed.
- [x] `docs/data-model.md` read costs (summary: 2 count reads plus up to 20; own log: one per cook); `docs/architecture.md` names the cook writes.
- [x] `npm test`, `npm run lint`, `npm run build` pass.

## Notes

Take displayName from the user's profile, not free input (RL-194 review: the rules do not tie it).

RL-196 implementation (2026-10-21):
- `logCook`, `getRecipeCookSummary`, `subscribeOwnCooks`, `setCookBranch`, `deleteCook` in `src/services/firestore.ts`; hooks `useRecipeCooks` and `useOwnCooks` in `src/hooks/useCooks.ts`. The create goes through `writeLimited`, so it has the same window and `last` handling as suggestions and recipes.
- displayName comes from the signed-in `AppUser` (the Firebase Auth name, which `useProfile.updateName` keeps in step with `profiles/{uid}`), trimmed to 100. Not a free input. Note trimmed, empty becomes null, capped at 500.
- A `permission-denied` on create reads `termsAcceptance/{uid}`; if the version is not `TERMS_VERSION` it throws `TermsNotAcceptedError` (message: "Accept the updated Terms to log a cook. Reload the page to see them."). Any other denial is rethrown as is.
- Two composite indexes added (`cooks` recipeId+createdAt desc, uid+createdAt desc), guarded in `src/lib/indexes.test.ts`, deployed by RL-209.
- `rejectAfter` gained an optional timeout so the summary is bounded at 6 s.
- Emulator walk not done; the rules side was emulator-checked in RL-194 and the service tests pin the exact create payload against `isWellFormedCook`.
- Review fixes: `logCook` now takes `recipeId` and reads the recipe in the transaction for `rootId`/`recipeOwnerId` (`RecipeNotPublishedError` when missing or rootless); optional `cookId` with a `'skip'` mode in `writeLimited` makes a same-id retry write nothing and not bump the window; `useRecipeCooks.log` keeps the id across a timeout; a failed refresh keeps the shown summary.
