## Context

Written for RL-193's recommendations (Firestore, not Storage); regroom if the author chose
otherwise. The uploaded-avatar rule (RL-019, `profiles`: `data:image/` string of at most 100000
characters) is the pattern. The cook (RL-194) carries `uid` and `recipeOwnerId`, so the photo
rule can read it with one `get()`.

## Acceptance criteria

- [ ] `match /cookPhotos/{cookId}`: `allow read: if true`. Create: `verified()`; keys exactly `uid, recipeId, url, createdAt`; `uid == request.auth.uid`; `get(/cooks/$(cookId)).data.uid == request.auth.uid` and its `recipeId` equals `recipeId`; `url is string && url.matches('^data:image/jpeg;base64,.*') && url.size() <= 200000`; `createdAt == request.time`. No update.
- [ ] Delete: verified, and either `resource.data.uid == request.auth.uid` or `get(/recipes/$(resource.data.recipeId)).data.createdBy.uid == request.auth.uid`.
- [ ] Emulator probe codes in Notes: cook adds (200), second add (403, exists), someone else adds for that cook (403), PNG or other prefix (403), 200001 characters (403), cook deletes (200), recipe owner deletes (200), third party deletes (403), signed-out read (200).
- [ ] `docs/data-model.md` collection row and rules paragraph, "in the repo, deployed by RL-209"; note that decision 3's size reasoning is met by the 200000 cap and the separate collection.
- [ ] `npm test`, `npm run lint`, `npm run build` pass.

Client (RL-205, RL-206). Deploy (RL-209).
