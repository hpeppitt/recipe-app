## Context

Written for RL-193's recommendations (Firestore, not Storage); regroom if the author chose
otherwise. The uploaded-avatar rule (RL-019, `profiles`: `data:image/` string of at most 100000
characters) is the pattern. The cook (RL-194) carries `uid` and `recipeOwnerId`, so the photo
rule can read it with one `get()`.

## Acceptance criteria

- [x] `match /cookPhotos/{cookId}`: `allow read: if true`. Create: `verified()`; keys exactly `uid, recipeId, url, createdAt`; `uid == request.auth.uid`; `get(/cooks/$(cookId)).data.uid == request.auth.uid` and its `recipeId` equals `recipeId`; `url is string && url.matches('^data:image/jpeg;base64,.*') && url.size() <= 200000`; `createdAt == request.time`. No update.
- [x] Delete: verified, and either `resource.data.uid == request.auth.uid` or `get(/recipes/$(resource.data.recipeId)).data.createdBy.uid == request.auth.uid`.
- [x] Emulator probe codes in Notes: cook adds (200), second add (403, exists), someone else adds for that cook (403), PNG or other prefix (403), 200001 characters (403), cook deletes (200), recipe owner deletes (200), third party deletes (403), signed-out read (200).
- [x] `docs/data-model.md` collection row and rules paragraph, "in the repo, deployed by RL-209"; note that decision 3's size reasoning is met by the 200000 cap and the separate collection.
- [x] `npm test`, `npm run lint`, `npm run build` pass.

## Notes

Implemented in `firestore.rules` (`match /cookPhotos/{cookId}`, after cooks). Two consistency
points from RL-194's review applied: create uses `acceptedTerms()` (which includes `verified()`),
like cooks, recipes and suggestions; the cook's own delete uses `signedIn()` so erasure works if
verification lapses, while the recipe owner's delete stays `verified()`. No explicit exists check
for "second add": the document id is the cook id, so a second write is an update and there is no
update rule. Confirmed by a variant run with `allow read, update: if true`: second add returned 200,
so the 403 below comes from the missing update rule. The size check runs before the regex. Review follow-up: the url regex is tightened to
`^data:image/jpeg;base64,[A-Za-z0-9+/]+={0,2}$` and the table below is from the re-run.
