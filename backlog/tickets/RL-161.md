## Context

When the chat finds similar recipes before generating, the user can choose "Create New
Recipe Anyway" (`RecipeChatPage.tsx` ~470, `dismissSimilar` in `useRecipeChat.ts` ~302); the new
original then has no tie to the family it resembles. 7d: the new recipe gets a **New original**
tag and a **Related family** card (accent-2-100, "Related family", the other family's emoji,
title, User Pill and "7 versions"), "Shown on both recipes, so people browsing either one find
the other", and a line "Is this really a version of Banana bread? **Move it into that family**.
You stay the author." The author put it in v1, design-first, on 2026-10-20, noting the conflict
with "originals never change" and with rules ownership: a client can only write its own
recipes (`isOwnerUpdate`), though an owner may already rewrite its own `parentId`, `rootId` and
`depth`. RL-162 to RL-164 are written for the recommended answers. Becomes `needs-human` when
approved.

## Questions and the groomer's recommendation

1. **Where the link lives**: only on the new original, as `relatedFamilyId = <the match's rootId>`;
   the other family finds its cousins with a public equality query on that field (recommended:
   no write to anyone else's recipe, no rules change, no Dexie bump since the field is not
   indexed locally). Or on both, which needs the other owner or a server.
2. **Which match**: the first match shown when the user chose to write it anyway (recommended),
   or let them pick.
3. **Where the card shows on the other side**: on that family's original only (recommended) or
   on every version in it. Show at most 3 cousins there.
4. **Move it into that family**: only the new original's author; only while every version in
   its own family is theirs (recommended), so no other cook's `rootId` needs rewriting. It
   attaches as a child of the matched recipe (which may itself be a branch), keeps its title,
   prompt and author, becomes "<root> variation", and its own branches move with it.
5. **"Originals never change"**: moving changes the moving recipe, never the family it joins.
   Confirm this does not break the principle (recommended reading: the rule protects the parent
   from being edited by a branch, which still holds).
6. **Tell the other family's author** when a recipe moves in: send the RL-153 `branch`
   notification (recommended) or nothing.
7. **Unlinking** a related family: not in v1 (recommended).
