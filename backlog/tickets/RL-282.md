## Context

Author decision, 2026-10-22: the flag defaults from the device time zone at sign-up and the
user can edit it. `AuthContext.ensureProfile` calls `createOrUpdateProfile(uid, { displayName })`
after the Terms check on every verified sign-in path (see "Terms acceptance is private..." and
the email-link order of operations in `docs/decisions.md`; do not reorder them).
`createOrUpdateProfile` already reads the profile before writing. Accounts created before this
ships have no `country` key, so "when the key is absent" covers both new sign-ups and the beta
testers' next sign-in, once; after that the user's choice (including null for No flag) is never
overwritten. A zone that maps to nothing writes null, so it is not retried.

Privacy implications, for RL-283 and the decisions entry: the country is inferred without
asking and is public; it is coarse location and personal data. It never comes from IP or GPS,
can be wrong for travellers and VPN users, is visible to the user on their own profile, and
can be removed with No flag.

## Acceptance criteria

- [x] `createOrUpdateProfile` takes an optional `{ defaultCountry }` used only when the document is created or lacks a `country` key; existing values, including null, are never changed by it.
- [x] `ensureProfile` passes `countryFromTimeZone(Intl.DateTimeFormat().resolvedOptions().timeZone)`; only ensureProfile passes it.
- [x] No extra profile read is added; ensureProfile stays fire-and-forget and still runs after the Terms check on every path.
- [x] Tests: new profile gets the zone's code; existing profile without the key gets it; existing `country: null` and `'GB'` are untouched; unknown zone writes null.
- [x] `docs/decisions.md` entry "Profile flag defaults from the time zone (author, 2026-10-22)" with the privacy points above; `docs/data-model.md` profiles row.
- [x] A `backlog/QA.md` entry: "Sign up a new account in a fresh browser; the flag matches your time zone. Set the computer's time zone to Europe/London, sign up another; it shows GB."
- [x] `npm test`, `npm run lint`, `npm run build` pass.

## Out of scope

The UI (RL-281). IP geolocation. Changing the flag when the user travels.

## Notes

- `createOrUpdateProfile(uid, data, { defaultCountry })` adds `country` to the same write when the doc is missing or has no `country` key; `data` wins if it sets country itself. Only `ensureProfile` passes the option.
- The write is the existing ensureProfile update/create (displayName plus country), owner and verified, passing `countryOk` in the RL-278 rules; failure is still swallowed by `.catch`.
- Tests: `src/services/firestore.profiles.test.ts` (new, missing key, null, code, unknown zone, no option) and `src/contexts/AuthContext.test.tsx` (Europe/London to GB, unknown zone to null; older assertions accept any options so they pass in any machine time zone).
- Before RL-291 deploys, the live rules do not bound `country`, but the value always comes from the table, so it is a valid code or null.
