## Context

New standing product decision from the author, 2026-10-14, quoted: "For anything anonymous,
let's make it easy and say that anon accounts can ONLY save a bookmark locally, nothing
else. I am the only current user, so anything we push new will be the standard, we can wipe
all previous data."

This reverses the consume/contribute split: product decision 1 in `docs/decisions.md`, the
`verified()` comment block in `firestore.rules` (lines 10-43), and the notifications comment
(lines 159-167), which deliberately keep favourite, follow and notification creates open to
anonymous accounts. It also removes the reason `isOwnerUpdate` and recipe delete stay on
`signedIn()` (pre-gate anonymous recipes), since RL-042 wipes them.

This ticket is the rules and docs half. RL-041 is the client half and must ship in the same
release, before RL-022 deploys these rules.

Generation checked: an anonymous user cannot generate today. `RecipeChatPage.tsx` (line 137)
shows the sign-up screen to any user without `emailVerified`, and generation never touches
Firestore (Firebase AI Logic, called from `services/gemini.ts`). Saving a generated recipe
writes Dexie and then `publishRecipe`, whose create rule already needs `verified()`. So the
decision changes nothing for generation. That conclusion goes to the author as a question to
confirm, not as a quiet decision.

## Acceptance criteria

- [x] `verified()` replaces `signedIn()` on every client write rule: recipe `isFavoriteCountBump`, `isOwnerUpdate`, and delete; favourites create and delete; suggestions update (review); notifications create, update (mark read) and delete; profiles create, update (owner and `isFollowerCountBump`) and delete; follows create and delete.
- [x] Unchanged on purpose: recipe `isViewIncrement` (open to signed-out visitors) and `clientErrors` create. A comment on each says why they are exempt from the decision (an implicit page-view metric and crash telemetry, not user actions).
- [x] Read rules are unchanged here. Suggestion reads are tightened in RL-018.
- [x] The comments that justify anonymous access (the `verified()` block's "Reading, favouriting and following deliberately stay open" paragraph, the notifications block, the `isOwnerUpdate` pre-gate paragraph) are rewritten to state the new rule and cite the decision.
- [x] `docs/decisions.md`: product decision 1 gets a dated superseding entry with the author's quote, the consequence (anonymous accounts hold local bookmarks only; every cloud action needs a verified email), and that existing data is wiped (RL-042). The original text stays, marked superseded.
- [x] `docs/data-model.md` rules section (around lines 71-90) and `docs/capabilities.md` rows "Verified-email gate on contributing", "Anonymous sign-in", "Anonymous → email upgrade" and favouriting and following describe the new rule.
- [x] Generation is confirmed unchanged with the evidence above in the PR description, and listed for the author to confirm.
