## Context

Two problems in one flow.

1. `recipeOwnerId` on a suggestion is client-supplied and unchecked (`firestore.rules`
   lines 117-119). A wrong value means the real owner can never review it (update requires
   `resource.data.recipeOwnerId == request.auth.uid`), and `allow delete: if false` means it
   stays forever.
2. `updateSuggestionStatus` (`services/firestore.ts`, around lines 470-522) writes
   `status: 'approved'` and fires the notification before the collaborator `arrayUnion`. If
   that last write fails it returns `null`, the suggestion is stuck "approved" with no
   collaborator, the suggester is told it was approved, and `handleReview` in
   `RecipeDetailPage.tsx` treats the `null` as success and navigates to the variation flow.

The FUN-7 fix note in `AUDIT.md` explains why the collaborator is mirrored to Dexie
(`addLocalCollaborator` in `useSuggestions.approve`); keep that.

## Acceptance criteria

- [ ] Suggestion create additionally requires `get(/databases/$(database)/documents/recipes/$(request.resource.data.recipeId)).data.createdBy.uid == request.resource.data.recipeOwnerId`.
- [ ] On approve, `updateSuggestionStatus` adds the collaborator first, then writes `status`, then sends the notification. If the collaborator write fails it throws (after `reportError`) without touching status or notifying.
- [ ] On reject, behaviour is unchanged.
- [ ] `useSuggestions.approve` mirrors to Dexie only after the cloud writes succeed, as now.
- [ ] `handleReview` treats a `null` result from `approve` as a failure: it shows the existing "Couldn't approve that suggestion. Please try again." error and does not navigate.
- [ ] Retrying an approval whose status write failed after the collaborator write succeeded works (the `arrayUnion` is idempotent) and is covered by a comment.
- [ ] `docs/data-model.md` suggestions paragraph mentions the owner check and its one extra read per suggestion.
- [ ] A `backlog/QA.md` entry: approve a suggestion on the preview build and confirm the suggester appears as a collaborator and receives the approval notification.

## Out of scope

Cleaning up existing suggestions with a wrong `recipeOwnerId` (RL-042 wipes all
production data), the read rule (RL-018), and the deploy (RL-022).
