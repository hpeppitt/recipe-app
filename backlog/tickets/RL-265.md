## Context

RL-256 let an owner publish a collection (`visibility: 'public'`) with current Terms but no write
limit; its pending row left a write window to the author. The author decided on 2026-10-22: a
daily cap of 5 publishes per user, using the existing write-window pattern (RL-048, RL-049; see
the writeWindows section of `docs/data-model.md` and the `writeWindows` block and `movedWindow()`
in `firestore.rules`). `cook` (RL-194) is the most recent action added and is the template: every
place that lists `'cook'` gets `'cookbook'` too.

A publish is a write that makes a collection public: an update from `private` to `public`, or a
create with `visibility: 'public'` (the client never creates one public today, but the rules
allow it, so it must be bound too). Editing a description or the recipe list of an already
public cookbook, unpublishing, and following are not publishes. Unpublish then publish again
counts again.

Client side, `setCookbookSharing` (`services/firestore.ts`) is a plain `updateDoc`. A publish
must go through `writeLimited` with action `'cookbook'`. `writeLimited` does `tx.set(ref, data)`,
so either pass a data function that reads the collection inside the transaction and returns the
whole document with `visibility`, `description` and `updatedAt` changed (keeping `ownerUid`,
`createdAt`, `followerCount` and `lastAddedAt` as stored, so a concurrent follow bump is not
lost), or add a narrowly scoped update mode to `writeLimited`. Either is fine; log the choice.
`useCollections`' `write()` turns every unknown error into the generic failure copy, so a
`RateLimitedError` must be mapped to its own copy there.

The rules edit stays in the repo; RL-261 deploys it. Until then production has no cookbook
rules at all (Share already fails live, per the RL-257 QA note), so there is no deploy-order gap
beyond RL-261's own.

## Acceptance criteria

- [ ] `firestore.rules`: `cookbookCap()` returns 5; `capFor()` maps `'cookbook'` to it and `windowMsFor()` to `recipeWindowMs()`; `ownWindowIds()` adds `u + '_cookbook'` (and its comment says six ids); the "Write limits" comment block lists `cookbooks     5 per day (publishes: a collection becoming public)`.
- [ ] The collection create rule, when `visibility == 'public'`, and the owner update rule, when `resource.data.visibility != 'public'` and the result is `'public'`, also require `movedWindow('cookbook', 'collections/' + collectionId)`. An update that keeps a public collection public, or makes it private, needs no window. The collections comment's access budget is updated (a publish is now terms plus the window).
- [ ] `src/lib/rateLimit.ts`: `'cookbook'` in `RateLimitAction`, `COOKBOOK_CAP = 5` on `RECIPE_WINDOW_MS`, in `RATE_LIMITS` and the file comment. `rateLimit.test.ts` extends the existing literal, map and `ownWindowIds` assertions to `cookbook` and asserts `movedWindow('cookbook', 'collections/' + collectionId)` is in the rules.
- [ ] `setCookbookSharing` publishes (private to public) through `writeLimited(..., 'cookbook', ...)` and leaves stop-sharing as a plain update with no window. At the cap it throws `RateLimitedError('cookbook')` having written nothing (`firestore.cookbook.test.ts`).
- [ ] `rateLimitMessage` in `src/lib/errors.ts` returns "You've shared a lot of cookbooks today. Try again tomorrow." for `'cookbook'`, and the Share as a cookbook sheet shows exactly that in its existing `role="alert"` line, with the description kept (`useCollections` maps `RateLimitedError` to it without setting the page `error`; tests in `useCollections.test.tsx` and `CollectionPage.test.tsx`).
- [ ] The `writeWindows` id lists in Download my data (`services/firestore.ts`, the `writeWindows` export section) and `scripts/data-request.mjs` include `cookbook`, with their tests updated.
- [ ] Emulator probes recorded in Notes: five publishes in a day (200 each, with the window), the sixth (403), a publish without the window move (403), a public create without the window (403), a description edit on a public cookbook without the window (200), unpublish without the window (200), a window update past the cap (403), and the existing RL-256 Terms probes still as before.
- [ ] `docs/data-model.md`: the `writeWindows` table row and section list `cookbook` (5 a day, publishes only), and the collections rule description names the window; "in the repo, deployed by RL-261".
- [ ] `docs/capabilities.md` cookbook sharing row names the cap and the copy.
- [ ] `docs/decisions.md`: a dated addendum under "Cookbooks are public collections followed by pull (RL-255)": 5 publishes a day through a `cookbook` write window, counted on the change to public, rejected alternative no limit (RL-265, author decision 2026-10-22).
- [ ] `backlog/DECISIONS.md`: the RL-256 row is marked `decided 2026-10-22: cookbook write window, 5 a day (RL-265)`.
- [ ] A `backlog/QA.md` entry: on the emulators or after RL-261, share and stop sharing one cookbook until the sixth Share shows the copy above; adding a recipe to an already shared cookbook still works after the cap.
- [ ] `npm test`, `npm run lint`, `npm run build` pass.
