## Context

A brand-new browser profile opening `/recipe/:id` can render "Recipe not found" for a
recipe that exists: the bounded cloud read loses its race on a cold connection (fresh App
Check token exchange) and the page treats "did not arrive in time" as "does not exist". A
first-time visitor following a shared link reads that as a dead link and does not retry.
`useRecipe` already sets `error: true` on timeout and exposes `cloudError` and `retry`
(added for UI-12), so the defect may be in how `RecipeDetailPage` renders that state.
Establish which before changing anything.

## Acceptance criteria

- [x] A timeout or network failure on the cloud read renders a "Could not load this recipe" state with a working Try again button, matching the existing `parentCloudError` pattern.
- [x] "Recipe not found" renders only when the cloud read completed and returned no document.
- [x] The timeout path is covered by a test (hook-level if RL-002 has landed, otherwise by extracting the state decision into `src/lib`).

## Out of scope

Changing the timeout value or adding retries inside `withTimeout`.

## Verification

Tests. Human QA: a fresh-profile cold load of a shared link, noted in `backlog/QA.md`.

## Notes

Defect location: neither useRecipe nor RecipeDetailPage. The hook already sets cloudError on timeout or rejection (and tells "Dexie unsettled" and a stale id apart from "checked"), and the detail page already branched on it. The page that lost the distinction was RecipeEditPage, which ignored cloudError and showed "Recipe not found" on a timeout. Fixed there with the same state and a Try again button. The detail page only got its copy aligned to "Could not load this recipe" and "Try again". Loading never flashes not-found: isLoading stays true until the cloud read settles. VersionTreePage, RecipeChatPage and the detail page already handle cloudError. A hook test (src/hooks/useRecipe.test.tsx) covers timeout (real 6s wait), rejection, retry and genuine absence. No state-decision extraction to lib was needed.
