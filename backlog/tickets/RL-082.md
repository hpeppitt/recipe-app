## Context

Author answer of 2026-10-18: a verified user's save goes to Firestore first and is cached
in Dexie only on success; a failed or timed-out publish is an error with a retry, and nothing
is left as a local-only own recipe. Generation needs the network, so there is no offline
create and no queue. Decision 1b in `docs/decisions.md` (RL-076) records it.

Today `saveRecipe` in `src/hooks/useRecipeChat.ts` calls `createRecipe` (`src/db/recipes.ts`,
which mints the id and adds the Dexie row), then waits up to `PUBLISH_TIMEOUT_MS` (4 s) for
`publishRecipe`, and navigates to `/recipe/:id` with `saved: 'local'` and an optional RL-049
`note` when the publish failed. Under the new sync (RL-078) that local row would be removed by
the next snapshot, so the order must flip.

What already makes a retry safe: `publishRecipe` (`src/services/firestore.ts`) re-reads the
recipe inside its create transaction and writes the re-publish merge, with no window, no
counters and no `recipeCount` bump, if it exists by then (RL-049). So retrying with the
**same id** after a timeout that actually landed cannot create a duplicate or count twice.
A new id per attempt would. `rateLimitMessage` (`src/lib/errors.ts`) turns the daily-cap
error into "You've published a lot today. Try again tomorrow." `publishRecipe` needs no
change.

There is no `useRecipeChat.test.tsx` yet; create it. Local-only mode (Firebase not configured) cannot generate, so it never reaches this path in
practice; keep its Dexie-only branch as it is.

## Acceptance criteria

- [x] `src/db/recipes.ts` gains `buildRecipe(...)` with the same parameters as `createRecipe`, returning the record without writing it; `createRecipe` becomes `buildRecipe` plus `db.recipes.add`. Tests cover both.
- [x] For a verified user with Firebase configured, `saveRecipe` builds the recipe once and keeps it in a ref for the chat session's current target version, publishes it with the existing 4 s bound, and only on success `put`s it in Dexie, tracks `trackRecipeCreated`, and navigates with `saved: 'cloud'`.
- [x] On a failed or timed-out publish nothing is written to Dexie, the page stays, and the hook's `error` is set to `rateLimitMessage(err)` when that returns a message, otherwise "Couldn't save the recipe. Check your connection and try again." The save button is re-enabled.
- [x] Pressing Save again for the same version retries with the same id (asserted in a test); saving a different version builds a new recipe.
- [x] A failure of the Dexie `put` after a successful publish is logged and reported (`save-recipe-cache`) and the save still counts as done: navigation proceeds, and RL-078's listener fills the row.
- [x] Without Firebase configured the existing Dexie-only save is unchanged.
- [x] `src/hooks/useRecipeChat.test.tsx` covers: success order (publish before the Dexie write), failure leaves Dexie empty and sets the error, the rate-limit message, and same-id retry.
- [x] `RecipeChatPage.tsx` shows the save error where the hook's errors already render, and the double-tap guard still holds.
- [x] `docs/capabilities.md` "Save a generated recipe" row and `docs/data-model.md` (write order and the RL-049 "the recipe is already in Dexie" sentence) describe the cloud-first save.
- [x] A `backlog/QA.md` entry: on the preview as a verified user, generate and save, and confirm the recipe page and Explore show it; generate again, set DevTools offline, tap Save, confirm the error and that nothing new appears in My Recipes, then go online and tap Save again and confirm exactly one copy appears.
- [x] `npm run build`, `npm run lint` and `npm test` pass.

## Notes

- 2026-10-18 implementer: `buildRecipe` (pure, no write), `createRecipe` = build plus `add`, and a
  small `cacheRecipe` (`put`) in `src/db/recipes.ts`. `saveRecipe` keeps `{ source, recipe }` in a
  ref keyed on the identity of the `GeneratedRecipe` object the card passes, so the same card
