## Context

"Export All Recipes" in `SettingsPage` exports local Dexie recipes only. GDPR and UK GDPR give
a right to data portability, which today is met only by email (RL-055). Everything a verified
user owns in the cloud is readable by them under the rules, so a client-side export is
possible without a server: profile, own published recipes, favourites, follows where they
are either party, suggestions they made or received, their messages, notifications addressed
to them, and their `termsAcceptance` (RL-047).

## Acceptance criteria

- [x] Settings, Data section, gains "Download my data", shown to signed-in users. Anonymous users get only local data (recipes and bookmarks), labelled as such.
- [x] It produces one JSON file containing the local export plus the cloud data listed above, with a top-level `exportedAt`, `uid` and schema `version`.
- [x] The assembly is a pure function in `src/lib/dataExport.ts` with tests; the Firestore reads live in `services/firestore.ts`.
- [x] A read that fails is listed in the file's `errors` array instead of aborting the export.
- [x] `docs/capabilities.md` updated; the Privacy Policy wording may then point at it (author re-signs per RL-046).
- [x] A `backlog/QA.md` entry: download on the preview build and check the file contains a favourite, a follow and a suggestion made on the account.

## Out of scope

Deletion (RL-057), import of this format, and exporting other users' replies beyond the
user's own threads.

## Verification

`npm test`, `npm run build`, then the browser check above.

## Notes

- Pure assembly in `src/lib/dataExport.ts` (tests in `dataExport.test.ts`); reads in `fetchCloudDataForExport` in `src/services/firestore.ts` (tests in `firestore.dataExport.test.ts`); button and download in `SettingsPage.tsx` (tests in `SettingsPage.test.tsx`); `exportAllFavorites` added to `src/db/favorites.ts`.
- Queries (all filter on what the rule checks, no orderBy so no new index): recipes `createdBy.uid`; favorites `uid`; notifications `recipientUid`; follows `followerId` and `followingId` merged; suggestions `suggestedBy.uid` and `recipeOwnerId` merged, each thread read by parent path; profile, termsAcceptance and the four `writeWindows/{uid}_{action}` ids by get (writeWindows included: cheap and owner-readable).
- Emulator check (`firebase emulators:exec --only firestore --project demo-rl056`, unsigned tokens, script in the session scratchpad, not in the repo). Verified owner: every list above HTTP 200 with the seeded doc, an unfiltered messages list 200, termsAcceptance 200, writeWindows 200 (missing id 404, not denied), profile 404 (none seeded). Another uid asking for the same data: favorites, follows (both), suggestions (both), notifications lists 403 and termsAcceptance and writeWindows gets 403; a non-participant's unfiltered messages list 403. Signed-in but unverified (email_verified false): favorites, follows, notifications, recipes 200, both suggestions queries 403.
- What an unverified email user sees: the file downloads, the `suggestions` section is in `errors` as permission-denied, the status line says 1 part could not be fully read. Anonymous and signed-out users get local only with `cloud: null` and a note.
- Truncation: 500-row pages, up to 10000 rows per query, then a warning in `errors` (never silent). A partly failed two-query merge keeps the rows it got and warns.
- Local recipes are redacted too (other creators and collaborators become `other-user-N`, including inside nested `chatHistory[].recipe`); the `local` placeholder uid is kept. On a shared browser Dexie is not partitioned per account, so the local `recipes` section may contain recipes created under another account on this device: they are content on this device and are kept, with other identities aliased. Bookmark rows whose uid is neither the requester's nor `local` are left out and counted in `local.bookmarksOfOtherAccountsOmitted` (omitting is safer than aliasing: they are another person's reading habits).
- Collaborator-on-others'-recipes is intentionally not exported: the recipe is the owner's content, the user's contribution appears through their suggestions, and finding them needs `array-contains` on the exact `{uid, displayName}` object (a name change breaks it). `clientErrors` are not readable by clients; the operator export covers them.
- Unknown fields on follows, notifications, suggestions, replies and favourites are dropped by a field whitelist (chosen over a string-scrub pass as simpler and not dependent on seeing the other uid first).
- Suggestions: reply threads are read 10 at a time. On the 30s deadline the rows and threads read so far are returned with a warning. An unverified account skips suggestions with "Verify your email to include suggestions".
- The 10000 cap now peeks one extra row, so exactly 10000 is not reported as truncated; the existing paging test now expects the peek query (21 queries, was 20) and `fetchCloudDataForExport` takes `(uid, emailVerified)`, so the Settings test asserts `('u1', true)`.
- Not fixed (low, in QA.md): conditional live regions, UTC filename date.
