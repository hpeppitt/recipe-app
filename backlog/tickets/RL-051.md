## Context

RL-047 (terms acceptance) and RL-048 and RL-049 (rate limits) change `firestore.rules`
after RL-022's deploy. Kept as a second deploy rather than folded into RL-022 so the P1
security rules are not held up by the terms text (RL-046) or the rate-limit work. Same
procedure and same reasoning as RL-022: the new client works under the old rules, the old
client does not work under the new ones (it writes no window documents and no terms acceptance),
so client first, rules last. The procedure for diffing the live ruleset is in
`docs/operations.md`.

*Update 2026-10-15.* This is the same deploy as RL-022, not a second one: the rules file
deploys as one unit, so RL-022's rules step already carries the RL-047, RL-048 and RL-049
guards. Keep the two tickets for their separate acceptance and QA lists, but run them as one
sequence from the "Release and deploy runbook" in `docs/operations.md`. Between the client and
the rules, suggestions, replies, notifications and first publishes fail (RL-048, RL-049): keep
the gap to minutes.

## Acceptance criteria

- [ ] RL-046 is signed off, so the terms text may ship.
- [ ] The live ruleset is diffed against HEAD and the current ruleset id recorded as the rollback target.
- [ ] The client with RL-045, RL-047, RL-048 and RL-049 is released via `/release`.
- [ ] The author's own `termsAcceptance/{uid}` document exists with the current version before the author's first contributing write (recipe, suggestion or reply create), by either of two ways. The client cannot create it before the rules are live (no rule matches `termsAcceptance`, so its read and write are denied), so "sign in on the new client and accept beforehand" does not work. (a) Straight after the rules deploy, reload the live app signed in with the verified account and accept the dialog (or let the stored acceptance be written). (b) Before the deploy, create the document by hand in the Firestore console (console writes bypass rules) as `termsAcceptance/{uid}` with `version` (string, the current `TERMS_VERSION`), `acceptedAt` (integer ms) and `recordedAt` (timestamp), only AFTER the RL-042 wipe (the wipe deletes it) and with `version` re-checked against `TERMS_VERSION` at deploy time (if RL-046 changes the terms date, a hand-made document is stale and the dialog asks again).
- [ ] `firebase deploy --only firestore:rules` is run and the post-deploy diff is empty.
- [ ] The date and ruleset ids are recorded in `docs/operations.md`.
- [ ] The QA.md checks from RL-047, RL-048 and RL-049 are done on live.
