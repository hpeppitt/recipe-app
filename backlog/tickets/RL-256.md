## Context

Written for RL-255's recommendations. RL-211's collection rule is owner-only with
`visibility == 'private'` fixed. The profile `followerCount` ±1 bump (`isFollowerCountBump`
pattern) is the model for a foreign counter update.

## Acceptance criteria

- [x] Collections: read if `resource.data.visibility == 'public'` or the owner; the owner may change `visibility` between `private` and `public`, `description` (string <= 280 or null) and `lastAddedAt` (== request.time, set when `recipeIds` grows); anyone verified may bump `followerCount` by exactly ±1 and nothing else.
- [x] `match /cookbookFollows/{followId}`: id `{uid}_{collectionId}`; create and delete by that uid, verified, only for a public collection (`get`); keys `uid, collectionId, createdAt, lastSeenAt`; update only `lastSeenAt` by the follower; read by the follower only.
- [x] Emulator probe codes in Notes, including a signed-out read of a public (200) and a private (403) collection, a follow of a private one (403), and a +2 bump (403).
- [x] `docs/data-model.md`, "in the repo, deployed by RL-261".
- [x] `npm test`, `npm run lint`, `npm run build` pass.

## Notes

RL-256 (2026-10-22, reworked after data-integrity review). Rules only, plus `COOKBOOK_DESCRIPTION_MAX` (280) in `src/lib/kitchen.ts`, tied to the rules text by `kitchen.test.ts`. Emulator only (`firebase emulators:exec --only firestore --project demo-rl256`, REST with unsigned test tokens; `Bearer owner` only to seed termsAcceptance documents and a follow of a deleted collection). Nothing deployed.

Design:
- Collections read: `visibility == 'public'` (anyone, signed out included) or the verified owner. A `where ownerUid ==` own query and a `where visibility == 'public'` query both pass; unfiltered lists deny.
- `description`, `lastAddedAt`, `followerCount` are optional keys, so RL-211 documents stay valid. Create allows `followerCount` 0 and `lastAddedAt` equal to the request time.
- Owner update: `visibility` in private/public, `description` null or <= 280, `lastAddedAt` only to the request time and only when `recipeIds.size()` grows (optional, RL-257 sets it); never `ownerUid`, `createdAt`, `followerCount`.
- Review fix 4: an owner create or update whose resulting visibility is `'public'` also needs `acceptedTerms()` (a published cookbook is public content, like a cook). No write window: no collection rule has one, and adding a `cookbook` action means a sixth id in `ownWindowIds()`, `capFor()`, `windowMsFor()`, `RATE_LIMITS` and its test, plus a client transaction; left as a choice for the author (pending row in backlog/DECISIONS.md).
- Review fixes 1 and 2: the bump (`isFollowBump()`) is verified, `followerCount` only, and tied to the writer's own follow `cookbookFollows/{uid}_{collectionId}` in the same batch: +1 needs `!exists && existsAfter` and a public collection; -1 needs `exists && !existsAfter`, any visibility, and the result >= 0. The owner bumps only through their own follow, like anyone. A follow create or delete without a bump is still allowed (erasure, a cookbook deleted under the follower), so the count can only drift low, never be pushed up.
- `cookbookFollows`: get decided by the id prefix (missing own follow gives 404), list on `where uid ==` own; create verified, exact keys, both timestamps the request time, id `{uid}_{collectionId}`, collection public (one `get`); update `lastSeenAt` only, to the request time; delete signed in only with no public check (deviation logged in backlog/DECISIONS.md).
- Access budget: owner private write 0, owner public write 1 (termsAcceptance); follow create 1 (the collection); follow plus bump batch 2 to 3 (the collection, the follow before and after).
