## Context

Under the 2026-10-14 decision an anonymous account bookmarks to Dexie only (RL-041). The
author has since decided that adding an email must carry those bookmarks into cloud
favourites on the verified account. There are two upgrade paths (`completeEmailSignIn` in
`services/firebase.ts`, `runEmailLinkCompletion` in `AuthContext.tsx`):

- **Linked** (`linked: true`): the uid is kept, so the Dexie rows are already under the right
  uid and only the cloud half is needed.
- **Existing account** (`previousUid` set): `runMigration` moves Dexie rows to the new uid with
  `migrateFavoritesUid` (`db/favorites.ts` lines 11-21), which deletes and re-puts one row at
  a time with no transaction, so a failure midway loses bookmarks. It is untested. This was
  the original audit finding #20.

The cloud writes must pass RL-040's rules: `verified()` on the favourite create and on the
`favoriteCount` +1 bump. Both linking and email-link sign-in mint a token with
`email_verified` immediately (see "Email-link completion has a required order of operations"
in `docs/decisions.md`). Idempotence comes from the rules: favourites have `allow update: if
false`, so writing a favourite that already exists is denied and the whole batch rolls back,
which means a retry can never bump the count twice. A batch whose recipe no longer exists in
the cloud (deleted, or never published) also fails on the bump, so that bookmark stays local.

## Acceptance criteria

- [x] `migrateFavoritesUid` runs its read, deletes and puts inside `db.transaction('rw', db.favorites, ...)`, preserving `createdAt`.
- [x] A new `pushLocalFavoritesToCloud(uid)` writes, for each Dexie favourite of `uid`, one `writeBatch` containing `favorites/{uid}_{recipeId}` (same fields as `addCloudFavorite`, with the local `createdAt`) and the `favoriteCount` `increment(1)`. Batches run one at a time; a denied batch is skipped and counted, not retried. No notifications are sent for migrated favourites.
- [x] Which rows to try is a pure function in `src/lib/favoritesMigration.ts` (local rows in, rows to push out, deduplicated by recipe id), with tests.
- [x] `AuthContext` calls it once after a successful upgrade on either path (after `runMigration` on the existing-account path), not on ordinary sign-ins.
- [x] A failed or partial push leaves Dexie unchanged and is reported once through `reportError` with context `favorites-upgrade`; the user is not blocked.
- [x] `src/db/favorites.test.ts` covers: rows move to the new uid, other users' rows untouched, a put that throws mid-loop leaves every row under the old uid. `src/services/firestore.favorites.test.ts` (mocked Firestore) covers: one batch per favourite with the bump, a rejected batch does not stop the rest.
- [x] `docs/capabilities.md` (anonymous upgrade row) and `docs/data-model.md` (favourites) describe the carry-over.
- [x] A `backlog/QA.md` entry: on the preview build, bookmark two recipes as anonymous, add an email, then confirm both show as favourites and each recipe's favourite count went up by one; bookmark a third local-only recipe and confirm it stays a local bookmark.

## Out of scope

Pulling cloud favourites down to other devices (RL-043), unfavourite sync, and favourites of
recipes that were never published.

## Verification

`npm test`. Emulator walk-through of both upgrade paths with RL-040's rules loaded, recorded
in Notes, including a second run that pushes nothing and bumps nothing.

## Notes

- 2026-10-15 implementer. `migrateFavoritesUid` now runs inside one `db.transaction('rw', db.favorites, ...)`; the rollback test fails on the old code (checked by stashing the fix). No Dexie version block touched.
- `pushLocalFavoritesToCloud(uid)` in `src/services/firestore.ts` reads Dexie, selects rows with `selectFavoritesToPush` (`src/lib/favoritesMigration.ts`), and commits one batch per row sequentially, each bounded by `withTimeout` at 5000 ms. It returns `{ attempted, pushed, skipped }` and never touches Dexie or sends notifications. `recipeOwnerId` comes from the local recipe, else `'local'` (logged in `backlog/DECISIONS.md`).
- Order of operations ("Email-link completion has a required order of operations", docs/decisions.md): the push runs only after `completeEmailSignIn` has returned a result, so after `authStateReady()`, after the existing-account check, after the link or sign-in that mints the `email_verified` token, and after the URL is cleared. It adds no step before or inside that sequence. Linked path: after `setUser` and `ensureProfile`. Existing-account path: after `await runMigration(...)`, `clearAnonymousUid()` and `addPreviousUid()`. It is fire-and-forget, guarded by a per-uid ref and by `emailVerified`, and catches everything into one `reportError(..., 'favorites-upgrade')`, so the upgrade state is set regardless. Not called from `onAuthStateChanged` (ordinary sign-ins) or sign-out.
- Emulator probes, 2026-10-15: `firebase emulators:exec --only firestore --project demo-rl034` with a REST `:commit` script in the scratchpad (unsigned emulator tokens; two recipes `r1`, `r2` seeded as owner `chef` with `favoriteCount` 0). Each commit is the push's batch: favourite set plus recipe update with `favoriteCount` increment 1 and `exists: true`.
