## Context

`useFollowers` in `hooks/useFollow.ts` is the pattern to copy: state stamped with the key it
belongs to, a `cancelled` flag, and a `.catch` that reports and settles. Its neighbours do
none of that:

- `useFollow` (lines 22-45): the lookup has no catch or cancel and is never reset when
  `targetUid` changes, so "Following" from profile A shows on profile B until B's lookup
  returns. `toggle` has no catch, so a failed follow is an unhandled rejection with no
  feedback.
- `useCloudFavorite` (`hooks/useFavorites.ts` lines 119-156): the same three problems.
- `useFollowingList` (`useFollow.ts` lines 96-111): no catch, so a failure leaves
  `isLoading` true forever; no cancel.
- `useUserRecipes` and `useFollowingRecipes` (`hooks/useUserRecipes.ts` lines 47-98): no
  cancel, so profile A's late response renders under profile B.
- `useFavoriteIds` (`useFavorites.ts` line 28) builds a new `Set` every render, which
  defeats the `useMemo` in `useRecipeLibrary` that depends on it.

RL-041 changes what these hooks do for anonymous users (local bookmark only, follow routes to
sign-up) and lands first. The hygiene below then applies to the verified-user cloud paths
that remain.

## Acceptance criteria

- [x] `useFollow` and `useCloudFavorite` keep their lookup result keyed by `uid:targetId`, derive `false` when the key does not match the current one, ignore responses after cleanup, and on lookup failure call `reportError` and settle as not following / not favourited.
- [x] Both toggles catch failures, call `reportError`, leave the previous state in place, and expose an `error` string that clears on the next toggle and on id change.
- [x] `ProfilePage` shows the follow error inline under the Follow button and `SharedRecipePage` shows the favourite error inline near the favourite control, in existing secondary text styles. Copy: "Couldn't update that. Check your connection and try again."
- [x] `useFollowingList`, `useUserRecipes` and `useFollowingRecipes` use a `cancelled` flag and, where missing, a `.catch` that reports and settles `isLoading` to false.
- [x] `useFavoriteIds` memoises the `Set` on the `favorites` array.
- [x] No `setState` runs synchronously in an effect body (the lint rule `useFollowers` was written around).

## Out of scope

`useRecipeLibrary` (RL-027), the N+1 reads in the same hooks (RL-029), and the local
`useFavorite` hook, which already handles failures.

## Verification

Hook tests if RL-002 has landed (stale response ignored, failure settles loading).
Otherwise `npm run lint` and `npm run build` plus a browser check. Human QA entry in

## Notes

- Design trap confirmed on the Firestore emulator (demo-rl026, repo rules, unsigned token with `email_verified: true`, REST). A GET of a MISSING `follows/me_nobody` returned 403, and of a MISSING `favorites/me_r2` returned 403 (existing docs returned 200). The rules dereference `resource.data`, so the normal not-following and not-favourited case is a denial, not "not found". Reporting lookup failures from `getDoc` would have beaconed a false error on nearly every page view.
- Chose (b): `isFollowing` and `isCloudFavorite` in `src/services/firestore.ts` are now `getDocs` queries with two equality filters (`followerId`/`followingId`, `uid`/`recipeId`) and `limit(1)`. Emulator-verified: missing returns 200 with 0 docs, existing returns 200 with 1 doc. Real denials and network failures still reject, so the hook reports them (`follow-lookup`, `favorite-lookup`). Equality-only filters need no composite index. No rules or index change. Covered by `firestore.following.test.ts`.
- `TOGGLE_ERROR` lives in `useFollow.ts` and `useFavorites.ts` imports it.
- `useUserRecipes` stats are now derived from the recipes instead of held in state. `useFollowingList` and `useFollowingRecipes` derive `isLoading` from a key-stamped state, which also removes the one-frame "No recipes from followed users" flash.
- Not touched: `useRecipeLibrary` (RL-027), N+1 reads (RL-029), local `useFavorite`. `useOwnRecipes` still has pre-existing lint warnings (exhaustive-deps).
- `useCloudFavorite` previously had no `reportError` source labels; new labels: `follow-lookup`, `follow-toggle`, `favorite-lookup`, `load-following`, `load-user-recipes`, `load-following-recipes`; toggle failures reuse `favorite` and `unfavorite`.
