## Context

Written for RL-236's recommendations. RL-211's kitchen rule forbids changing `memberUids`; this
opens exactly three membership changes. List arithmetic in rules: `request.resource.data.memberUids
.toSet().difference(resource.data.memberUids.toSet())` and `.size()`.

## Acceptance criteria

- [ ] `match /kitchenInvites/{code}`: read by anyone verified (the joiner must see who invited them); create by the kitchen's `ownerUid` (checked with `get`), keys exactly `kitchenId, ownerUid, ownerName, expiresAt, createdAt`, `expiresAt <= request.time + duration.value(7, 'd')`, `code.size() >= 20`; delete by its owner; no update.
- [ ] Kitchen update, join: the only changed keys are `memberUids` and `joinCode`; the new set is the old plus `request.auth.uid` only; size at most 6; `joinCode` names an invite for this kitchen with `expiresAt > request.time`.
- [ ] Kitchen update, leave: a member removes only themselves, not the owner.
- [ ] Kitchen update, remove: the owner removes any non-owner member.
- [ ] Ordinary member edits (`shopping`, `pantry`, `updatedAt`) stay as in RL-211 for every member.
- [ ] Emulator probe codes in Notes for each allow and deny, including joining with an expired code, adding someone else, a seventh member, and a member removing another member.
- [ ] `docs/data-model.md` rows and rules paragraphs, "in the repo, deployed by RL-249".
- [ ] `npm test`, `npm run lint`, `npm run build` pass.
