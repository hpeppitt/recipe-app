## Context

Written for RL-236's recommendations. RL-211's kitchen rule forbids changing `memberUids`; this
opens exactly three membership changes. List arithmetic in rules: `request.resource.data.memberUids
.toSet().difference(resource.data.memberUids.toSet())` and `.size()`.

## Acceptance criteria

- [x] `match /kitchenInvites/{code}`: read by anyone verified (the joiner must see who invited them); create by the kitchen's `ownerUid` (checked with `get`), keys exactly `kitchenId, ownerUid, ownerName, expiresAt, createdAt`, `expiresAt <= request.time + duration.value(7, 'd')`, `code.size() >= 20`; delete by its owner; no update.
- [x] Kitchen update, join: the only changed keys are `memberUids` and `joinCode`; the new set is the old plus `request.auth.uid` only; size at most 6; `joinCode` names an invite for this kitchen with `expiresAt > request.time`.
- [x] Kitchen update, leave: a member removes only themselves, not the owner.
- [x] Kitchen update, remove: the owner removes any non-owner member.
- [x] Ordinary member edits (`shopping`, `pantry`, `updatedAt`) stay as in RL-211 for every member.
- [x] Emulator probe codes in Notes for each allow and deny, including joining with an expired code, adding someone else, a seventh member, and a member removing another member.
- [x] `docs/data-model.md` rows and rules paragraphs, "in the repo, deployed by RL-249".
- [x] `npm test`, `npm run lint`, `npm run build` pass.

## Notes

RL-211 review: the own-kitchen read branch (kitchenId == request.auth.uid) lets a user read kitchens/{uid} even if they are no longer in memberUids. If the owner can ever leave or be removed, tighten it to resource == null || uid in memberUids. Add the join as a separate allow update so the RL-211 update rule stays as is.

RL-237 (2026-10-21, reworked after review). Rules only; no client. Emulator only (`firebase emulators:exec --only firestore`, REST commits with unsigned test tokens; `Bearer owner` used only to seed an expired invite and 5- and 6-member kitchens, states the rules refuse). Nothing deployed.

Design:
- The RL-211 ordinary update rule is unchanged except through `isWellFormedKitchen`, which now accepts an optional `joinCode` key: absent, or present before and after with the same value (so it cannot be added, even as null); never on create. All 67 RL-211 probes give the same codes as before.
- Join, leave and remove are three further `allow update` branches (OR). Leave is `signedIn()` so a lapsed member can leave; remove stays verified.
- Join writes `joinCode = '<own uid>:<code>'`; the uid part must equal the writer and the code part (20 to 64, `^[A-Za-z0-9_-]{20,64}$`, also required of the invite id at create) must name a live invite for this kitchen (one `get`). The join must change `joinCode`. A lingering value is bound to its joiner, so a stranger cannot reuse it, a second joiner with the same link needs no clearing write, and nothing ever has to clear it.
- Own-kitchen read tightened per the RL-211 review: `(kitchenId == uid && resource == null) || uid in memberUids`.
- `kitchenInvites`: get by any verified user; list only by the owner (`where ownerUid == uid`); no update; delete by owner.
- Kitchen delete only when `memberUids.size() == 1` (matches the erase script, which already skips shared kitchens).
- Rejoin after leaving while one's own identical value lingers: 403 (the join must change `joinCode`). Client fix in RL-238 Notes: leave and remove send `joinCode: deleteField()`; probed leave-clearing then rejoin 200.
- Join twice: 403 (a member is not a non-member), not idempotent; RL-238 treats "already in memberUids" as joined.
- Access budget: join 1 `get` (the invite), invite create 1 `get` (the kitchen), nothing else. A join into a 300 + 300 item kitchen passes.

Mutation check (one clause removed at a time, the matching deny flips to 200): uid prefix check (someone else's prefix, stranger writing the lingering value), `joinCode` unchanged-or-absent in `isWellFormedKitchen` (edit changing or adding joinCode), invite expiry, invite kitchenId, member cap, owner not removed (owner leaves), delete sole-member check, owner-only list, `'joinCode' in resource.data` (adding joinCode null), the code charset at create (colon and dot codes). A code with a `/` is a nested path the REST API refuses (400). With the uid prefix in place, `changedKeys().hasAll([... 'joinCode'])` is belt and braces: removing it alone flips nothing. The removed member's `array-contains` query returns 200 with no document. Probe script: probe237.mjs in the session scratchpad; RL-211's probe211.mjs re-run unchanged.

Noticed, not touched: rules do not stop one user being in two kitchens (client's job per RL-236); expired invites are never deleted (they only stop working); `ownerName` is unverified (RL-238 shows the profile name).
