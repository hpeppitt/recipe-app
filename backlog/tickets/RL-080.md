## Context

RL-023 (`docs/decisions.md`, "Recipe delete waits for the cloud and reports what remains")
deletes the local subtree first, then waits up to 10 seconds for
`deletePublishedRecipeTree`, and on failure offers "Try again" or "Leave anyway". With the
cloud as the source of truth (decision 1b, RL-076) and the listener from RL-078, a recipe
left in the cloud is copied straight back into Dexie, so "Leave anyway" leaves a recipe the
user believes is gone. The order has to flip for a verified owner: cloud first, then the
device copy.

`handleDelete` and `runCloudDelete` are in `src/pages/RecipeDetailPage.tsx`;
`deleteRecipeTree` in `src/db/recipes.ts` deletes and returns the subtree ids in one step,
and its ids are passed as `extraIds` so variations the cloud tree query misses are still
attempted. The page now needs those ids before deleting, so add a read-only helper rather
than changing `deleteRecipeTree`. `deletePublishedRecipeTree` already skips other users'
descendants and ids with no cloud doc, so deleting a saved copy of someone else's recipe,
or a recipe already gone from the cloud, resolves with `failed: 0` and only the device copy
goes. Offline, Firestore's `deleteDoc` does not reject, it waits, so the 10 second
bound decides.

## Acceptance criteria

- [ ] `getSubtreeIds(id)` in `src/db/recipes.ts` returns the same ids `deleteRecipeTree(id)` would remove, without removing anything; a test covers a root with a grandchild.
- [ ] For a verified user with Firebase configured, `handleDelete` runs the cloud delete first (ids from `getSubtreeIds` as `extraIds`, same 10 second bound) and calls `deleteRecipeTree` only when it reports `failed === 0`, then leaves as today.
- [ ] When the cloud delete fails or times out, nothing is removed from Dexie and the failure dialog says: title "Couldn't delete this recipe", body "It's still saved in your account and on this device. Check your connection and try again." followed, when the count is known, by "{n} copies couldn't be removed." (using `pluralize`). Buttons are "Try again" (repeats the same delete) and "Cancel" (closes the dialog and stays on the recipe). "Leave anyway" is removed.
- [ ] Anonymous, signed-out and local-only deletes are unchanged: local only, then leave.
- [ ] A failure of the local delete after a successful cloud delete is logged and leaves the page as it is today for a local failure; the RL-078 sync removes the own rows the snapshot no longer has.
- [ ] `RecipeDetailPage.test.tsx` covers: verified success removes cloud then local in that order; verified failure removes nothing locally and shows the new copy; Try again succeeds; Cancel stays; anonymous delete never calls the cloud.
- [ ] `docs/capabilities.md` "Delete a recipe" row and the RL-023 entry in `docs/decisions.md` describe the new order and why (a recipe left in the cloud would sync back), keeping RL-023's reasoning on skipped descendants and missing docs.
- [ ] A `backlog/QA.md` entry: on the preview as a verified user, delete a recipe with a variation and confirm both leave My Recipes and Explore; then set DevTools offline, try to delete another, and confirm the dialog copy, that the recipe is still listed after Cancel, and that Try again works once back online. Check the dialog at 390 px in both themes.
- [ ] `npm run build`, `npm run lint` and `npm test` pass.

## Out of scope

Deleting other users' descendants (needs a Cloud Function, product decision 2). A
background retry queue. "Delete Recipes on This Device" (RL-081). Any rules change.
