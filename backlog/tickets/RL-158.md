## Context

Written for RL-157's recommended answers (2a, 4); regroom if the author chose otherwise. Today
`allow update` on recipes is `isViewIncrement() || isFavoriteCountBump() || isOwnerUpdate()`
(`firestore.rules` ~157-160), so nobody can re-point another cook's version. In a batched write,
`get()` sees the stored state and `existsAfter()` the state after the batch, which is what makes
"only while deleting the parent" provable without a server.

## Acceptance criteria

- [ ] A new `isReparentAfterParentDelete()` joins the update rule: `verified()`; `changedKeys().hasOnly(['parentId', 'depth'])`; the stored `parentId` (the old parent P) is a string; `get(P).data.createdBy.uid == request.auth.uid`; `!existsAfter(P)`; `get(P).data.parentId` is a string (P is not an original) and equals the new `parentId`; new `depth == resource.data.depth - 1`. Comment it like the neighbouring functions.
- [ ] Nothing else in the recipe rules changes; `hasBoundedContent` is not needed (content does not change).
- [ ] Emulator probe codes in Notes (batched REST commits): owner of P deletes P and re-points a child by another cook in one batch (200); the same update without deleting P (403); re-pointing to anything other than P's parent (403); changing `title` too (403); a third party doing it (403); P being an original (403).
- [ ] `docs/data-model.md` rules paragraph, marked "in the repo, deployed by RL-160".
- [ ] `npm test`, `npm run lint`, `npm run build` pass.
