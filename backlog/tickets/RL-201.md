## Context

RL-197's Grow navigates to `/recipe/<id>/vary` with `state: { suggestion, fromCookId }`. When
that variation is saved, `setCookBranch(fromCookId, branchId)` (RL-196) records it. This is the
save path (`useRecipeChat.ts` ~355-395, cloud first, RL-082), hence tier hard: the cook update
must run only after the recipe save succeeded and must never fail the save.

## Acceptance criteria

- [x] `RecipeChatPage` reads `fromCookId` from navigation state alongside `suggestion` and passes it to the hook.
- [x] After a successful variation save, the hook calls `setCookBranch` fire-and-forget; a failure is reported as `cook-branch` and the save still completes and navigates.
- [x] Only the first saved variation of that chat credits the cook (one `branchId` per cook, which the rules also enforce).
- [x] Tests: credited after save, not on failure, failure does not block, only once.
- [x] `docs/capabilities.md` Log a cook row mentions the credit.
- [x] A `backlog/QA.md` entry: Needs a tweak with a note, Grow, Save Variation; the cook log shows Branched linking to the new branch.
- [x] `npm test`, `npm run lint`, `npm run build` pass.

## Out of scope

Crediting branches grown later by hand.

## Verification

Hook tests, `data-integrity-reviewer`.

## Notes

`useRecipeChat(parentRecipe, fromCookId?)` calls `setCookBranch(fromCookId, recipe.id)` inside
`publishThenCache`'s `onPublished`, so it runs only after the cloud publish succeeded (never on a
local-only save), without awaiting; a rejection goes to `reportError(err, 'cook-branch')`. A
`cookCreditedRef` makes it once per chat; in practice the post-save lock already prevents a second
save. `RecipeChatPage` reads `fromCookId` from the same navigation state as `suggestion`. Six hook
tests: credited after publish, not on failed publish, rejected credit reported and save navigates,
hanging credit does not block, only the first successful save credits, no cook no call.
