## Context

Nobody is told when their recipe is branched (gap-C: no `branch` event; RL-092 left it out).
The notification create rule (`firestore.rules` ~296-320) allows a fixed key set and the types
`favorite`, `follow` (message null) and the suggestion types (message ≤ 500), through the
`notification` write window. RL-153 writes the new event; RL-155 stores the "Notify me when"
choices. The groomer's design: preferences live in a private document
`notificationPrefs/{uid}` `{ branch: bool, suggestion: bool, follow: bool, updatedAt }`, read only
by its owner, and are applied when the recipient reads Activity (writers never read someone
else's preferences, so no cross-user read is opened). Record that in data-model.md. If RL-146
merges first, rebase onto its type list; the two tickets touch the same rule.

## Acceptance criteria

- [x] Notification create accepts `type == 'branch'` with `message` null or a string ≤ 500, and only when `recipeId` is present and `get(/databases/$(database)/documents/recipes/$(request.resource.data.recipeId)).data.createdBy.uid == request.auth.uid` (the sender wrote the branch; one read). Other types unchanged.
- [x] `match /notificationPrefs/{uid}`: read, create, update, delete only when `verified()` and `request.auth.uid == uid`; writes require keys only `branch`, `suggestion`, `follow`, `updatedAt`, the three bools, and `updatedAt == request.time`. No list for anyone else.
- [x] The client-types test in `notifications.test.ts` (added by RL-146, or added here if this lands first) covers `branch`.
- [x] Emulator probe codes in Notes: branch notification by the branch author (200), by someone else (403), with a 501-char message (403); prefs write by owner (200), by another user (403), with an extra key (403), read by another user (403).
- [x] `docs/data-model.md`: a `notificationPrefs/{uid}` row and the rules paragraph, marked "in the repo, deployed by RL-156".
- [x] `npm test`, `npm run lint`, `npm run build` pass.

## Notes

Implemented 2026-10-21.

**Rules.** The notification create gets a third disjunct, `isBranchNotice()` (a function inside
`match /notifications`): `request.resource.data.type in ['branch']`, `message` null or a string
of at most 500 UTF-16 units, `'recipeId' in d`, and the recipe's `createdBy.uid` equal to the
sender (one `get`). Tightened after review, see below. The type list is written as `request.resource.data.type in [...]` so the
regex in `notifications.test.ts` finds it. Suggestion rules untouched, so the suggestion create
budget is unaffected. `match /notificationPrefs/{uid}`: read for the verified owner, delete for the signed-in owner (after review);
create and update for the verified owner with `keys().hasOnly(['branch', 'suggestion', 'follow',
'updatedAt'])`, three `is bool`, `updatedAt == request.time`. `allow read` covers list, and
another user is denied.

**Test.** `branch` is not in `AppNotification['type']` yet (RL-153 adds it), so it is not in the
`clientTypes` Record; a separate case asserts the rules allow `branch`. RL-153 should add it to
`clientTypes`.
