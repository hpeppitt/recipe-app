## Context

Sign-up is passwordless: the email step of `AuthModal` and `EmailLinkingForm` (the gates'
`tone="invite"` form and the profile banner) send a link, and the account becomes verified
when the link is opened (`completeEmailSignIn` in `services/firebase.ts`, then
`AuthContext`). So acceptance is given on the form but can only be recorded once the user is
verified, possibly after a page reload. Anonymous accounts only bookmark locally (RL-041) and
are not asked.

Design (groomer's, with the storage location set by the author on 2026-10-14; log any change
in `backlog/DECISIONS.md`):

- **Where.** An owner-only top-level document `termsAcceptance/{uid}` with `version`
  (string), `acceptedAt` (int, client ms when the box was ticked) and `recordedAt` (server
  timestamp). Not on the public profile: the author decided acceptance is private.
- **How it gets there.** The form stores `{ version, acceptedAt }` under a new
  `STORAGE_KEYS` entry when the link is sent. When a user becomes verified and has no
  `termsAcceptance` document with the current version, `AuthContext` writes it from that
  entry.
- **Enforcement.** Rules carry the current version as a literal. `termsAcceptance/{uid}`:
  read by the owner only; create and update by the owner with `verified()`,
  `keys().hasOnly(['version', 'acceptedAt', 'recordedAt'])`, `version` equal to the
  literal, `acceptedAt is int` and not more than a minute ahead of `request.time`, and
  `recordedAt == request.time`; delete by the owner (needed for account erasure, RL-057; a
  deleted acceptance simply blocks contributing again). A helper `acceptedTerms()`
  (`verified()` plus a `get()` of `termsAcceptance/$(request.auth.uid)` whose `version`
  equals the literal) guards the content-creating writes: recipe create, suggestion create,
  message create. One extra document read per such write.
- **When the version changes.** Bumping `TERMS_VERSION` and the rules literal together makes
  contributing writes fail for anyone on the old version, so a verified user whose
  acceptance is not current sees a minimal blocking dialog on app load: one sentence, links
  to the three pages, the checkbox and "Accept". Declining signs them out. (Author confirmed
  blocking, 2026-10-14.)

## Acceptance criteria

- [x] Every email form (the `AuthModal` email step, `EmailLinkingForm` in both tones, and the cross-device "needs email" prompt) has an unticked required checkbox: "I accept the Terms of Service and have read the Privacy Policy", both linked to RL-045's pages. The send button is disabled until it is ticked.
- [x] Sending stores `{ version: TERMS_VERSION, acceptedAt: Date.now() }` via `services/storage.ts`.
- [x] On becoming verified, `termsAcceptance/{uid}` is written with `version`, `acceptedAt` and `recordedAt: serverTimestamp()`, before the profile is created so the first contributing write already passes.
- [x] If no stored acceptance exists for a verified user whose `termsAcceptance` document is missing or out of date (for example the link opened on another device), `TermsUpdateDialog` is shown and its acceptance is recorded the same way.
- [x] `firestore.rules` has the `termsAcceptance/{uid}` block and `acceptedTerms()` as described above, with the version literal next to a comment pointing at `src/lib/legal.ts`. Profile rules are not changed by this ticket.
- [x] A test in `src/lib/legal.test.ts` reads `firestore.rules` and fails if its version literal differs from `TERMS_VERSION`.
- [x] `docs/data-model.md` documents the `termsAcceptance` collection and the rule. `docs/decisions.md` records the design and the version-change behaviour.
- [x] A `backlog/QA.md` entry: on the preview build, sign up with the box unticked (button disabled), ticked (works), then confirm `termsAcceptance/{uid}` in the console has the three fields and that another account cannot read it.

off.

## Notes

- Flow: `TermsCheckbox` (new, replaces `LegalLinks.tsx`) gates the AuthModal email step, `EmailLinkingForm` (both tones, so also `SignUpDialog` and the chat gate) and the `EmailLinkStatus` needs-email prompt, with a "Tick the box above to continue." hint tied to the box and the button by `aria-describedby`. Each stores `{ version, acceptedAt, email }` (email normalised) with `setTermsAcceptance` just before sending and clears it if the send fails. `AuthContext.checkTermsOnce` runs once per uid per session for verified users: after `completeEmailSignIn` returns and before `ensureProfile` and `pushFavoritesOnce` on the linked path, before the migration and push on the existing-account path, and before `ensureProfile` in `onAuthStateChanged`. Missing or old record plus a current stored entry for the same address: write, then clear. Otherwise the dialog, through `TermsContext` and `TermsGate` (inside `BrowserRouter` in `App.tsx`), which stays off `/terms`, `/privacy` and `/cookies`.
- Deploy-order trap: a failed or slow (5 s) read is unknown, reported at most once per session as `terms-check`, never shows the dialog, and is not cached: `online` and the tab becoming visible recheck, at most 3 times per session. A failed Accept shows an inline error and Retry; Decline is guarded against double taps, shows an error if sign-out fails, and is never blocked by Accept. The combined deploy order is in docs/operations.md.
