## Context

`RecipeEditForm.handleSave` in `src/pages/RecipeEditPage.tsx` writes Dexie first with
`updateRecipe`, then re-publishes only if `getPublishedRecipe` finds a cloud copy, and on a
cloud failure navigates with `saved: 'local'`. Under the sync (RL-078) the next snapshot
overwrites that local edit with the cloud version, so the edit would vanish after the user
was told it was saved. Author answers of 2026-10-18 (decision 1b, RL-076): cloud first, last
write wins between devices.

`publishRecipe`'s re-publish branch is a `setDoc` merge, so the last write to land wins,
which is the agreed rule. It writes `updatedAt` from the record it is given, so set it on the
published record. "Editing is not a decision to publish" (`docs/decisions.md`, "Edits apply
in place") still holds: an edit never creates a cloud copy. If none exists, the recipe was
deleted on another device. If `RecipeEditPage.test.tsx` does not exist, create it.

## Acceptance criteria

- [x] For a verified user with Firebase configured, `handleSave` checks for the cloud copy and publishes `{ ...recipe, ...patch, updatedAt: now }` within a 5 second bound (`withTimeout`), and only on success writes the same record to Dexie with `updatedAt` equal to `now` and navigates with `saved: 'cloud'`.
- [x] When the cloud copy is missing, nothing is written and the form shows "This recipe is no longer in your account." with no retry.
- [x] When the check or the publish fails or times out, nothing is written to Dexie, the form stays open with the draft intact, and `saveError` reads "Couldn't save your changes. Check your connection and try again."; Save works again.
- [x] Anonymous, signed-out and local-only edits keep today's Dexie-only behaviour.
- [x] Tests cover: success order (cloud then Dexie), failure leaves Dexie unchanged with the draft kept, missing cloud copy, and the local-only path.
- [x] `docs/capabilities.md` "Manual recipe editing" row describes cloud-first edits and last write wins.
- [x] A `backlog/QA.md` entry: on the preview as a verified user, edit a recipe and see it on its `/shared/<id>` link; then set DevTools offline, edit, tap Save, confirm the error and that the draft is kept, go online, Save again, and confirm the edit. Check the error at 390 px in both themes.
- [x] `npm run build`, `npm run lint` and `npm test` pass.

## Out of scope

Conflict merging beyond last write wins. Edit history (rejected, `docs/decisions.md`). The
sync (RL-078).

## Verification

`npm test`. Human: the offline edit in the QA entry.

## Notes

Cloud check and publish share one 5 s `withTimeout` (`CLOUD_SAVE_TIMEOUT_MS`), so a hang in
either reports the connection error. The missing-copy message disables Save until the user
leaves, which is how "no retry" is met. A Dexie write failure after a successful publish is
logged and reported (`edit-recipe-cache`) and the save still completes, as in RL-082, since the
sync fills the row. The error element was already `role="alert"` and sits directly above Save,
so no scroll or focus change was needed; a retry clears it at the start (existing
`setSaveError(null)`).

Noticed, not touched: the Dexie-only path still navigates with `saved: 'cloud'` (today's
behaviour, kept per the criterion), so an anonymous or local-only edit may show the cloud
variant of the toast.
