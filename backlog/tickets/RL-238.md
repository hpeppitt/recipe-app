## Context

RL-213 assumed kitchen id = uid. Now the id comes from `kitchens where memberUids
array-contains uid limit 1` (first one wins; with none, the user's own id). Member names and
avatars come from `profiles` (public).

## Acceptance criteria

## Notes
The erase script only reads kitchens/{uid}; query memberUids array-contains uid, arrayRemove the uid and anonymise pantry addedBy for kitchens the user only belongs to.

From RL-237: on remove and before deleting a kitchen, delete the owner's live invites (owner can list them). Generate invite codes with crypto.getRandomValues (at least 20 URL-safe characters). Show the inviter's name from profiles/{ownerUid}.displayName, not the invite's ownerName. Treat 'already in memberUids' as joined. One kitchen per person is the client's job. The join writes joinCode = '<own uid>:<code>' with arrayUnion on memberUids and nothing else; the rules delete a kitchen only when the owner is its sole member.

From RL-237 round 2: Leave and remove send arrayRemove plus updatedAt serverTimestamp and joinCode deleteField(), so the same person can rejoin with a live link. The join is updateDoc with arrayUnion(uid) and joinCode only (no updatedAt), since a non-member cannot read the kitchen.

Implementation (2026-10-21): `useKitchen` resolves the id with `memberUids array-contains uid limit 2` (a kitchen other than the own one wins; limit 2 because a joined user keeps their unused own document), once per session, shared by the listener and `addRecipeToKitchen`/`addLeftoversToPantry`; re-resolved after the last unmount and on a listener failure (a removed member falls back to their own kitchen). `updateKitchen` writes any resolved id and creates only `kitchens/{uid}`; it still updates only shopping, pantry and updatedAt, so joinCode is untouched. Joining while in another shared kitchen, or owning one with members, is refused with copy (not an automatic leave). A denied join with a live invite reads as "This kitchen is full." after a re-resolve rules out "already a member". Erase passes an owned shared kitchen to the first other member in memberUids (decision pending in backlog/DECISIONS.md). Export: `cloud.kitchenMemberships` (client) and `kitchenMemberships` (script). Review round (same day): ShopFamilySheet reads the resolved kitchen's pantry; a denied or vanished-kitchen write clears the resolved id; a good snapshot resets the listener retry; the lookup failing is a plain failure, never "may have saved"; one membership action at a time; createInvite never sets the hook error; joining deletes the joiner's own invites first; a denied join re-reads the invite (gone: expired copy; user already a member: joined; else full); the export drops `joinCode`; the erase deletes a `joinCode` the uid left.
