## Context

`publishRecipe` (`services/firestore.ts` lines 43-57) builds `content` with
`collaborators: data.collaborators ?? []` and on re-publish writes it with
`setDoc(..., { merge: true })`. A merge replaces arrays wholesale, so the local copy's
collaborators overwrite the cloud's. Approval adds the collaborator in the cloud with
`arrayUnion` and mirrors it to Dexie only on the approving device (FUN-7 in `AUDIT.md`), so
editing the recipe on another device, or after a failed mirror, silently deletes collaborator
credit. Edits re-publish (see "Edits apply in place" in `docs/decisions.md`), so this is
reachable through normal use.

## Acceptance criteria

- [x] On the re-publish path, the payload does not contain `collaborators`; the cloud array is only ever changed by the approval `arrayUnion`.
- [x] The create path still writes `collaborators` (local value or `[]`).
- [x] `src/services/firestore.publish.test.ts` adds: re-publish payload has no `collaborators` key; first publish payload has it.
- [x] The `publishRecipe` doc comment says why.

## Out of scope

Syncing cloud collaborators back into Dexie, and repairing collaborators already lost in
production.

## Verification

`npm test`. Human QA in `backlog/QA.md`: approve a suggestion on one browser profile, edit the
recipe from a second profile signed into the same account, and confirm the collaborator is
still shown on `/shared/:id`.

## Notes

- Path choice: option A, which was already in place. Since FUN-10, `publishRecipe` reads the doc with `getDoc` and branches on `exists()`, so the fix only drops `collaborators` from the merge payload on the exists branch and adds it (local value or `[]`) to the create payload. No new round trip. Option B (`updateDoc` then fall back to create) adds a not-found failure as a control-flow branch and a second write on every first publish, for no gain since the read already exists. Option C (`arrayUnion` on create) is wrong: a create is not a merge, and `arrayUnion` on a missing doc just writes the array, so it adds nothing over a plain value.
- Rules: the re-publish is a merge `setDoc` on an existing doc, so an owner update evaluated on the merged document. `hasBoundedContent` and the `createdBy`/`createdAt` checks see the stored values plus the payload; omitting `collaborators` changes nothing there. The create path is unchanged.
- Race (two devices publishing for the first time at once): unchanged from before. Both can see a missing doc and both send a plain `setDoc`; the second lands as a full overwrite (an owner update) with counters 0 and its own `collaborators`. In that window there are no approvals or favourites yet, so nothing is lost in practice. Not fixed here.
- Errors: unchanged. A `getDoc` rejection still rejects `publishRecipe` with nothing written (no fallback), and a `setDoc` rejection still rejects. Return value (`void`), `chatHistory` exclusion, `createdAt` handling and the first-publish-only `recipeCount` bump are untouched.
- Callers: `useRecipeChat` (save after generation, usually first publish), `RecipeDetailPage` share (retry, either path), `RecipeEditPage` (re-publish only, guarded by `getPublishedRecipe`). None reads `collaborators` from the result, so no caller changes.
- Tests in `src/services/firestore.publish.test.ts`: re-publish has no `collaborators` key (local copy with and without collaborators); create writes the local value and the `[]` default; a `getDoc` failure rejects and writes nothing; a re-publish `setDoc` failure rejects. Existing assertions untouched. The `getDoc` mock gained a `getDocError` switch (null by default, reset in `beforeEach`), so existing tests see the same mock. The two re-publish tests fail against the old code (checked with the old `firestore.ts` stashed: 2 failed, 12 passed).
- Emulator probe, 2026-10-15: `firebase emulators:exec --only firestore --project demo-rl037` with the repo's rules and a REST `:commit` script in the scratchpad (unsigned emulator tokens with `email_verified: true`, owner uid `owner`). Results:
  - create of `recipes/r1` with `collaborators [c1]`, counters 0, `exists: false`: 200; collaborators after: `["c1"]`.
  - re-publish as the fixed SDK sends it, `updateMask` of the payload fields (`title`, `ingredients`, `instructions`, `createdBy.uid`, `createdBy.displayName`, `createdAt`, `rootId`, `depth`) without `collaborators`: 200; collaborators after: `["c1"]`.
  - the old payload, same mask plus `collaborators` set to `[]`: 200; collaborators after: `[]` (the bug, so the probe discriminates).
  - control, the fixed re-publish from another verified uid: 403 (rules are enforced).
- Out of scope, noted: Dexie copies on other devices still lack collaborators added by approval (no pull-down).
