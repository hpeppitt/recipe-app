## Context

Written for RL-161's recommended answers 1 and 2; regroom otherwise. `SimilarRecipe`
(`useRecipeChat.ts` ~41) has no `rootId`; `dismissSimilar` (~302) generates past the matches;
`saveRecipe` (~317) builds the record with `buildRecipe(...)` and publishes it cloud first.
Cloud documents are mapped back into `Recipe` in several places that list fields explicitly
(`recipeSync.ts` ~25, `useRecipe.ts` ~87, `useRecipeTree.ts` ~16, `library.ts` ~76); a new
field must be carried in each or it is lost on sync. The field is not indexed in Dexie, so no
schema version bump (which would need a human).

## Acceptance criteria

- [x] `Recipe` gains optional `relatedFamilyId?: string | null`, and every cloud-to-local mapping above carries it (tests for `recipeSync` mapping).
- [x] `SimilarRecipe` carries `rootId`; when the user taps "Create New Recipe Anyway", the first match's `rootId` is held for this chat; the next saved original (no parent) gets `relatedFamilyId` set to it, published and cached with the recipe. Refining keeps it; starting a new chat or saving a variation clears it.
- [x] On the recipe page, an original with `relatedFamilyId` shows a "New original" tag (accent tag: accent-100 fill, accent-800 text, semibold 13px pill) above the metadata pills.
- [x] Tests: the id is set only after Create anyway, only on originals; the tag renders.
- [x] `docs/data-model.md` lists the field.
- [x] A `backlog/QA.md` entry. `npm test`, `npm run lint`, `npm run build` pass.

## Out of scope

The Related family card (RL-163), moving (RL-164), changing the dedup panel.

## Verification

Gates: tests, `data-integrity-reviewer`, `ui-reviewer`. Human on the emulator: ask for a recipe
that matches an existing one, tap Create New Recipe Anyway, save, see New original; check the
document has `relatedFamilyId` and that it survives a reload on a second device.

## Notes
- `Recipe.relatedFamilyId?: string | null` (types/recipe.ts) and `PublishedRecipe.relatedFamilyId`. `toLocalRecipe` carries it (and drops it when absent, so sync sees no diff); `useRecipe` and `useRecipeTree` spread the whole published doc, so they already carry it. `library.ts` `feedMapper` builds a `FeedRecipe` card, not a `Recipe`, and nothing on a card reads the field, so it is not added there.
- `SimilarRecipe.rootId` (cloud matches fall back to `id`). `dismissSimilar` holds `similarRecipes[0].rootId` in a ref only when there is no parent; `saveRecipe` adds it to an original only, and a variation save clears it. A new chat is a new hook instance, so it starts empty.
- "New original" pill sits under the description in the original's header (above the metadata pills), styled like the kcal pill.
- Rules (review round 1): `hasBoundedContent` now requires `relatedFamilyId` absent, null, or a string of at most 128 characters. Repo only; RL-160 deploys it (noted there). No Dexie version change (field not indexed).
- Emulator probe 2026-10-21 (`firebase emulators:exec --only firestore`, REST commits with the recipe window): normal publish 200; null 200; UUID 200; 128 chars 200; 129 chars 403; number 403; map 403; owner update to 129 chars 403; owner update to 128 chars 200; title merge on a recipe with the field 200; view increment 200.
- Review round 1 also: the held id is cleared whenever a fresh dedup runs (a Create anyway whose generation failed no longer tags a later unmatched original; test added and checked to fail without the fix); a cloud match that is a branch with no rootId records nothing; `ImportedRecipeSchema` keeps the field on restore; the pill has an sr-only ", similar to an existing recipe family".
- Tests: recipeSync mapping (2), useRecipeChat (4: set after Create anyway and kept through a refine, published and cached; not set without a match; new chat; never on a variation), RecipeHeader (3).
