## Context

The author decided that production deploys start from a release tag and wait for their
approval in the GitHub Environment `production` (RL-293: required reviewer `hpeppitt`, tag
rule `v*`, no admin bypass). Approving the run replaces running `firebase deploy` by hand, so
the "deploy rules to production" tickets become "approve the production run".

The order is the risky part (`docs/operations.md`, "The pending release order", "A later Terms
bump is the reverse"). RL-295's `resolveOrder` decides it: an explicit dispatch input, else a
`deploy-order:` line in the annotated tag message (which `/release` writes, RL-300), else
rules first, with the reason "Terms version changed" when the live and tagged Terms versions
differ and "default" otherwise. Client first needs an explicit tag line or dispatch input.

The reviewer must see the plan before approving, but a job that reads production needs the
production secret, which is only released after approval. So the workflow has two jobs: a
**plan** job with no Environment and no credentials, which works from git alone (the
`firestore.rules` and `firestore.indexes.json` diff since the previous `v*` tag, the Terms
version at each, the tag message, and the resulting order), and a **deploy** job in the
`production` Environment. After approval the runner resolves the order again from the live
ruleset (RL-296); if that differs from the plan the reviewer approved, the run stops before
any deploy step. Git is not a reliable record of what is live (operations.md, 2026-08-14), so
the live check is the one that counts, and a disagreement means a human looks.

## Acceptance criteria

- [ ] `.github/workflows/deploy-prod.yml` runs on `push` of tags matching `v*.*.*` and on
  `workflow_dispatch` with one input `order` (`auto`, `rules-first`, `client-first`; default
  `auto`). It has `permissions: contents: read` and concurrency group `deploy-prod` with
  `cancel-in-progress: false`.
- [ ] The **plan** job: fails unless the ref is a tag matching `v*.*.*` (a dispatch must be
  run "from" a tag) and the tagged commit is an ancestor of `origin/main`; runs `npm ci`,
  `npm run build`, `npm run lint`, `npm test`; then writes to the job summary the tag, the
  previous `v*` tag, the rules and indexes diff between them, both Terms versions, the tag
  message's `deploy-order` line if any, the planned order with its reason, and the planned
  steps. It exposes the planned order as a job output.
- [ ] The **deploy** job `needs: plan`, names `environment: production` with URL
  `https://recipe-lab-3832b.web.app`, has a 45 minute timeout, sets
  `DEPLOY_ENVIRONMENT: production`, builds with the production Environment's `vars` (same
  list as RL-297), authenticates as RL-297 does, writes the tag message to a file, and runs
  `node scripts/deploy.mjs prod --order <dispatch input or auto> --tag-message <file>
  --expect-order <plan output>`.
- [ ] A run on a branch ref never reaches the deploy job's secret: the plan job fails first,
  and the Environment's tag rule refuses it anyway.
- [ ] `docs/operations.md` describes the production pipeline: tag, plan summary, approve in
  the run page (Review deployments, production, Approve and deploy), the order rules, what a
  mismatch stop means, and that a rejected or failed run deploys nothing after the failed
  step.
- [ ] `backlog/QA.md` gets a line: the first production run (RL-303) shows the plan before
  the approval prompt and an empty ruleset diff after.
- [ ] `npm run build`, `npm run lint`, `npm test`, `npm run backlog -- validate` pass.
