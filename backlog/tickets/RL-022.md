## Context

RL-040 (every client cloud write needs a verified email) and RL-015 to RL-021 (the audit
rules) change `firestore.rules` and `firestore.indexes.json` in the repo and are verified
against the emulator. RL-041 is the matching client. Rules deploy as one unit and the deploy
is outward-facing and on the "What needs a human" list in `backlog/README.md`, so it is its
own ticket. The procedure for diffing the live ruleset is in `docs/operations.md`.

Order matters:

1. RL-042 wipes production data first (its own ticket, a dependency here).
2. Indexes, because the new client queries (RL-018 suggestions, RL-021 following feed) fail
   without them.
3. The client release, because the new client works under the old rules but the old client
   does not work under the new ones (its unfiltered suggestions query is denied, and it
   writes cloud favourites, follows and profiles for anonymous users).
4. The rules.

Do not use the live app between the wipe and the rules deploy.

## Acceptance criteria

- [ ] RL-042 is done: production Firestore is empty.
- [ ] The live ruleset is fetched and diffed against `firestore.rules` at HEAD, and the current ruleset id is written down as the rollback target.
- [ ] `firebase deploy --only firestore:indexes` is run and every new index shows as built in the console.
- [ ] The client containing RL-040, RL-041 and RL-015 to RL-021 is released via `/release`.
- [ ] `firebase deploy --only firestore:rules` is run, and the post-deploy diff of the live ruleset against HEAD is empty.
- [ ] The deploy date, previous ruleset id and new ruleset id are recorded in `docs/operations.md`.
- [ ] The QA.md checks from RL-040, RL-041 and RL-015 to RL-021 are done on live: as anonymous, bookmarking works locally and every other action asks for sign-up with a clean console; as a verified user, publish, edit, favourite, follow, suggest and approve work and notify; a third account sees no one else's suggestions; avatar upload works.
