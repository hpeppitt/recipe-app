## Context

`fetchCloudDataForExport` (`services/firestore.ts` ~1206, RL-056) reads one section per
collection with `exportSection` and a 10000-row cap; `scripts/data-request.mjs` (RL-055, Admin
SDK, dry run first) exports and erases one uid. New user-owned collections must join both.

## Acceptance criteria

- [x] Download my data gains `cooks` (`where uid == uid`) and `cookPhotos` (`where uid == uid`), with other people's uids anonymised as today (`recipeOwnerId` becomes `other-user-N`).
- [x] `data-request.mjs export` includes both; `erase` deletes both in its dry-run-first flow and lists counts.
- [x] Tests for both paths (mocked SDK, as the existing tests do).
- [x] `docs/operations.md` Data requests section and `docs/data-model.md` list the collections.
- [x] `npm test`, `npm run lint`, `npm run build` pass.

## Out of scope

## Notes

- Download my data: `fetchCloudDataForExport` reads `cooks` and `cookPhotos` where `uid == uid` with `exportSection`/`readMerged`, plus `writeWindows/{uid}_cook`. `assembleDataExport` (lib) adds `cloud.cooks` (key-picked, `recipeOwnerId` aliased) and `cloud.cookPhotos` (key-picked, URL kept). `DATA_EXPORT_VERSION` stays 1 (additive). `SettingsPage.test.tsx` fixtures gained the two sections.
- Script: `collect` reads own cooks, own cook photos and other people's cooks of own recipes (`recipeOwnerId == uid`). Erase plans photos first, then cooks, then anonymises others' cooks' `recipeOwnerId` to `deleted-user`; one or two ops per group, within `BATCH_LIMIT`. Export and counts include both; `redactExport` aliases `recipeOwnerId`.
- Size: one maximum photo makes a 201.5 KB export row; documented as about 200 KB per photo. No path logs a URL (tests assert it for the service and the dry-run lines; the emulator erase log had 0 `base64` hits).
- Emulator run (2026-10-21), never the live project: `firebase emulators:exec --only auth,firestore --project demo-rl207` with a seed of recipes r1 (userA1) and r2 (userB2), cook k1 by userA1 on r2 with a 199999-character photo, cook k2 by userB2 on r1, and `writeWindows/userA1_cook`; then `node scripts/data-request.mjs export userA1 --emulator --project demo-rl207 --out <scratch>` (cooks 1, cookPhotos 1, writeWindows 1, `recipeOwnerId` other-user-1) and `erase userA1 --emulator --project demo-rl207` dry run: DELETE recipes/r1, DELETE cookPhotos/k1, DELETE cooks/k1, UPDATE cooks/k2 set recipeOwnerId deleted-user, DELETE writeWindows/userA1_cook; 5 writes in 1 batch; DRY RUN. The export file was deleted.
- Decision logged in backlog/DECISIONS.md (others' cooks anonymised; cook window included; others' photos on erased recipes kept).
- Review follow-up: `readAllDocs` takes its constraints as an array and an optional accumulator; the cookPhotos section's `onTimeout` returns the pages read so far with a warning (tested). `docs/capabilities.md` lists cooks and cook photos.
