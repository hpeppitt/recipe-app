## Context

The magic link returns to the app origin (`sendEmailSignInLink` and `sendEmailLinkForLinking`
in `src/services/firebase.ts` ~95-112 use `url: window.location.origin`), so the page and the
interrupted action are lost; capabilities.md says so ("the interrupted action does not run on
its own"). This ticket is the first seam: record the intent and return to the page. RL-136
consumes the intent. Read decisions.md "Email-link completion has a required order of
operations" first: completion runs in `AuthContext` on mount, and its ordering must not change.
`completeEmailSignIn` already clears the link with `history.replaceState({}, '', pathname)`
(~175), which keeps a path, so returning to `/recipe/<id>` is safe.

`EmailLinkStatus` (the 15b outcome sheet) is rendered only inside `AppShell` (~90) and hidden
when a recipe is shown alone, so a link that lands on `/recipe/<id>`, a route outside the
shell, would complete silently with no sheet for "needs email", "expired" or "linked".

## Acceptance criteria

- [x] Pure `src/lib/pendingAction.ts`: type `PendingAction = { kind: 'save' | 'branch' | 'suggest'; recipeId: string; at: number } | { kind: 'follow'; uid: string; at: number }`; `parsePendingAction(raw: unknown, now: number): PendingAction | null` rejects wrong shapes, non-string ids, and anything older than 1 hour (`PENDING_ACTION_TTL_MS`). Tests cover each kind, bad shapes and expiry.
- [x] `src/services/storage.ts` gains `getPendingAction`, `setPendingAction`, `clearPendingAction` on one localStorage key, using the module's existing safe wrappers.
- [x] `AuthModal` and `SignUpDialog` take an optional `pending?: PendingAction` prop. When the email form sends a link, the pending action is stored first (before the send, like the email itself, because the link can be opened before the promise settles). Callers pass it: recipe page Save, Suggest and Branch (RL-134); shared page Save, Suggest and Make it yours; profile Follow. Plain "Sign in" buttons pass nothing.
- [x] Both send functions in `firebase.ts` use `url: window.location.origin + window.location.pathname` (no query or hash), so the link returns to the same page.
- [x] The sent step (`SentStep`) says "The link brings you back to this page." instead of Recipe Lab home.
- [x] `EmailLinkStatus` is rendered once at the app root (beside `TermsGate` in `App.tsx`, inside the router) instead of in `AppShell`, so its sheet shows on every route; it never renders twice. Its existing tests still pass.
- [x] Choosing the guest option in `AuthModal` clears any stored pending action: a guest cannot contribute (decision 1a); a guest saves by tapping Save again, as today.
- [x] `docs/capabilities.md` (Passwordless email sign-in row) and `docs/architecture.md` (auth section) describe the return-to-page link and the stored intent; capabilities still says the action does not run until RL-136.
- [x] A `backlog/QA.md` entry. `npm test`, `npm run lint`, `npm run build` pass.

## Out of scope

Running the action (RL-136). Cross-device completion: an intent lives on the device that
asked, so a link opened elsewhere returns to the page but runs nothing (state it in the docs).
Firebase console changes: the authorized domain is unchanged, only the path differs.

## Verification

Gates: tests, `ui-reviewer`. Emulator walk (`npm run emulators`, `npm run dev:emulated`;
`docs/operations.md` shows how to read the oobCode link): signed out on `/recipe/<id>`, Save,
send a link, open it in the same browser: you land on `/recipe/<id>` signed in and the link
sheet behaves as before. Open a link on `/profile/<uid>` that needs an email (other browser):
the 15b sheet shows over the profile.

## Notes

- `lib/pendingAction.ts` also exports `PendingIntent` (a `PendingAction` without `at`), which is the type of the `pending` prop: the time is stamped at send, so the hour runs from the send. Logged in `backlog/DECISIONS.md`.
- A send with no `pending` (plain Sign in) clears any stored intent; a failed send clears it too, mirroring the Terms tick.
- `useBranchEntry`'s `branch` now takes a recipe id, so the tree and Timeline Branch entries also store a branch intent.
- `EmailLinkStatus` now also shows below lg over a recipe opened from a list (it was hidden there).
- `docs/legal/data-inventory.md` gains a row for the new `recipe-app-pending-action` key.
- Review fixes: the link keeps the hash on `/shared` only (`linkReturnPath` in `lib/pendingAction.ts`, used by both send functions and `clearLinkFromUrl`), because a self-contained shared recipe lives in the hash; this is the one exception to "no query or hash". A failed link (expired, email-taken, failed) clears the intent in `AuthContext`'s completion catch, with the completion order unchanged; needs-email keeps it. The guest option clears it only after the anonymous sign-in succeeds, and a failed send clears it only if that send wrote it.
