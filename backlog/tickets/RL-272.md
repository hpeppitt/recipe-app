## Context

RL-271 stops new multi-emoji recipes. Existing ones are in Firestore and in Dexie. Rewriting
production documents needs a human (`backlog/README.md`), and a Dexie version bump does too, so
this ticket normalises on read at the three seams every stored recipe passes through:

- Dexie: a `this.recipes.hook('reading', ...)` in `db/database.ts` (no `version()` change).
- The own-recipe sync: `toLocalRecipe` in `lib/recipeSync.ts` (decision 1b; this is the
  dual-store path, hence `hard`).
- Published reads: `withBoundedImportedFrom` in `lib/linkImport.ts` already wraps every
  `getDocs`/`getDoc` of `recipes` in `services/firestore.ts` (nine call sites); add the emoji
  step there and update its doc comment.

The fallback for a stored value with no emoji at all is `RECIPE_EMOJI_FALLBACK`.

## Acceptance criteria

- [x] A Dexie recipe row stored with "🍞🧈" reads back as "🍞" from every `db/recipes.ts` reader; the row on disk is unchanged until it is next written.
- [x] `toLocalRecipe` returns one emoji, so an owner's re-publish of an old recipe sends one.
- [x] Every published read returns one emoji; `importedFrom` handling is unchanged.
- [x] No Dexie `version()` call is added and no Firestore document is rewritten by code.
- [x] Tests for each seam with a two-emoji fixture (`src/test/factories.ts`).
- [x] `docs/data-model.md` notes that older documents may hold several emoji and are normalised on read.
- [x] `npm test`, `npm run lint`, `npm run build` pass.

## Out of scope

Denormalised copies (`recipeEmoji` on notifications and suggestions, shopping list sources,
collection tiles): they were copied from the recipe and are short-lived or few; new copies
are one emoji after RL-271. A one-off production cleanup script.

## Verification

Unit tests. Human: open a recipe on live that was saved with several emoji (if any exist) and
see one.

## Notes

- Dexie: `this.recipes.hook('reading', ...)` in `src/db/database.ts`, outside every `version()` block. It returns a copy with `emoji: oneEmoji(emoji, RECIPE_EMOJI_FALLBACK)` and passes `undefined` through, because Dexie calls it for missing keys on `get`/`bulkGet`. `Collection.raw()` skips it, which the test uses to prove the row on disk is unchanged.
- Sync: `toLocalRecipe` normalises the emoji. Because Dexie rows also read normalised, `same(next, row)` stays true for an unchanged legacy row, so no extra puts.
- Published reads: `withBoundedImportedFrom` normalises `emoji` when the key is present and returns the same object when nothing changes, so the existing identity test still holds.
- Tests: `src/db/recipes.test.ts` (all six readers plus raw row), `src/lib/recipeSync.test.ts`, `src/lib/linkImport.test.ts`.
