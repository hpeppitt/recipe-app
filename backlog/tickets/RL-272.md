## Context

RL-271 stops new multi-emoji recipes. Existing ones are in Firestore and in Dexie. Rewriting
production documents needs a human (`backlog/README.md`), and a Dexie version bump does too, so
this ticket normalises on read at the three seams every stored recipe passes through:

- Dexie: a `this.recipes.hook('reading', ...)` in `db/database.ts` (no `version()` change).
- The own-recipe sync: `toLocalRecipe` in `lib/recipeSync.ts` (decision 1b; this is the
  dual-store path, hence `hard`).
- Published reads: `withBoundedImportedFrom` in `lib/linkImport.ts` already wraps every
  `getDocs`/`getDoc` of `recipes` in `services/firestore.ts` (nine call sites); add the emoji
  step there and update its doc comment.

The fallback for a stored value with no emoji at all is `RECIPE_EMOJI_FALLBACK`.

## Acceptance criteria

- [ ] A Dexie recipe row stored with "🍞🧈" reads back as "🍞" from every `db/recipes.ts` reader; the row on disk is unchanged until it is next written.
- [ ] `toLocalRecipe` returns one emoji, so an owner's re-publish of an old recipe sends one.
- [ ] Every published read returns one emoji; `importedFrom` handling is unchanged.
- [ ] No Dexie `version()` call is added and no Firestore document is rewritten by code.
- [ ] Tests for each seam with a two-emoji fixture (`src/test/factories.ts`).
- [ ] `docs/data-model.md` notes that older documents may hold several emoji and are normalised on read.
- [ ] `npm test`, `npm run lint`, `npm run build` pass.

## Out of scope

Denormalised copies (`recipeEmoji` on notifications and suggestions, shopping list sources,
collection tiles): they were copied from the recipe and are short-lived or few; new copies
are one emoji after RL-271. A one-off production cleanup script.

## Verification

Unit tests. Human: open a recipe on live that was saved with several emoji (if any exist) and
see one.
