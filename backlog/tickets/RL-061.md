## Context

Since RL-041, `handleShare` in `src/pages/RecipeDetailPage.tsx` skips the publish retry for a
user without `emailVerified` and falls through to `pickShareUrl` (`src/lib/share.ts`), which
returns a self-contained `/shared#r=...` link. The author overruled that at the 2026-10-17 QA
pass (`backlog/QA-CHECKLIST.md` section 4; `backlog/DECISIONS.md`, the first RL-041 row):
an anonymous user who taps Share gets the sign-up dialog, and sharing waits until they add an
email. This follows decision 1a in `docs/decisions.md` (anonymous accounts are local-bookmark
only).

The dialog already exists: `src/components/auth/SignUpDialog.tsx` (title, body, `onClose`),
used by `ProfilePage.tsx` for Follow and own-profile editing with `needsSignUp =
!user?.emailVerified`. It wraps `EmailLinkingForm tone="invite"`, which links the email to an
anonymous account (same uid, recipes keep their `createdBy`) or sends a sign-in link to a
signed-out visitor.

Decisions taken at grooming:

- **Who is gated:** with Firebase configured, anyone without `emailVerified`: anonymous,
  signed out, and email-unverified, **but only when the recipe has no published copy**.
  Author's answer at approval (2026-10-17): an already-public recipe can still be shared.
  So for an unverified user, Share first runs the existing `getPublishedRecipe` check. If it
  resolves a document, copy the `/shared/<id>` link as a verified user would. If it
  resolves nothing, or fails or times out, open the dialog: never publish, and never hand
  out a self-contained link. Local-only mode (Firebase not configured) has no accounts and
  keeps sharing the self-contained link.
- **Signed out:** same dialog as anonymous, matching Follow. `EmailLinkingForm` already picks
  `sendEmailLink` for them. If they then sign in to an account that did not create the recipe,
  Share behaves as it does today for any verified non-creator (publish is refused, a
  self-contained link is handed out); that is not changed here.
- **After verifying, Share does not resume automatically.** The email link completes in a
  new page load, often in another tab or app, so the intent would need persisting; and
  `navigator.clipboard.writeText` needs a user gesture in Safari, so an automatic copy after
  the redirect would fail anyway. The dialog body says to tap Share again.
- **Self-contained links keep producers**, so `hashShareUrl`, `pickShareUrl` and the
  self-contained toast copy stay: local-only mode; the publish timing out
  (`SHARE_PUBLISH_TIMEOUT_MS`) or failing; the daily publish limit (RL-049); and a verified
  user sharing a copy saved from someone else's link (`publishRecipe` refuses a non-creator).
  The `/shared` reader (`SharedRecipePage`, `decodeRecipeFromHash`) is untouched.

## Acceptance criteria

- [x] In `RecipeDetailPage`, when `isFirebaseConfigured` and `!user?.emailVerified`, choosing Share runs `getPublishedRecipe`. A published document: copy the `/shared/<id>` link and record `trackRecipeShared`, exactly as for a verified user. No document, an error or a timeout: open `SignUpDialog` and do nothing else (no `publishRecipe`, no clipboard write, no `trackRecipeShared`). `publishRecipe` is never called for an unverified user.
- [x] While auth is still loading (`isLoading` from `useAuth`, as `RecipeChatPage` reads it), Share does not open the dialog; it stays disabled until auth resolves.
- [x] The dialog copy is: title "Sign up to share this recipe"; body "Share links open from the shared library, so the recipe needs an account with an email. Once you're signed in, tap Share again." "Not now" closes it and the page is unchanged.
- [x] The now unreachable `if (!user?.emailVerified) return false;` inside `handleShare` and its comment are removed. Verified users' Share flow is otherwise unchanged, including the timeout and rate-limit fallbacks to the self-contained link.
- [x] With Firebase not configured, Share still copies a self-contained link with no dialog.
- [x] `src/pages/RecipeDetailPage.test.tsx` (new, following `ProfilePage.test.tsx`'s mocks and `src/test/renderWithProviders.tsx`) covers: anonymous user on an unpublished recipe opens the dialog and `publishRecipe` and the clipboard are not called; anonymous user on a published recipe copies the `/shared/<id>` link with no dialog; anonymous user whose `getPublishedRecipe` rejects gets the dialog, not a self-contained link; signed-out user on an unpublished recipe, dialog; verified user copies a `/shared/<id>` link when `getPublishedRecipe` resolves a document; Firebase not configured copies a `/shared#r=` link.
- [x] `docs/capabilities.md`, "Share a recipe by link" row: says sharing an unpublished recipe needs a verified email when Firebase is configured (RL-061; anonymous and signed-out users can share a recipe that is already published, and otherwise get the sign-up dialog and tap Share again after verifying), and lists when a self-contained link is still produced (local-only mode, publish timeout or failure, the daily publish limit, a copy saved from someone else's link).
- [x] `backlog/DECISIONS.md` gets one row for the no-auto-resume choice (alternative: persist the share intent and copy after the email link completes).
- [x] A `backlog/QA.md` entry: on the preview build, as an anonymous user, open a recipe saved from a share link and tap Share: the dialog shows and nothing is copied. As an anonymous user, open a published recipe from Explore and tap Share: its `/shared/<id>` link is copied with no dialog. Add an email, open the link, return to the recipe and tap Share: a `/shared/<id>` link is copied if you created it, otherwise a self-contained link. Repeat the first step signed out. Check the dialog at 390 px in light and dark mode, and that focus returns to the menu button on "Not now".

## Out of scope

- Removing `hashShareUrl`, `pickShareUrl`'s self-contained branch, or the `/shared#r=` reader.
- Persisting a pending share across the email round trip.
- Letting a verified non-creator publish someone else's recipe, or changing what they get.
- Other entry points: `SharedRecipePage` has no Share action; leave it.
- Refactoring `SuggestChangeModal` or `ProfilePage` onto any new shared gate helper.

## Verification

`npm test` (the new page test), `npm run build`, `npm run lint`. Only a human in a browser can
check the email round trip, the clipboard on iOS Safari, and the dialog's layout and focus
(QA.md entry above).

## Notes

All criteria met. Share is disabled while `isLoading` from `useAuth` is true. The sign-up dialog is a separate `showShareSignUp` state. Focus return and layout are unchecked in a browser (QA.md).
