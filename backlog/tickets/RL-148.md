## Context

Review today is `updateSuggestionStatus(id, 'approved' | 'rejected', reviewer)`
(`src/services/firestore.ts` ~718): approve adds a collaborator, writes the status, then
notifies; `useSuggestionReview` then opens `/recipe/:id/vary` with the message prefilled.
RL-145 recorded the replacement in `docs/decisions.md` and provides `applySuggestionEdits`,
`buildBranchFromSuggestion`, `hasApplicableEdits` and `describeEdits`; RL-146 lets the rules
accept `applied`, `branched` (+ `branchId`) and the two new notification types (repo only;
test against the emulator).

Write paths to reuse, not reinvent:
- An edit by a verified owner is cloud first (decisions.md 1b, RL-083; the save block in
  `RecipeEditPage.tsx` ~297-340): check the cloud copy exists, `publishRecipe(edited)` with a
  fresh `updatedAt` within a timeout, then `cacheRecipe`.
- A new recipe is cloud first (RL-082, `saveRecipe` in `useRecipeChat.ts` ~354-390):
  `publishRecipe` (create path, `recipe` write window, `RateLimitedError`), then `cacheRecipe`.
- Notifications go through `notify()` after the action commits and never fail it (RL-049).
- Order matters as in RL-017: the recipe write first, then the status, then the notification,
  so a failure never leaves a suggestion marked done with nothing behind it.

## Acceptance criteria

- [x] `applySuggestion(suggestion, recipe, reviewer)` in `services/firestore.ts`: with applicable edits, runs `applySuggestionEdits`; stale edits throw a `StaleSuggestionError` (nothing written); otherwise writes the edited recipe with the suggester added to `collaborators` (deduped by uid) through the RL-083 sequence, then `status: 'applied'`, then notifies the suggester (`type: 'suggestion_applied'`, message `describeEdits`). Without applicable edits (free text or general only) it writes only `status: 'applied'` and notifies ("Mark applied").
- [x] `keepSuggestionAsBranch(suggestion, recipe, owner)`: requires `hasApplicableEdits`; builds the branch with `buildBranchFromSuggestion` and a new UUID, publishes it (create) then caches it, then writes `status: 'branched', branchId`, then notifies the suggester (`type: 'suggestion_branched'`, `recipeId` = the branch id, `recipeTitle` = the parent title, message `describeEdits`). A rate-limited publish surfaces `rateLimitMessage` and writes nothing else.
- [x] Decline keeps `updateSuggestionStatus(id, 'rejected', reviewer)`; the `'approved'` branch of that function and the collaborator write are removed, with `addLocalCollaborator` kept only if still used.
- [x] `useSuggestionReview` exposes `apply(id)`, `keepAsBranch(id)`, `decline(id)` with the existing single `reviewingId` guard and an error per action ("Couldn't apply that suggestion. Please try again.", "That recipe changed since the suggestion. Open it and edit by hand.", "Couldn't keep that as a branch. Please try again."). After Keep as branch it navigates to `/recipe/<branchId>` with `state: { saved: 'cloud' }`; after Apply it stays and the recipe shows the change (the own-recipe sync or the cached write).
- [x] `NOTIF_VERBS` gains `suggestion_applied: 'applied your suggestion to'` and `suggestion_branched: 'kept your suggestion as a branch of'`; `AppNotification['type']` gains both; `ActivityPage` `BADGES` gives them the sage `bg-accent-2-600` with `Check` and `GitBranch` icons.
- [x] Analytics: `trackSuggestionReviewed` records `'applied' | 'branched' | 'rejected'` (event name unchanged).
- [x] Tests (`useSuggestionReview.test.tsx` and service tests with the Firestore module mocked): order of writes for apply and branch, nothing written on stale, status not written when the recipe write fails, notification failure does not fail the action, Mark applied path.
- [x] Callers of the old `review(id, 'approve' | 'reject', message)` still compile until RL-149 and RL-150 replace them: keep a thin adapter or update the two call sites minimally (Approve becomes Apply) and say which in the PR.
- [x] `docs/capabilities.md` "Approve / decline a suggestion" row becomes "Apply, keep as branch or decline a suggestion"; `docs/architecture.md` names the write order.
- [x] `npm test`, `npm run lint`, `npm run build` pass.
