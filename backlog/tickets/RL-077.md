## Context

The cloud sync (RL-076 plan, RL-078 wiring) compares a local row's `updatedAt` with the
cloud doc's to decide whether this device holds an edit the cloud lacks. Two writes today
make those values disagree for no real change, which would freeze a recipe on one device:

- `RecipeEditForm.handleSave` (`src/pages/RecipeEditPage.tsx`) calls `updateRecipe`, which
  stamps `updatedAt: Date.now()` in Dexie (`src/db/recipes.ts`), then re-publishes
  `{ ...recipe, ...patch }`, which carries the pre-edit `updatedAt`. The cloud then looks
  older than the edit that produced it, on every device.
- `addLocalCollaborator` (`src/db/recipes.ts`, called from `src/hooks/useSuggestions.ts`)
  bumps `updatedAt` locally when mirroring an approval. The cloud doc's `updatedAt` does not
  move (the approval is an `arrayUnion` on `collaborators` only), so the approving device's
  row looks newer than the cloud forever.

`publishRecipe` writes `updatedAt` as part of the merge (it strips only `chatHistory`, and
`collaborators` on a re-publish), and `isOwnerUpdate` in `firestore.rules` allows it, so no
rules change is needed. Keep the Dexie pattern of `get()` then `put()` (`docs/decisions.md`,
"Dexie `update()`").

## Acceptance criteria

- [ ] `updateRecipe` returns the record it wrote (or `undefined` when the id is not in Dexie), and its only caller is updated.
- [ ] `handleSave` re-publishes a record whose `updatedAt` equals the value Dexie stored for that edit. When the recipe is not in Dexie (opened from the cloud), it publishes with `updatedAt: Date.now()` set once and used for that publish.
- [ ] `addLocalCollaborator` writes the collaborator without changing `updatedAt`. Its existing idempotence on uid is unchanged.
- [ ] `src/db/recipes.test.ts` covers: `updateRecipe` returns the stored row with the new `updatedAt`; `addLocalCollaborator` leaves `updatedAt` as it was.
- [ ] Nothing else about the edit flow changes: still local first, still re-publishes only when a published copy exists, same toasts.
- [ ] `docs/data-model.md` says, in the recipes rules paragraph or beside the Dexie table, that a re-publish after an edit carries the same `updatedAt` Dexie stored, and why (the sync compares them).
- [ ] A `backlog/QA.md` entry: on the preview as a verified user, edit a published recipe, then open its `/shared/<id>` link in a private window and confirm the edit shows. (The updatedAt value itself is checked by the test, not by hand.)
- [ ] `npm run build`, `npm run lint` and `npm test` pass.

## Out of scope

Changing whether an edit publishes a recipe that has no cloud copy (waits on the author's
answer about private recipes). Any sync code (RL-078). `migrateRecipesUid`, which also
stamps `updatedAt` but moves rows to a new uid, so the sync treats them as unsynced anyway.
