## Context

`.claude/skills/release/SKILL.md` step 5 runs `npx firebase deploy` from the author's laptop
and step 6 verifies by hand. The author decided `/release` only tags, and the production
workflow (RL-298) deploys after their approval. The workflow takes the order from a
`deploy-order:` line in the annotated tag message (RL-295 `orderFromTagMessage`), so
`/release` is where the order is decided: it reads the `done` deploy tickets in this release
(their titles say "rules before the client" or "client first") and whether `TERMS_VERSION`
changed since the last tag (`src/lib/legal.ts`).

`docs/operations.md` "Release and deploy runbook (first production release)" is the
v0.3.0 checklist and is now history; its "Deploying" section carries the manual commands, the
ruleset diff recipe and the header checks, which RL-296 automated. There is no rollback
section: the only rollback note is "note the previous ruleset id".

## Acceptance criteria

- [ ] `/release` steps 1 to 3 are unchanged. Step 4 creates an **annotated** tag
  `vX.Y.Z` whose message includes `deploy-order: rules-first` or `deploy-order: client-first`,
  chosen as: rules first by default; client first only when a `done` deploy ticket in the
  release says client first and `TERMS_VERSION` did not change since the previous tag; if a
  ticket says client first and the Terms version changed, or tickets conflict, ask the author
  with AskUserQuestion. It pushes the commit and the tag.
- [ ] Step 5 no longer runs any `firebase` command. It tells the author the run is waiting
  (`gh run list --workflow deploy-prod.yml --limit 1`, with the run URL), that they approve it
  under Review deployments after reading the plan summary, and waits for the run to finish
  (`gh run watch`).
- [ ] Step 6 reads the run's summary instead of verifying by hand: an empty ruleset diff after
  deploy, the header check, the bundle match, both ruleset ids. A failed or stopped run is
  reported with its step and the rollback below; the release is not called done.
- [ ] Step 7's final message names the version, tag, order and reason, the ruleset ids, and the
  live URL. The skill never deploys `functions/`.
- [ ] `docs/operations.md`: the first-release runbook moves under the RL-042 "First release
  record" as history (kept, shortened to what happened); a new "Release runbook" gives the
  steps above in order: `/qa-pass` on dev, `/release`, approve, live walks. The manual
  commands in "Deploying" are kept only as the documented break-glass path for when GitHub Actions is
  unavailable (no npm script for it), with the warning that it bypasses the approval and must
  name `--project prod`.
- [ ] A new "Rollback" section in `docs/operations.md`: hosting, by Firebase console, Hosting,
  Release history, Roll back on the previous release (instant, no rebuild) or a dispatch of
  Deploy prod from the previous tag; rules, by a dispatch of Deploy prod from the previous tag
  with the order that suits, or by releasing the recorded previous ruleset id; indexes are
  never deleted by the pipeline, so an old client keeps working; a rollback across a Terms
  bump needs the rules and client rolled back together, rules last.
- [ ] `docs/agent-workflow.md`'s description of `/release` matches.
- [ ] `backlog/QA.md` gets a line: the next `/release` stops at the approval prompt and the
  tag message carries a `deploy-order` line.
- [ ] `npm run backlog -- validate` passes.
