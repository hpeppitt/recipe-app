## Context

RL-146 and RL-152 change `firestore.rules` in the repo. Deploying rules is a human step
(`backlog/README.md`). The repo already carries an undeployed rules set waiting on RL-022 and
RL-051; rules deploy as one unit, so this deploy goes after RL-051's. Order: ship the client
that writes `edits`, `applied`, `branched`, `branchId` and `branch` notifications first (the
live rules still allow `approved` and plain suggestions, so old behaviour keeps working), then
the rules, because once these rules are live `'approved'` is denied and an old client's Approve
fails. This becomes `needs-human` when approved at /groom.

## Acceptance criteria

- [ ] The client from RL-148 to RL-155 is live (`/release`).
- [ ] The live ruleset is diffed against HEAD before and after `firebase deploy --only firestore:rules`, per docs/operations.md "Diff the released ruleset", with both ruleset ids recorded in operations.md; the after-diff is empty.
- [ ] On live, with two verified accounts: a structured suggestion applies, one is kept as a branch, one is declined; a branch notifies the parent's author; a notification toggle saves.
- [ ] capabilities.md and data-model.md lose their "deployed by RL-156" caveats.

## Out of scope

Any code change. The reparent rules (RL-160).
