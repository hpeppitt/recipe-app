## Context

RL-135 stores a `PendingAction` before the link is sent and returns the link to the page.
This ticket runs it. The verified state arrives asynchronously after the link completes
(`AuthContext` `runEmailLinkCompletion`), and the Terms check (`checkTermsOnce`, RL-047) may
block contributing until accepted, so the hook must wait for a verified user whose terms are
settled. Writes reuse the existing paths: favourite `toggleFavorite` (`useFavorite` /
`useCloudFavorite`), follow `toggleFollow` (`useFollow`), suggest opens suggest mode
(`setSuggestingFor` on the recipe page, `setSuggesting` on the shared page), branch navigates
to `/recipe/<id>/vary`.

## Acceptance criteria

- [x] `usePendingAction(match: (a: PendingAction) => boolean, run: (a: PendingAction) => void)`: when the user is verified, auth is not loading, the Terms prompt is not pending, and a stored action passes `parsePendingAction` and `match`, it clears the stored action first, then calls `run` exactly once (StrictMode-safe ref guard). A stored action that does not match the page stays stored until it expires or another page matches it.
- [x] Recipe page and shared page: `save` turns the favourite on only if it is off (never toggles it off); `suggest` opens suggest mode when the recipe can be suggested to (otherwise nothing); `branch` navigates to `/recipe/<id>/vary`. Profile: `follow` follows only if not already following.
- [x] Each run shows the page's existing confirmation (Saved state, Following state, suggest mode, the composer); a failure shows the page's existing error, and the action is not retried.
- [x] An expired, malformed or mismatched action never runs. Signing out clears it.
- [x] Tests (`usePendingAction.test.tsx` with a mocked auth context): runs once for a matching action, not for unverified, not while terms pending, not when expired, clears before running, and `save` does not unsave an already saved recipe.
- [x] `docs/capabilities.md`: the sign-in row says the interrupted save, follow, suggest or branch now runs on return, same device only, within an hour.
- [x] A `backlog/QA.md` entry. `npm test`, `npm run lint`, `npm run build` pass.

## Out of scope

Guest (anonymous) upgrades through `AuthModal`'s guest option beyond `save`. Any new
confirmation UI. Cross-device runs.

## Verification

Gates: tests, `ui-reviewer`, `data-integrity-reviewer` (favourite and follow writes reached
from a new trigger). Emulator walk for each of save, follow, suggest and branch: signed out,
tap, send link, open it in the same browser, see the action done once; reload the page and see
it does not run again.

## Notes

- From RL-135 review: clear the intent on consume and on sign-out, and ignore it if the signed-in uid differs from the one that asked (shared devices).
- "The uid that asked" is pinned at completion: a signed-out visitor has no uid, so `AuthContext` stamps the stored intent with `by` (the uid this device's own link signed in) after `checkTermsOnce`, and `usePendingAction` runs it only for that uid. A completion with a typed address (link sent from another device) clears it; `signOut` clears it. Logged in `backlog/DECISIONS.md` and `docs/decisions.md`.
- `useFavorite`, `useCloudFavorite` and `useFollow` gain `ready` (the lookup for the current key has answered), so Save and Follow only run once the current state is known and only ever turn on.
- A branch intent on the recipe page matches any recipe in the loaded family, since the tree's "Branch from" can name another version.
- Review fixes: `useFavorite.ready` waits for the first cloud hydrate per uid (the module `hydrations` map now holds a settled promise) and re-reads Dexie after it, so a cloud-only favourite is not re-added. `useFollow.ready` stays false after a failed lookup. The profile follow also waits for the profile to load. The auth listener clears the intent when a user goes to none (sign-out in another tab), not on a load that starts signed out.
- No announcement added for a remembered Save: neither page announces a favourite save today (the Save button's Saved label and `aria-pressed` are the confirmation). `SavedToast` is the generated-recipe publish toast ("Recipe saved" or "Saved on this device"), only on the recipe page, and `useFavorite` swallows cloud failures, so reusing it would claim a save that may not have reached the cloud. Logged as a reviewer note in QA.md.
