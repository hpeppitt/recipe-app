## Context

RL-040 makes every cloud write need `verified()`. Without this ticket the client would keep
attempting those writes for anonymous users and fail with `permission-denied`. The pattern to
follow is the one-tap sign-up gate from PR #16 (commit d9e28ef): contribute actions open a
dialog that shows `EmailLinkingForm` with `tone="invite"` to anyone without `emailVerified`,
which picks `linkEmail` for an anonymous account (keeping the uid) and `sendEmailLink` for a
signed-out visitor. `SuggestChangeModal.tsx` (`needsSignUp`) and `RecipeChatPage.tsx` (line
137) are the two existing gates.

Anonymous cloud writes today: the favourite toggle writes Dexie then `addCloudFavorite` /
`removeCloudFavorite` (`useFavorite`, `useCloudFavorite`); `useFollow` writes follows;
`AuthContext` calls `createOrUpdateProfile` on every auth change and in
`handleSignInAnonymously`; profile editing on `ProfilePage` writes the profile.

A bookmark needs a uid (Dexie favourites are keyed by `uid`), and product decision 6 rejected
a synthetic device uid. So "signed-out" bookmarking keeps going through the existing one-tap
anonymous sign-in prompt; see the author question on this.

## Acceptance criteria

- [ ] For a user without `emailVerified`, `useFavorite` writes Dexie only and never calls `addCloudFavorite` or `removeCloudFavorite`. Verified users keep today's dual write.
- [ ] On `SharedRecipePage`, an anonymous user's favourite toggle saves a local bookmark (a Dexie favourite row) instead of calling `useCloudFavorite`'s cloud path. A signed-out user gets the existing sign-in prompt, whose anonymous option is described as "bookmark on this device only".
- [ ] Follow, profile editing (name and avatar) and any other cloud action open the sign-up call to action for anonymous and signed-out users instead of writing.
- [ ] `AuthContext` does not call `createOrUpdateProfile` for an anonymous user, either on auth change or in `handleSignInAnonymously`. The generated display name stays on the Firebase Auth user. On upgrade to a verified email the profile is created as for any email user.
- [ ] `AuthModal` copy for "Continue Anonymously" says it only saves bookmarks on this device.
- [ ] On upgrade, local bookmarks are left in Dexie untouched by this ticket. Pushing them into cloud favourites on the verified account is RL-034 (author answer, 2026-10-14).
- [ ] Anonymous account creation is unchanged: one tap, with the auto-generated display name from `lib/identity.ts` (author answer, 2026-10-14).
- [ ] Generation stays verified-only and is guarded against regression: the check in `RecipeChatPage.tsx` (line 137) moves into a pure `canGenerate({ isConfigured, user })` in `src/lib/` (true only for a configured app with a user whose `emailVerified` is true, or for local-only mode where the composer is already disabled), used by `RecipeChatPage`, with tests covering signed-out, anonymous, unverified and verified users.
- [ ] No `permission-denied` is thrown or beaconed during an anonymous session that bookmarks, opens profiles and browses.
- [ ] `docs/capabilities.md` rows for favourites, following and profiles say what an anonymous user can do.
- [ ] A `backlog/QA.md` entry: as an anonymous user on the preview build, bookmark a recipe and see it under Favorites, tap Follow and get the sign-up call to action, open your own profile and confirm editing routes to sign-up; console clean throughout.

## Out of scope

Signed-out bookmarking without any account, pushing bookmarks to the cloud on upgrade (RL-034), the
rules (RL-040), and the async hygiene in the same hooks (RL-026).

## Verification

`npm run build`, `npm run lint`, `npm test`; hook tests if RL-002 has landed. Browser walk
against the emulator with RL-040's rules loaded, as anonymous, signed-out and verified.
