## Context

The suite covers `src/db` and `src/lib` only, in a node environment. Every page and hook
is protected by nothing but the typecheck hook, and browser verification has been
unavailable to agents since 2026-08-13 (see docs/operations.md). An autonomous loop that
cannot run a browser needs a cheaper net under the UI, or every UI ticket ends in the
human QA pass unverified. This is the single biggest enabler for the workflow.

## Acceptance criteria

- [ ] `@testing-library/react`, `@testing-library/jest-dom`, `@testing-library/user-event` and `jsdom` are dev dependencies; nothing new ships in the client bundle.
- [ ] Vitest runs `*.test.tsx` files under a jsdom environment and the existing node suites still run under node (per-file environment pragma or a workspace split, whichever is smaller).
- [ ] A `renderWithProviders` helper in `src/test/` wraps a component in `MemoryRouter` and `AuthProvider` with an injectable fake user, so page tests do not touch Firebase.
- [ ] Two example tests prove the harness: `RecipeCard` renders a title and emoji; `EmptyState` renders its action button and the click handler fires.
- [ ] `npm test` and CI pass with no change to `.github/workflows/ci.yml` beyond what jsdom needs.
- [ ] `docs/operations.md` describes how to write a component test and which environment a test file gets.

## Out of scope

Backfilling tests for existing pages. Each later UI ticket adds its own.

## Verification

`npm test` green, the two example tests present, and the time for the full suite stays under a minute.

## Notes

Firebase SDK imports in `services/firebase.ts` are no-ops when `VITE_FIREBASE_*` are unset,
which is already the test environment. If a page test still pulls Firebase in, mock
`services/firebase` at the module boundary rather than adding env vars.
