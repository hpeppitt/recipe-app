## Context

Product decision 2 keeps the project on Spark with no Cloud Functions, so per-user limits
have to be enforced by the rules alone. The existing `rateLimits/{uid}` collection is
reserved for the undeployed Cloud Function and must stay closed (see its comment in
`firestore.rules`), so this uses a new collection.

Pattern (groomer's design, reversible): one document per user per action,
`writeWindows/{uid}_{action}` with `windowStart` (timestamp), `count` (int) and `at`
(timestamp). The limited write and the window update go in one transaction. The window rule
allows: create with `count == 1` and `windowStart == at == request.time`; update either
starting a new window (only when `request.time > resource.data.windowStart + window`) with
`count == 1`, or the same window with `count == resource.data.count + 1` and
`count <= cap`; always `at == request.time`; never delete (a delete would reset the limit).
The limited document's create rule requires
`getAfter(/databases/$(database)/documents/writeWindows/$(request.auth.uid + '_' + action)).data.at == request.time`,
which proves the window moved in the same request. Two extra reads per limited write.

Caps (groomer's choice): suggestions 10 per hour, replies 30 per hour. Messaging abuse is the
author's stated concern; suggestions and replies are also what produce notifications.

## Acceptance criteria

- [x] `firestore.rules` has a `writeWindows/{windowId}` block as above: owner read; create and update only by `verified()` with `windowId == request.auth.uid + '_' + action` for `action in ['suggestion', 'reply']`; `keys().hasOnly(['windowStart', 'count', 'at'])`; delete denied.
- [x] Suggestion create and message create additionally require the `getAfter` check for their action.
- [x] `src/lib/rateLimit.ts` exports the caps and window lengths and a pure `nextWindow(prev, nowMs, cap, windowMs)` that returns the next state or `limited`, with tests for first write, within window, at cap, over cap and window expiry.
- [x] `createSuggestion` and `addSuggestionMessage` use `runTransaction`: read the window, call `nextWindow`, throw a `RateLimitedError` without writing if limited, otherwise write the content and the window (with `serverTimestamp()` for `at` and, on reset, `windowStart`).
- [x] `lib/errors.ts` maps `RateLimitedError` to "You've sent a lot of suggestions recently. Try again in a while." (or "replies"), shown in the existing error slot of the suggest dialog and the reply form.
- [x] Each `RateLimitedError` is reported through `reportError` with context `rate-limited-suggestion` or `rate-limited-reply`. That `clientErrors` entry, which carries the uid, is the detection signal (see RL-050).
- [x] The notification side-write keeps working: it is still fire-and-forget after the transaction commits.
- [x] `docs/data-model.md` documents `writeWindows` and the read cost; `docs/decisions.md` records the pattern and caps.
- [x] A `backlog/QA.md` entry: on the preview build, send replies quickly past the cap and confirm the message, then confirm the clientErrors entry in the console.

## Notes

- Implemented 2026-10-15. Rules: `suggestionCap()` 10, `replyCap()` 30, `windowMs()` 3600000 as named functions with a comment block; `movedWindow(action)` (`existsAfter()` then `getAfter().data.at == request.time`) ANDed onto the suggestion and message creates after every existing condition (RL-017, RL-018, RL-047 untouched); a `writeWindows/{windowId}` block. Client: `src/lib/rateLimit.ts` (`SUGGESTION_CAP`, `REPLY_CAP`, `WINDOW_MS`, `RESET_MARGIN_MS` 60000, `nextWindow`), `RateLimitedError` and `rateLimitMessage` in `src/lib/errors.ts`, and `writeLimited()` in `src/services/firestore.ts` used by `createSuggestion` and `addSuggestionMessage`.
- Trap 1, read rule: decided from the id only (`windowId in [uid + '_suggestion', uid + '_reply']`), never `resource.data`. Probed: a read of a MISSING window as its owner returns 404 (allowed, not found); as another user 403; signed out 403. A uid has no underscore and the list match is exact, so `x_suggestion_extra`, `x_other` and another user's id are denied for read and write.
- Trap 2, access calls: a transaction commit is a multi-document request (limit 20). Suggestion create touches the recipe, `termsAcceptance` (exists and get of one path) and the window (existsAfter and getAfter of one path): 3 documents. Message create touches the parent suggestion (two get()s of one path), `termsAcceptance` and the window: 3 documents. The window write's own rule touches none. All full-guard creates with a valid current `termsAcceptance` seeded passed under the emulator (below). Nothing comes near the limit.
- Trap 3, clock skew: the client resets only when `nowMs > windowStart + WINDOW_MS + RESET_MARGIN_MS`, otherwise increments; the rules' same-window branch has no time check, so an increment past server expiry is accepted (probed: window expired 61 min ago, count 5 -> 6, allowed). A slow client clock only makes the user wait a little longer. A future `windowStart` counts as an open window; `nextWindow` never throws. A client clock more than a minute fast can still see a reset denied (generic failure).
- Trap 4, offline: a transaction is not queued. Behaviour change: a suggestion or reply made offline now fails with the generic message instead of queueing. Bounded at 5 s with the existing rejecting `rejectAfter` (constant renamed `TERMS_TIMEOUT_MS` to `CALL_TIMEOUT_MS`), not `withTimeout`, because `withTimeout` resolves a fallback and would swallow `RateLimitedError`. Measured with the web SDK in node: against an unreachable backend `runTransaction` rejects `unavailable` after about 9.5 s, so the 5 s bound fires first. Note `disableNetwork()` does NOT stop a transaction (it committed in the probe); real loss of connectivity does. A timed-out transaction may still commit later.
- Trap 5, deploy order: both orders break suggestions and replies for a short gap (control on HEAD rules: the new client's window read and the suggestion plus window commit are both 403). No client fallback, by design; logged pending in backlog/DECISIONS.md. docs/operations.md: client then rules, back to back, consistent with RL-047's client-first order, with what users see in each gap.
- Same-window increments use `tx.update(windowRef, { count, at: serverTimestamp() })`, so `windowStart` stays as stored and the rule's `request.resource.data.windowStart == resource.data.windowStart` holds; first write and reset use `tx.set` of all three fields with `serverTimestamp()` for `windowStart` and `at`.
