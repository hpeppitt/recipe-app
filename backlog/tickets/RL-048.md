## Context

Product decision 2 keeps the project on Spark with no Cloud Functions, so per-user limits
have to be enforced by the rules alone. The existing `rateLimits/{uid}` collection is
reserved for the undeployed Cloud Function and must stay closed (see its comment in
`firestore.rules`), so this uses a new collection.

Pattern (groomer's design, reversible): one document per user per action,
`writeWindows/{uid}_{action}` with `windowStart` (timestamp), `count` (int) and `at`
(timestamp). The limited write and the window update go in one transaction. The window rule
allows: create with `count == 1` and `windowStart == at == request.time`; update either
starting a new window (only when `request.time > resource.data.windowStart + window`) with
`count == 1`, or the same window with `count == resource.data.count + 1` and
`count <= cap`; always `at == request.time`; never delete (a delete would reset the limit).
The limited document's create rule requires
`getAfter(/databases/$(database)/documents/writeWindows/$(request.auth.uid + '_' + action)).data.at == request.time`,
which proves the window moved in the same request. Two extra reads per limited write.

Caps (groomer's choice): suggestions 10 per hour, replies 30 per hour. Messaging abuse is the
author's stated concern; suggestions and replies are also what produce notifications.

## Acceptance criteria

- [ ] `firestore.rules` has a `writeWindows/{windowId}` block as above: owner read; create and update only by `verified()` with `windowId == request.auth.uid + '_' + action` for `action in ['suggestion', 'reply']`; `keys().hasOnly(['windowStart', 'count', 'at'])`; delete denied.
- [ ] Suggestion create and message create additionally require the `getAfter` check for their action.
- [ ] `src/lib/rateLimit.ts` exports the caps and window lengths and a pure `nextWindow(prev, nowMs, cap, windowMs)` that returns the next state or `limited`, with tests for first write, within window, at cap, over cap and window expiry.
- [ ] `createSuggestion` and `addSuggestionMessage` use `runTransaction`: read the window, call `nextWindow`, throw a `RateLimitedError` without writing if limited, otherwise write the content and the window (with `serverTimestamp()` for `at` and, on reset, `windowStart`).
- [ ] `lib/errors.ts` maps `RateLimitedError` to "You've sent a lot of suggestions recently. Try again in a while." (or "replies"), shown in the existing error slot of the suggest dialog and the reply form.
- [ ] Each `RateLimitedError` is reported through `reportError` with context `rate-limited-suggestion` or `rate-limited-reply`. That `clientErrors` entry, which carries the uid, is the detection signal (see RL-050).
- [ ] The notification side-write keeps working: it is still fire-and-forget after the transaction commits.
- [ ] `docs/data-model.md` documents `writeWindows` and the read cost; `docs/decisions.md` records the pattern and caps.
- [ ] A `backlog/QA.md` entry: on the preview build, send replies quickly past the cap and confirm the message, then confirm the clientErrors entry in the console.

## Out of scope

Notification and recipe-create limits (RL-049), console settings (RL-050), the deploy
(RL-051), and per-recipient limits.

## Verification

`npm test`. Emulator probes recorded in Notes: suggestion without the window write (deny),
with it (allow), the 11th within an hour (deny), a window reset before the hour (deny),
deleting a window (deny), writing another user's window (deny). App walk-through against
`npm run dev:emulated` with the cap temporarily lowered in both places.
