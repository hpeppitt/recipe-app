## Context

`firestore.rules` lines 168-172: `notifications` create checks only `fromUid` and
`read == false`, so any signed-in account can write a notification to any `recipientUid`
with any `type`, any `message` and any extra fields.

RL-040 applies the 2026-10-14 decision (anonymous accounts are local-bookmark only) and
raises this create rule to `verified()`, which also makes the old comment about keeping it
open for anonymous favourites and follows obsolete. This ticket adds the shape checks on top,
so it lands after RL-040 in the same rule block.

Notification writers today, all in `src/services/firestore.ts`: `addCloudFavorite`
(`favorite`, message null), `followUser` (`follow`, message null, no recipe fields),
`createSuggestion` (`suggestion`), `addSuggestionMessage` (`suggestion_reply`),
`updateSuggestionStatus` (`suggestion_approved` / `suggestion_rejected`). The last three
copy user text into `message`, and neither suggestions nor replies have a length cap, so a
500-character rule cap would silently drop the notification for a long suggestion (the
writes are fire-and-forget by design, see "Notifications are fire-and-forget" in
`docs/decisions.md`).

## Acceptance criteria

- [ ] The `notifications` create rule additionally requires `request.resource.data.keys().hasOnly(['recipientUid', 'type', 'recipeId', 'recipeTitle', 'recipeEmoji', 'fromUid', 'fromDisplayName', 'message', 'read', 'createdAt'])`.
- [ ] Create stays `verified()` (from RL-040).
- [ ] `type in ['favorite', 'follow']` requires `message == null`.
- [ ] `type in ['suggestion', 'suggestion_reply', 'suggestion_approved', 'suggestion_rejected']` requires `message` either null or a string with `size() <= 500`.
- [ ] Any other `type` is denied.
- [ ] A pure helper in `src/lib/notifications.ts` truncates notification message text to at most 500 characters (ellipsis included), with tests in `src/lib/notifications.test.ts` for under, at, and over the limit.
- [ ] The three text-carrying notification writes in `services/firestore.ts` pass `message` through that helper. The suggestion and message documents themselves keep the full text.
- [ ] `docs/data-model.md`, notifications paragraph, states the new constraints.
- [ ] A `backlog/QA.md` entry under "Since the last release" says: after the rules deploy (RL-022), favourite a recipe and follow its owner from a second verified account and confirm the owner gets both notifications.

## Out of scope

Constraining `recipientUid` (for example forbidding self-notification), capping
`recipeTitle`, adding a length cap to suggestions or replies themselves, and deploying the
rules. The deploy is RL-022.

## Verification

`npm test` for the helper. Emulator probes (`npm run emulators`, see `docs/operations.md`)
recorded in Notes, each an allow or deny observed, all as a verified user unless stated:
`favorite` with null message (allow), `favorite` with a message (deny), `suggestion` with 500
chars (allow) and 501 chars (deny), any write with an extra key (deny), unknown `type`
(deny), anonymous `favorite` (deny). Then the app against the emulator: a verified favourite
and follow still notify the owner.
