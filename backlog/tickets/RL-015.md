## Context

`firestore.rules` lines 168-172: `notifications` create checks only `fromUid` and
`read == false`, so any signed-in account can write a notification to any `recipientUid`
with any `type`, any `message` and any extra fields.

RL-040 applies the 2026-10-14 decision (anonymous accounts are local-bookmark only) and
raises this create rule to `verified()`, which also makes the old comment about keeping it
open for anonymous favourites and follows obsolete. This ticket adds the shape checks on top,
so it lands after RL-040 in the same rule block.

Notification writers today, all in `src/services/firestore.ts`: `addCloudFavorite`
(`favorite`, message null), `followUser` (`follow`, message null, no recipe fields),
`createSuggestion` (`suggestion`), `addSuggestionMessage` (`suggestion_reply`),
`updateSuggestionStatus` (`suggestion_approved` / `suggestion_rejected`). The last three
copy user text into `message`, and neither suggestions nor replies have a length cap, so a
500-character rule cap would silently drop the notification for a long suggestion (the
writes are fire-and-forget by design, see "Notifications are fire-and-forget" in
`docs/decisions.md`).

## Acceptance criteria

- [x] The `notifications` create rule additionally requires `request.resource.data.keys().hasOnly(['recipientUid', 'type', 'recipeId', 'recipeTitle', 'recipeEmoji', 'fromUid', 'fromDisplayName', 'message', 'read', 'createdAt'])`.
- [x] Create stays `verified()` (from RL-040).
- [x] `type in ['favorite', 'follow']` requires `message == null`.
- [x] `type in ['suggestion', 'suggestion_reply', 'suggestion_approved', 'suggestion_rejected']` requires `message` either null or a string with `size() <= 500`.
- [x] Any other `type` is denied.
- [x] A pure helper in `src/lib/notifications.ts` truncates notification message text to at most 500 characters (ellipsis included), with tests in `src/lib/notifications.test.ts` for under, at, and over the limit.
- [x] The three text-carrying notification writes in `services/firestore.ts` pass `message` through that helper. The suggestion and message documents themselves keep the full text.
- [x] `docs/data-model.md`, notifications paragraph, states the new constraints.
- [x] A `backlog/QA.md` entry under "Since the last release" says: after the rules deploy (RL-022), favourite a recipe and follow its owner from a second verified account and confirm the owner gets both notifications.

## Out of scope

Constraining `recipientUid` (for example forbidding self-notification), capping
`recipeTitle`, adding a length cap to suggestions or replies themselves, and deploying the
rules. The deploy is RL-022.

## Verification

`npm test` for the helper. Emulator probes (`npm run emulators`, see `docs/operations.md`)
recorded in Notes, each an allow or deny observed, all as a verified user unless stated:
`favorite` with null message (allow), `favorite` with a message (deny), `suggestion` with 500
chars (allow) and 501 chars (deny), any write with an extra key (deny), unknown `type`
(deny), anonymous `favorite` (deny). Then the app against the emulator: a verified favourite
and follow still notify the owner.

Implemented 2026-10-14. Rule: `keys().hasOnly([...])` (no `hasAll`, so `follow` may omit the
recipe fields) plus a type-gated message check, on top of RL-040's `verified()`. The message
check uses `get('message', null)` so an absent `message` behaves as null.

Writers checked against the rule: `addCloudFavorite`, `followUser`, `createSuggestion`,
`addSuggestionMessage`, `updateSuggestionStatus` each send a subset of the allowed keys with no
extra key. The last three now pass `message` through `truncateNotificationMessage`.
`updateSuggestionStatus` falls back to null when the stored suggestion's `message` is not a
string, because the suggestion create rule does not enforce it and a throw there would land
after the status write.

Finding: the rules' `string.size()` counts UTF-16 code units, not code points or bytes.
Observed on the emulator: 250 emoji (500 units) allow, 251 emoji (502 units) deny, 500 `é`
allow, 501 `é` deny. The helper therefore counts `.length` and drops a trailing high
surrogate rather than splitting an emoji.
