## Context

Author decision of 2026-10-18, verbatim: "the behaviour needs to change where they're
stored. Recipes should be stored in the cloud and retrieved from the cloud on every device
so it's always the same. If this clashes with our previous logic, go with cloud as the
source of truth and load from local if there's no internet connection".

Follow-up answers the same day: creation needs a verified email (decision 1a), so only
verified users create recipes; a verified user's save and edit go to Firestore first and are
cached in Dexie only on success, with a failure shown as an error and a retry (RL-082,
RL-083), so no own recipe exists only on a device; edits from two devices are last write
wins; My Recipes becomes Created and Branched for the user's own recipes, with other people's
recipes listed only under Saved (the tabs are the rebrand's, RL-084 has the classifier).

Trigger: a recipe made on a phone was in Firestore and on Explore, but not in My Recipes or
the profile on a computer. Both read Dexie only (`useLocalLibrary` in
`src/hooks/useRecipeLibrary.ts`, `useOwnRecipes` in `src/hooks/useUserRecipes.ts`).

The shape (RL-078 wires it): a live listener copies the verified user's own Firestore
recipes into Dexie, so every Dexie reader shows the cloud state, and offline the last copy.
This ticket is the pure half. Because the save is cloud first, a server snapshot is the
whole truth about the user's own recipes: present means overwrite, absent means remove.

Tidy for rows from other accounts on this device, including the rows stamped with uids from
before the 2026-10-18 production wipe: `getPreviousUids()` (`src/services/storage.ts`, filled
by `AuthContext` on every sign-in) lists every uid that has signed in on this device. A row
whose `createdBy.uid` is in that list but is not the current user was made by another account
on this device. After cloud-first saves its cloud copy is the truth, and before the wipe it
is stale, so removing it is safe either way. Saved copies keep their original author's uid
(`handleSaveCopy` in `src/pages/SharedRecipePage.tsx`), which is not in the list unless that
author signed in here, and `'local'` rows (pre-auth, Dexie v2 backfill) are never in it, so
neither is touched. The service layer passes the list in, so `lib/` stays free of `services/`
imports (`docs/architecture.md`).

## Acceptance criteria

- [ ] `src/lib/recipeSync.ts` exports `planOwnRecipeSync(uid, localRows, cloudDocs, previousUids)` returning `{ put: Recipe[]; remove: string[] }`, with no imports from `services/`, `hooks/` or `db/`. The cloud document type is declared in this file.
- [ ] Cloud docs whose `createdBy.uid` is not `uid` are ignored. A malformed cloud doc (no string `id`, no string `title`, `ingredients` or `instructions` not arrays) is skipped, and a local row with that id is neither written nor removed.
- [ ] Each valid cloud doc goes in `put`, converted by an exported `toLocalRecipe(doc, localRow?)` that keeps only `Recipe` fields (drops `favoriteCount`, `viewCount` and any unknown key), defaults `parentId` to null, `rootId` to the id, `depth` to 0, `collaborators` to [], `prompt` to '', `notes` to [], and takes `chatHistory` from the local row or []. It is left out of `put` when the result equals the local row, so an unchanged snapshot writes nothing. No timestamp comparison: the cloud always wins (last write wins).
- [ ] A local row with `createdBy.uid === uid` and no cloud doc is in `remove`.
- [ ] A local row with `createdBy.uid !== uid` is in `remove` only when its uid is in `previousUids`. Rows of any other uid, including `'local'` and saved copies of other people's recipes, never appear in `put` or `remove`.
- [ ] `src/lib/recipeSync.test.ts` covers every criterion above with `makeRecipe` from `src/test/factories.ts`, including: an empty snapshot removes every own row and no saved copy; a changed title is overwritten; local `chatHistory` survives a merge; a previous account's row is removed and a `'local'` row is kept; running the plan on its own output gives an empty plan.
- [ ] `docs/decisions.md` gains "1b. A verified user's own recipes live in the cloud (2026-10-18)" under Product decisions. It quotes the author verbatim and records: Firestore is the source of truth for a verified user's own recipes, Dexie is their cache and offline fallback; creation needs a verified email (1a), so anonymous and signed-out users only keep local bookmarks of other people's recipes; save and edit are cloud first, cached in Dexie on success, with a failure shown as an error and a retry, no offline create and no queue (generation needs the network anyway); the sync overwrites from every server snapshot and removes own rows the snapshot lacks; edits from two devices are last write wins; rows of other accounts that signed in on this device are tidied away; My Recipes is split into Created (own, no parent) and Branched (own variations, including of other people's recipes), and other people's recipes appear only under Saved; a live listener is used although RL-043 rejected one for favourites, because "always the same" is the requirement and own recipes are one query; synced rows take the cloud's lower-case tags, reversing the RL-059 note that Dexie keeps its case; signing out of a verified account removes that account's own recipes from the device and they reload on the next sign-in (RL-085); imports are Saved copies, never published, and never carry the importer's or another of this device's account uids (RL-086).
- [ ] The same change adds a one-line dated note pointing at 1b to each entry it amends: product decision 4 (My Recipes still reads Dexie, filled from the cloud, and is split by RL-084), product decision 5 (a verified user's cleared recipes come back, copy is RL-081), "Recipe delete waits for the cloud" RL-023 (order reversed by RL-080), "Edits apply in place" (edits are cloud first, RL-083; an edit still never creates a cloud copy), and RL-049's recipe limit paragraph (a limited save now writes nothing anywhere and the chat page says why, RL-082).
- [ ] A `backlog/QA.md` entry for this ticket says there is nothing to check in a browser yet and names RL-078 as the ticket that makes it visible.
- [ ] `npm run build`, `npm run lint` and `npm test` pass.
