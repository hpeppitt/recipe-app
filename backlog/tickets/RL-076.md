## Context

Author decision of 2026-10-18, verbatim: "the behaviour needs to change where they're
stored. Recipes should be stored in the cloud and retrieved from the cloud on every device
so it's always the same. If this clashes with our previous logic, go with cloud as the
source of truth and load from local if there's no internet connection".

Trigger: the author made a recipe on a phone, signed in on a computer, and it was in
Firestore and on Explore but not in My Recipes or the profile. Both read Dexie only:
`useLocalLibrary` in `src/hooks/useRecipeLibrary.ts` and `useOwnRecipes` in
`src/hooks/useUserRecipes.ts`. `useRecipe` (`src/hooks/useRecipe.ts`) and `useRecipeTree`
already fall back to or merge the cloud, but prefer the local row, so a stale local copy
hides a newer cloud one.

The chosen shape (RL-078 wires it): a verified user's own recipes in Firestore are copied
into Dexie by a live listener, so every Dexie reader (My Recipes, profile, detail, tree,
edit) shows the cloud state, and offline the same readers show the last copy. This ticket
is the pure half: given the local rows and one server snapshot of the user's own cloud
recipes, return what to write and what to remove. It must never destroy local work that
has not reached the cloud.

To tell "deleted on another device" from "never reached the cloud" without a Dexie schema
change, a local row gets an optional, non-indexed `syncedAt`: the cloud version (its
`updatedAt`, else `createdAt`) last applied to that row. Non-indexed fields need no Dexie
version bump (see `docs/data-model.md` Migrations). The import schema
(`ImportedRecipeSchema`, a plain `z.object` extend) already strips unknown keys, so an
imported row never carries it; a test pins that.

`lib/` may not import from `services/` or `hooks/` (`docs/architecture.md`), so the cloud
document type is declared here, not taken from `PublishedRecipe`.

## Acceptance criteria

- [ ] `Recipe` in `src/types/recipe.ts` gains `syncedAt?: number` with a one-line comment: the cloud `updatedAt` last applied to this row, absent when the row has never been seen in the cloud.
- [ ] `src/lib/recipeSync.ts` exports `planOwnRecipeSync(uid, localRows, cloudDocs)` returning `{ put: Recipe[]; remove: string[] }`, with no imports from `services/`, `hooks/` or `db/`.
- [ ] Local rows whose `createdBy.uid` is not `uid` never appear in `put` or `remove`. Cloud docs whose `createdBy.uid` is not `uid` are ignored.
- [ ] A cloud doc that is malformed (no string `id`, no string `title`, `ingredients` or `instructions` not arrays) is skipped, and a local row with that id is neither written nor removed.
- [ ] The cloud version of a doc is `updatedAt` when it is a number, else `createdAt`, else 0.
- [ ] A valid cloud doc with no local row is in `put`, converted by an exported `toLocalRecipe(doc, localRow?)` that keeps only `Recipe` fields (drops `favoriteCount`, `viewCount` and any unknown key), defaults `parentId` to null, `rootId` to the id, `depth` to 0, `collaborators` to [], `prompt` to '', `notes` to [], takes `chatHistory` from the local row or [], and sets `syncedAt` to the cloud version.
- [ ] A valid cloud doc with a local row is skipped when the local `updatedAt` is greater than the cloud version (an edit made here that has not reached the cloud). Otherwise it is in `put`, merged by `toLocalRecipe` with the local `chatHistory` kept, but only when the result differs from the local row, so an unchanged snapshot writes nothing.
- [ ] A local own row with no cloud doc is in `remove` only when `syncedAt` is a number and the local `updatedAt` is not greater than `syncedAt`. A row with no `syncedAt` (save-time publish failed, imported, carried over by `migrateRecipesUid`) or with a newer local edit is kept.
- [ ] `src/lib/recipeSync.test.ts` covers every criterion above using `makeRecipe` from `src/test/factories.ts`, including: an empty cloud snapshot against synced rows (all removed) and against unsynced rows (none removed), equal versions (cloud applied), and a re-run on the plan's own output (empty plan).
- [ ] `src/lib/import.test.ts` asserts a record carrying `syncedAt` imports without it.
- [ ] `docs/decisions.md` gains a dated entry under Product decisions, "1b. A verified user's own recipes live in the cloud (2026-10-18)", quoting the author verbatim and stating: Firestore is the source of truth for a verified user's own recipes and Dexie is the cache and offline fallback; anonymous, signed-out and local-only users are unchanged (decision 1a, RL-041); the interim rules above (cloud wins unless this device holds a newer unsynced edit; a row is removed only when it was synced and has no newer local edit; nothing is pushed by the sync) and that they stand until the author answers the open questions filed with this grooming run (offline saves, private recipes, two-device conflicts, local recipes on sign-in); a live listener is used here although RL-043 rejected one for favourites, because "always the same" is the requirement and own recipes are one query; synced rows take the cloud's lower-case tags, which reverses the RL-059 note that Dexie keeps its case for those rows.
- [ ] The same change adds a one-line dated note, pointing at 1b, to each entry it amends: product decision 4 (My Recipes still reads Dexie, but for a verified user Dexie is filled from the cloud), product decision 5 (cleared recipes of a verified user come back; copy is RL-081), "Recipe delete waits for the cloud" RL-023 (order reversed by RL-080), and "Edits apply in place" (its "editing is not a decision to publish" stands until the author answers whether private recipes exist).
- [ ] A `backlog/QA.md` entry for this ticket says there is nothing to check in a browser yet and names RL-078 as the ticket that makes it visible.
- [ ] `npm run build`, `npm run lint` and `npm test` pass.

## Notes

2026-10-18, author answers (these replace the interim rules where they differ):
- Edits from two devices: last write wins. The interim "cloud wins unless this device holds a newer unsynced edit" rule is the policy, not a stopgap. Record it in the decisions entry.
- Which recipes appear where: My Recipes is split into Created (recipes the user authored from scratch) and Branched (variations the user made, including variations of other people's recipes). Other people's recipes themselves live only under Saved, never under Created or Branched. A collaborator's variation of someone else's recipe therefore belongs under that collaborator's Branched. Record this in the decisions entry; the tab split itself is a rebrand-era design item and is not built here.
- Creation needs a verified email (decision 1a, 2026-10-14); anonymous and signed-out users only keep local bookmarks. Open: whether the save becomes cloud-first for verified users, which would remove the unsynced-row handling. Not decided yet.
