## Context

RL-262 made two focus tests wait for the focus move with `waitFor`. The same pattern still
exists elsewhere: a test resolves an async step, then asserts `toHaveFocus()` (or
`document.activeElement`) synchronously, before the component's effect has moved focus.
`ProfilePage.test.tsx:747` ("keeps focus on the trigger when Add swaps to the flag", RL-281)
failed the RL-284 ship gate this way and passed 15 of 15 runs alone. RL-262's Notes list four
more candidates: `ChatInput.test.tsx:122`, `CookedSheet.test.tsx:191`,
`RecipeEditPage.test.tsx:248` and `:262`.

Separately, under heavy machine load, `RecipeDetailPage.test.tsx` ("opens the sign-up dialog
... on an unpublished recipe", "keeps the device copy ... cloud delete fails", "says so,
without Try again ...") and `SuggestMode.test.tsx` ("blocks Send past the edit cap") hit the 5 s
test timeout during RL-280's gates and passed when run alone.

## Acceptance criteria

- [ ] Every listed focus assertion that follows an async step is wrapped in `await waitFor(...)`, the pattern in `ShopFamilySheet.test.tsx` and RL-262. No assertion is removed or loosened.
- [ ] The four slow tests are made faster or more deterministic (for example, awaiting the specific element with `findBy*` instead of polling a broad query, or removing an unneeded real timer). If a test genuinely needs more time, explain why in Notes rather than raising the timeout.
- [ ] No `skip`, `todo`, retry, global timeout change or fake-timer workaround that hides a real wait.
- [ ] Each touched file passes 20 looped runs, and `npm test` passes 3 times in a row. Record the counts in Notes.
- [ ] `backlog/QA.md` has a `### RL-304` section: test-only, nothing to check in a browser.
- [ ] `npm run build`, `npm run lint` and `npm test` exit 0.

## Out of scope

Component changes. Other tests not listed.
