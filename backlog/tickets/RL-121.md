## Context

**Author's decision (2026-10-19, /groom):** favourites appear in the Saved page, and the heart
becomes the design's bookmark (the icon is RL-122). This reverses RL-091's "Favourites are NOT
listed here" note.

RL-091 builds `src/pages/SavedPage.tsx` from `splitLibrary(rows, rows, { uid, isConfigured }).saved`
(`src/lib/library.ts`): other people's root recipes stored in Dexie (saved copies and imports).
A favourite is only a Dexie row `{ uid, recipeId, createdAt }` (`db.favorites`, keyed
`[uid+recipeId]`; `src/db/database.ts`), so most favourited recipes have no Dexie recipe row.

**The gap this closes.** RL-043 hydrates a verified user's cloud favourites into Dexie once per
session (`useHydrateFavorites` in `src/hooks/useFavorites.ts`). Its pending entry in
`backlog/DECISIONS.md` (2026-10-15, RL-043, first row) says a hydrated favourite whose recipe is
not in Dexie never shows under My Recipes > Favorites, and the rejected alternative was "fetch
the favourited recipes by id (`recipes/{id}`) and list them". This ticket is that alternative,
on the page that replaces My Recipes for other people's recipes. It does not fix the Explore
Favourites chip, which still filters only the pages loaded so far (RL-098 keeps that chip; see
the open question in RL-122).

**Dual-store rules that apply** ([docs/decisions.md](../../docs/decisions.md) 1a, 1b, 6, and
"Cloud favourites hydrate once per session, add-only"):

- Read only. Nothing here writes to Dexie or Firestore. A fetched recipe is **not** cached into
  `db.recipes`: a Dexie row of someone else's recipe is a Saved copy that "Delete Recipes on
  This Device" and the RL-078 sync rules treat specially, and a favourite is not a copy.
- A favourite whose recipe was deleted is not removed: that would be a write, and removal on
  `removeCloudFavorite` also bumps the recipe's `favoriteCount`, which no longer exists.
- Local-only mode hides favourites (decision 6), so Saved stays as RL-091 built it there.
- Anonymous accounts have local favourites (bookmarks); `recipes/{id}` is `allow read: if true`
  in `firestore.rules`, so their rows can be fetched too. Signed out there is no uid and no
  favourite.

**Reads.** `getPublishedRecipe(id)` in `src/services/firestore.ts` is one `getDoc`, one billed
read per call, missing or not. It has no timeout; wrap each call in `withTimeout` (8000 ms,
as `getCloudFavorites` does) with failures reported through `reportError(err, 'saved-favorite-read')`.

## Acceptance criteria

- [x] A pure function in `src/lib/library.ts` (no service or hook import) takes the Dexie recipe rows, the RL-091 `saved` list, the user's favourite rows, the fetched results by id (`recipe`, `missing` or `failed`) and `uid`, and returns `{ rows, toFetch, deletedCount, failedCount }`:
  - a favourite whose recipe is in Dexie uses that row and is never in `toFetch`;
  - a favourite of the user's own recipe (`createdBy.uid === uid`, from either source) is left out, since own recipes live on the You tab;
  - favourited branches of other people's recipes are included (Saved roots-only applies to saved copies, not to favourites);
  - a recipe both saved and favourited appears once;
  - order is newest kept first: a favourite's `createdAt` for favourites, the recipe's `createdAt` for saved copies;
  - `missing` results count in `deletedCount`, `failed` in `failedCount`, unfetched ids in `toFetch`, and none of the three is in `rows`.
- [x] `src/lib/library.test.ts` covers each bullet above with `makeRecipe` from `src/test/factories.ts`.
- [x] `src/hooks/useSavedFavorites.ts` reads the user's favourites with a Dexie live query (as `useFavoriteIds` does), fetches each id in `toFetch` with the bounded `getPublishedRecipe` in parallel, and returns the pure function's output plus `retry()`.
  - A result (`recipe` or `missing`) is cached in a module-level map for the session, so returning to Saved costs no reads; `failed` is not cached and `retry()` refetches only failed ids.
  - When `navigator.onLine` is false, nothing is fetched; unfetched ids are reported as `offlineCount` instead of failed.

Human, on the preview against the live project as a verified user at 390x844:

- On browser A favourite two recipes by someone else and save one shared link with "Save to my
  library". On browser B, signed into the same account with a fresh profile, open Saved: all
  three show, newest kept first; devtools Network shows one `recipes/{id}` read per favourite
  and none on a second visit to Saved.

## Notes

Accepted cost: one read per favourited recipe not on the device, per session. A user with 200
such favourites pays 200 reads per session; leave a `shortcut:` comment naming that, to be
upgraded to a batched `documentId() in` query if favourite counts grow.

Implementer: done as specified. `buildSavedList(recipes, saved, favorites, fetched, uid)` takes the raw Dexie rows as its first argument so a favourite resolves to the device row; when a recipe is both saved and favourited it is ordered by the favourite's date. `withTimeout` swallows rejections, so `reportError(..., 'saved-favorite-read')` is attached to the read before the timeout wraps it. Offline state tracks the `online` and `offline` events. The data-integrity-reviewer criterion is left for the orchestrator (no Dexie or Firestore write is reachable: the hook only calls `getPublishedRecipe` and Dexie reads).

Data-integrity carve-out: no Dexie write and no recipe or favourite Firestore write is reachable. The one exception is `reportError` on a failed read, which writes a single budgeted error beacon; that is the only Firestore write reachable from the new code.
