## Context

One runner for every deploy, so a laptop and CI do the same steps in the same order. It wires
RL-295's pure helpers to the Firebase CLI (pinned by RL-294) and two REST reads that
`docs/operations.md` already documents by hand: the live ruleset ("Diff the released ruleset")
and the cache and security headers ("Cache headers are load-bearing"). The rules deploy is
the irreversible step in production (`backlog/README.md`, "What needs a human"), which is why
the runner refuses `prod` outside the production workflow (`resolveTarget` in RL-295) and why
this ticket is `hard`.

The runner never builds: the caller builds `dist/` first (CI from the GitHub Environment
variables, a laptop from its `.env`), and `bundleTargets` refuses a `dist/` built for the
other project. Firebase CLI deploys of indexes do not wait for the build to finish, hence the
explicit wait.

## Acceptance criteria

- [ ] `node scripts/deploy.mjs <dev|prod> [--order rules-first|client-first|auto]
  [--tag-message <file>] [--expect-order rules-first|client-first]` reads `.firebaserc`, resolves the target and project with
  RL-295's helpers, prints `Deploying to <target> (<project id>)` and the planned steps
  first, and exits non-zero with the reason on any refusal or failure, stopping at that step.
- [ ] Before any step it fetches the live ruleset (Firebase Rules API
  `projects/<id>/releases/cloud.firestore`, then the ruleset's source), prints the ruleset id
  as the rollback target, and prints a unified diff against `firestore.rules`. For `prod` it
  resolves the order with `resolveOrder` (live and head Terms versions, the tag message file,
  `--order`) and prints the order and its reason. With `--expect-order`, a different resolved
  order stops the run before the first deploy step, printing both and saying to rerun by
  dispatch with an explicit order (RL-298 passes the order its reviewer approved). A missing release (a fresh dev project) is
  reported and treated as "everything changes", not as an error.
- [ ] Access token: `gcloud auth print-access-token`. Every CLI call is
  `npx firebase <cmd> --project <id> --non-interactive`; the id is always explicit, never the
  default.
- [ ] Steps: `firebase deploy --only firestore:indexes`; then poll the Firestore Admin API
  `projects/<id>/databases/(default)/collectionGroups/-/indexes` every 15 s until
  `allIndexesReady`, failing after 20 minutes with the names still building; then
  `--only firestore:rules` and `--only hosting` in the planned order. Indexes are never
  deleted (no `--force`).
- [ ] Before the hosting step it reads every `dist/assets/*.js` (the Firebase config may sit
  in a lazy chunk, not the entry) and refuses unless
  `bundleTargets(<their joined text>, <project id>, <the other alias's id>)`.
- [ ] Verify: fetch the live ruleset again and require `rulesMatch`; fetch
  `https://<id>.web.app/`, `/sw.js` and the live entry script and require `checkHeaders` to be
  empty and `entryScriptOf(live index.html)` to equal `entryScriptOf(dist/index.html)`. Print
  the new ruleset id and the URL. When `GITHUB_STEP_SUMMARY` is set, append the project, order
  and reason, both ruleset ids, the diff and the URL to it.
- [ ] `package.json` has `"deploy:dev": "node scripts/deploy.mjs dev"`. There is no
  `deploy` or `deploy:prod` script (author decision: production has no npm script; the
  production workflow calls `node scripts/deploy.mjs prod` directly).
- [ ] `docs/operations.md` "Deploying" describes the runner, the `deploy:dev` script, that a local
  `deploy:dev` needs `firebase login` and `gcloud auth login` with access to the dev project
  and a `dist/` built from a `.env` that points at dev, and that `node scripts/deploy.mjs prod`
  refuses outside the production workflow.
- [ ] `backlog/QA.md` gets a line: from a laptop, `npm run build && npm run deploy:dev`
  succeeds against dev after RL-292 and RL-293, and `node scripts/deploy.mjs prod` refuses.
- [ ] `npm run build`, `npm run lint`, `npm test` pass.
