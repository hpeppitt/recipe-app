## Context

RL-009 added curated tag chips to Explore (`EXPLORE_TAGS` in `src/lib/constants.ts`, all
lower case). They query `where('tags','array-contains',tag)`, which matches byte for byte.
Tags are free text from the AI or the recipe editor, so a recipe tagged "Italian" never shows
under `italian`. The author overruled RL-009's "leave tags as stored" decision at the
2026-10-17 QA pass (`backlog/QA-CHECKLIST.md` section 4; `backlog/DECISIONS.md`, RL-009 row).

No backfill: production is wiped by RL-042 before release, so only new publishes matter.

**Where to normalise: the publish path only.** Decided at grooming, for these reasons:

- `publishRecipe` in `src/services/firestore.ts` is the one function every route to the cloud
  goes through: the save-time publish in `hooks/useRecipeChat.ts`, the Share retry in
  `pages/RecipeDetailPage.tsx`, and the re-publish after an edit in `pages/RecipeEditPage.tsx`.
  Normalising there also covers recipes already on a device from before this change.
- The chips only query Firestore. Local search (`lib/library.ts`, `lib/search.ts`) already
  lower-cases both sides, so the case of local tags matters nowhere.
- Normalising at AI parse or in the editor would change what users see on their own
  recipes and still miss recipes already in Dexie. It adds two call sites for no gain.

Accepted consequence: a creator's own recipe page (Dexie copy) can show "Italian" while the
published copy on Explore shows "italian". Tags render as stored in `components/recipe/TagList.tsx`.

`publishRecipe` writes `content` both in the create transaction (`writeLimited`, with
counters) and in the re-publish merge (`setDoc(..., { merge: true })` and the transaction's
own re-publish fallback). All three must carry the normalised tags.

## Acceptance criteria

- [ ] A pure `normalizeTags(tags: string[]): string[]` in `src/lib/library.ts` trims each tag, lower-cases it with `toLowerCase()`, drops empty strings, and removes duplicates while keeping first-seen order (`['Italian', ' italian ', '', 'Quick']` gives `['italian', 'quick']`). It tolerates a missing array (old recipes) by returning `[]`.
- [ ] Tests in `src/lib/library.test.ts` cover: mixed case, surrounding whitespace, empty strings, duplicates that differ only by case, order kept, and an `undefined` input.
- [ ] `publishRecipe` applies `normalizeTags` to `tags` once, before both the existing-doc merge and the `writeLimited` call, so the create payload, the merge payload and the transaction's re-publish fallback all store lower-case tags. Nothing else in the payload changes.
- [ ] The Dexie copy is not modified: `publishRecipe` does not write back to Dexie, and no code in `useRecipeChat`, `RecipeEditPage` or `parseRecipeJson` (`src/services/gemini.ts`) lower-cases tags.
- [ ] The comment above `EXPLORE_TAG_FIELD` / `EXPLORE_TAGS` in `src/lib/constants.ts` says published tags are lower-cased by `publishRecipe`, so the chips match regardless of the case the AI wrote.
- [ ] `docs/capabilities.md`, Library tabs row: "Tags are free text from the AI, so only exact lower-case matches are found" is replaced by a sentence saying published tags are stored lower case (RL-059), local tags keep their case, and the chip still needs an exact word match (`gluten free` does not match `gluten-free`).
- [ ] `docs/data-model.md`: the `recipes` Firestore row (or the RL-009 index row) notes that `tags` are stored trimmed, lower case and de-duplicated by `publishRecipe`.
- [ ] A `backlog/QA.md` entry: on the preview build, as a verified user, generate a recipe whose AI tags include a capitalised cuisine (for example ask for "an Italian pasta dinner"), check Explore with the `italian` (or matching) chip shows it, and check the recipe's own page still shows the tags as generated.

## Out of scope

- Normalising tags in Dexie, the AI response parser, the prompt (`lib/prompts.ts`) or the recipe editor.
- Synonyms, plurals or punctuation (`gluten free` versus `gluten-free`, `dessert` versus `desserts`). A tag vocabulary is a separate idea.
- Backfilling existing Firestore documents (RL-042 wipes them).
- Self-contained `#` share links (`lib/share.ts`): they never reach the chip query.
- Any rules change. `firestore.rules` does not inspect `tags`.

## Verification

`npm test` (the new `normalizeTags` tests), `npm run build`, `npm run lint`. Optional
emulator check: publish a recipe tagged `["Italian"]` through the app against `npm run
emulators` plus `npm run dev:emulated`, then confirm the document's `tags` is `["italian"]`
and the `italian` chip lists it. The human QA pass checks the real AI output on the preview
build (QA.md entry above).
