## Context

`firestore.rules` recipe create (lines 56-59) and `isOwnerUpdate` (lines 93-97) never look
at `createdAt`, `title`, `ingredients` or `instructions`. The shared feed is
`orderBy('createdAt', 'desc')` (`getPublishedRecipesPage` and `getAllPublishedRecipes` in
`services/firestore.ts`), so a recipe written with `createdAt: 9e15` sits on top of
everyone's feed forever, and a recipe padded towards the 1 MiB document limit is read on
every first paint.

`publishRecipe` re-publishes with `setDoc(..., { merge: true })` and the same `createdAt`,
so the field does not appear in `changedKeys()` on a normal re-publish or edit. Imported
recipes keep their original, older `createdAt` (`lib/import.ts`), which an upper bound
permits.

RL-040 changes `isOwnerUpdate` and delete from `signedIn()` to `verified()` under the
2026-10-14 decision and RL-042 wipes the pre-gate anonymous recipes its comment protects, so
this ticket builds on RL-040's version of the same function.

## Acceptance criteria

- [x] Create requires `createdAt is int` and `createdAt <= request.time.toMillis() + 60000`.
- [x] Create and `isOwnerUpdate()` both require `title is string && title.size() <= 200`, `ingredients is list && ingredients.size() <= 100`, and `instructions is list && instructions.size() <= 100`, evaluated on `request.resource.data`.
- [x] `isOwnerUpdate()` requires `!('createdAt' in changedKeys())`.
- [x] `isViewIncrement()` and `isFavoriteCountBump()` are unchanged.
- [x] The caps live as named constants in a comment block above the recipe rules, so RL-036 can mirror them on the client.
- [x] `docs/data-model.md` recipes paragraph lists the new constraints and the reason (feed pinning, first-paint size).
- [x] A `backlog/QA.md` entry: after RL-022 deploys, publish a new recipe and edit an existing published one on live; both succeed.

## Out of scope

Per-element validation inside the arrays (rules cannot iterate a list), caps on other
fields, client-side validation (RL-036), and the deploy (RL-022).

## Verification

Emulator probes recorded in Notes: create with `createdAt` an hour ahead (deny), now
(allow), a year in the past (allow), a non-int (deny), a 201-char title (deny), 101
ingredients (deny); owner update changing `createdAt` (deny); owner re-publish via the app
(allow); view increment and favourite bump by another user (allow). Then publish, edit and
re-publish through `npm run dev:emulated`.

## Notes

The caps (200 / 100 / 100) are the groomer's choice, generous against any generated recipe
seen so far. Log the final values in `backlog/DECISIONS.md` if changed. A client clock more
than a minute fast will now fail to publish; that is accepted.

### Implementation (2026-10-14)

- `firestore.rules`: comment block above `match /recipes` names MAX_TITLE_LENGTH 200,
  MAX_INGREDIENTS 100, MAX_INSTRUCTIONS 100, CREATED_AT_MAX_SKEW_MS 60000. Create adds the
  `createdAt` int and skew checks; create and `isOwnerUpdate()` call a new
  `hasBoundedContent()` on `request.resource.data`; `isOwnerUpdate()` adds
  `!('createdAt' in changedKeys())`. `isViewIncrement()` and `isFavoriteCountBump()` untouched.
  Caps unchanged from the ticket, so no DECISIONS.md entry.
- Real writers checked: `publishRecipe` creates with `setDoc` of the full recipe (minus
  `chatHistory`) and re-publishes with `setDoc(..., { merge: true })` of the same content, so
  `title`, `ingredients`, `instructions` and the unchanged `createdAt` are always present.
  `createdAt` comes from `Date.now()` (`db/recipes.ts`) or an import's stored value, and the
  JS SDK encodes a safe integer as `integerValue` (`toNumber` uses `isSafeInteger`), so
  `is int` holds. The edit page re-publishes `{ ...recipe, ...patch }` and `draftToPatch`
  does not touch `createdAt`. The suggestion-approval `collaborators` arrayUnion is checked
  against the stored fields.
