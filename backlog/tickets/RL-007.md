## Context

The data layer is local-first but the app dies on an offline reload, which betrays the
architecture's promise in a kitchen with a flaky connection. ROADMAP 2.3 scopes this:
`vite-plugin-pwa`, a real manifest and icons, precache the shell only (recipes already live
in IndexedDB and Firestore paths degrade via `withTimeout`), `registerType: 'prompt'` with a
visible "update available" affordance to avoid the stale-bundle failure.

## Acceptance criteria

- [x] `vite-plugin-pwa` is a dev dependency; the generated service worker precaches the shell and hashed assets only.
- [x] `public/` has a manifest with name, theme colours for both themes, and 192 and 512 px icons (SVG-derived, text-first, no food photography).
- [x] A new service worker triggers an in-app "Update available" affordance using the shared `Button`; it never auto-reloads mid-session.
- [ ] After one online visit, reloading `/` and `/recipe/:id` for a local recipe with the network disabled renders the app from cache.
- [x] `docs/capabilities.md` gains an "Offline shell and install" row; `docs/operations.md` notes how to verify against `npm run preview`.

## Out of scope

Background sync, push notifications, caching Firestore responses.

## Verification

`npm run build && npm run preview`, then the offline reload. The agent can do this with
curl for the shell; the human QA pass does the real offline reload on a phone.

## Notes

This adds a dependency to a dependency-light app, argued in ROADMAP 2.3. The plugin itself is a devDependency (it generates the worker at build), but its `virtual:pwa-register` module and `workbox-window` ship in the client bundle: `workbox-window` is a separate hashed chunk of 5.75 kB (2.36 kB gzip), and the register module is a small stub inside the entry bundle (not measured separately; the entry is 145.86 kB gzip in total). It completes local-first rather than fighting it.

Build output: `vite-plugin-pwa` 1.3.0, 33 precache entries, 1037.81 KiB. The list includes `index.html`, the entry bundle, the `firebase` chunk, every lazy route chunk, the CSS and the icons. No runtimeCaching is configured, the only registered route is the navigation fallback, and `sw.js` contains no Firestore or Firebase endpoint. Fallback denylist: `/__/`, `/api/`, `/_`. Email-link sign-in uses `window.location.origin` plus query params and lands on `/`, which the fallback correctly serves as the app; Firebase Auth's own `/__/auth` handler is denylisted. Not exercised in a real browser.

Verified with `vite preview`: `/`, `/sw.js`, `/manifest.webmanifest`, icons and `/recipe/abc` return 200 with the right types (text/javascript, application/manifest+json). `vite preview` does not apply `firebase.json` headers (it sent `no-cache` on everything), so the header rule is unverified until the hosting deploy. `firebase.json` needed no change: `/**` is already `no-cache` and only `/assets/**` is immutable, and `sw.js` and the workbox file sit at the root.

Needs the human: the fourth criterion (real offline reload of `/` and `/recipe/:id`) is NOT ticked. Also the update prompt flow, install on a phone, and post-deploy header check (see QA.md).

Fix round: the service worker is now registered once from `UpdatePrompt` mounted in `App.tsx` outside the routes, so deep links to `/recipe/:id` and `/shared/:id` register it and show the update bar. The `role="status"` wrapper is always mounted.
