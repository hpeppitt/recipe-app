## Context

`Avatar.tsx` lines 38-42 render `<img src={photoURL}>` for any `photoURL`, and profiles are
publicly readable and owner-writable with no field checks (`firestore.rules` lines
181-193). A user can set `photoURL` to a URL they host and log the IP and user agent of
everyone who sees their avatar, or store an unbounded string. The only legitimate writer is
`AvatarEditor.tsx`, which produces a 128x128 JPEG via `canvas.toDataURL('image/jpeg', 0.8)`,
well under 100 KB of base64. Photos beyond avatars are out per product decision 3.

RL-040 raises profile writes to `verified()` (anonymous accounts no longer have a cloud
profile), and this ticket adds the `photoURL` check to RL-040's version of the profile rules.

## Acceptance criteria

- [x] `Avatar` renders the `<img>` only when `photoURL` starts with `data:image/`; otherwise it falls through to the emoji or initials rendering.
- [x] Profile create, and owner update when `'photoURL' in changedKeys()`, require `photoURL` to be absent, null, or a string matching `^data:image/.*` with `size() <= 100000`.
- [x] `isFollowerCountBump()` is unchanged, and an owner update that does not touch `photoURL` is not affected by an existing bad value.
- [x] `docs/data-model.md` profiles paragraph records the constraint.
- [x] A `backlog/QA.md` entry: upload an avatar on the preview build and confirm it renders on the profile and library header.

## Out of scope

Rewriting existing profile documents, other profile field caps, and the deploy (RL-022).

## Verification

Emulator probes: owner sets a `https://` photoURL (deny), a 128px data URL from the app
(allow), a 100001-char data URL (deny), a displayName-only update on a profile seeded with a
bad URL (allow). Avatar upload through `npm run dev:emulated`.

## Notes

Source audit: every photoURL in src is `profiles.photoURL` (AvatarEditor data URL or null,
useProfile.updateAvatar, firestore.ts createOrUpdateProfile sets null, ProfilePage and
LibraryPage pass profile values to Avatar). AuthContext/`toAppUser` and Firebase Auth
`user.photoURL` are not read anywhere, and recipes createdBy, suggestions and notifications
carry no photoURL. So no legitimate source produces an https photoURL; nothing is hidden.
Recipe cards use the generated avatar and never pass photoURL.

Rules: `photoURLOk()` inside `match /profiles`; create requires it, owner update requires it
only when `'photoURL' in changedKeys()`. `isFollowerCountBump()` untouched. Not run: size
of a real canvas output (no browser here); a 128x128 q0.8 JPEG is typically a few KB, about
4-8 KB of base64, so far below 100000 (estimate, not measured).

Emulator probes (`firebase emulators:exec --only firestore --project demo-rl019`, REST with
unsigned tokens, seeded via owner bypass). New rules / HEAD rules (control):
- https photoURL, verified owner: DENY 403 / ALLOW 200
- 128px-style data URL: ALLOW 200 / ALLOW 200
- data:image/ of exactly 100000 chars: ALLOW 200 / ALLOW 200

- null photoURL: ALLOW 200 / ALLOW 200
- non-string (int) photoURL: DENY 403 / ALLOW 200
- displayName-only update on profile seeded with https URL: ALLOW 200 / ALLOW 200
- create with bad photoURL: DENY 403 / ALLOW 200

- anonymous account write: DENY 403 / DENY 403 (RL-040)
