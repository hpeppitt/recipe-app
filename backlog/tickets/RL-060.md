## Context

RL-055's `scripts/data-request.mjs erase <uid>` deletes every suggestion whose
`recipeOwnerId == uid`, with its whole `messages` thread, because the recipe is deleted
too. That throws away other users' suggestion text and replies. The author overruled this
at the 2026-10-17 QA pass (`backlog/QA-CHECKLIST.md` section 4; `backlog/DECISIONS.md`, the
RL-055 row on suggestions on own recipes) and approved this exact behaviour: keep those
threads and anonymise the owner side, the same way the suggester side is already anonymised.

The Privacy Policy draft already describes the new behaviour (`src/content/legal/privacy.ts`,
"Suggestions and replies", "How long") behind the marker `[DEPENDS ON RL-060; today the runbook
deletes them.]`. This ticket removes that marker.
Policy copy is author-owned: removing the marker is approved here, but no other wording may
change, and the whole draft still waits for the author's sign-off in RL-046.

The code to change is `buildErasePlan` (the first loop over `suggestions`), plus the existing
patch helpers `anonymisedSuggestionPatch` / `anonymisedMessagePatch` and `PLACEHOLDER_UID`
(`deleted-user`). The erase table in `docs/operations.md` ("Data requests") documents the
current behaviour row by row.

**Rules check, done at grooming (`firestore.rules`, `match /suggestions/{suggestionId}`).**
The suggester can still read the kept thread: the parent's read rule is `verified()` and
`recipeOwnerId == auth.uid || suggestedBy.uid == auth.uid`, and the `messages` read rule
`get()`s the parent and checks the same two fields. Neither reads the recipe, so a deleted
recipe and a `recipeOwnerId` of `deleted-user` do not affect the suggester. Nobody can sign in
as `deleted-user`, so the owner side is readable by no client.

What the rules do not change: in the app, a suggester reaches threads only from the recipe
page (`subscribeRecipeSuggestions` in `services/firestore.ts` filters by `recipeId`), so once
the recipe is gone the kept thread is visible to the suggester through the self-service
export (RL-056, `lib/dataExport.ts`) and an operator export, not in the app. The author
accepted that when overruling ("threads about a recipe nobody can open" was the stated
trade-off).

## Acceptance criteria

- [ ] For a suggestion with `recipeOwnerId == uid` and `suggestedBy.uid != uid`, `buildErasePlan` no longer deletes it. It plans one update setting `recipeOwnerId` to `PLACEHOLDER_UID` (a new exported helper, for example `anonymisedOwnerSuggestionPatch()`), and leaves `recipeId`, `recipeTitle`, `recipeEmoji`, `message`, `status`, `createdAt` and `suggestedBy` unchanged.
- [ ] In that thread, every message with `fromUid == uid` gets `anonymisedMessagePatch()` (`fromUid` to `deleted-user`, `fromDisplayName` to null). The other party's messages are untouched.
- [ ] A suggestion where the uid is both owner and suggester (an owner suggesting on their own recipe, which the create rule permits) is still deleted with its whole thread, messages first, since no other party is in it.
- [ ] The parent update and its message updates are in one plan group, so they land in the same batch when they fit, like the existing groups.
- [ ] After `--execute`, a re-run plans 0 writes (the `recipeOwnerId == uid` query no longer matches), and no document still contains the uid.
- [ ] `scripts/data-request.test.mjs`: the test "deletes suggestions on own recipes with their whole thread, messages first" is replaced by tests for the three cases above (other party's suggestion kept and owner side anonymised; other party's replies untouched; self-suggestion deleted). No existing test is weakened.
- [ ] An emulator run in the RL-055 style (scratchpad seeder, `firebase emulators:exec --only firestore,auth`), recorded in Notes with real output: a target who owns a recipe with another user's suggestion and a thread containing replies from both. After erase, the suggestion and the other user's replies are byte-identical except `recipeOwnerId`, the target's replies are anonymised, the recipe is gone, and the second dry run plans 0 writes.
- [ ] In the same emulator session, signed in as the suggester (verified, unsigned test JWT as RL-009 did), a read of the kept suggestion and a list of its `messages` both succeed after the erase. Record the result in Notes.
- [ ] `src/content/legal/privacy.ts`: the bracketed `[DEPENDS ON RL-060; today the runbook deletes them.]` is removed with its leading space, and nothing else in the file changes. `src/lib/legal.test.ts` (or whichever test checks the content) still passes.
- [ ] `docs/operations.md`, "Data requests" erase table: the `suggestions on the uid's own recipes` row says they are kept and anonymised (`recipeOwnerId` becomes `deleted-user`, the uid's replies anonymised as above, the other party's text untouched, a self-suggestion deleted with its thread). The "Not covered" bullet on free text also mentions that kept threads keep the deleted recipe's title and emoji.
- [ ] `docs/legal/claims-to-verify.md` item 23: the "Still open for the author" sentence about deleting threads on the owner's recipes is replaced by a line saying RL-060 keeps and anonymises them, matching the policy text.
- [ ] `docs/legal/data-inventory.md`, the "Operator data-request runbook" row: the sentence "Suggestions on the erased user's own recipes are deleted with their whole thread" is replaced with the new behaviour. Other users' favourites of the erased recipes are still deleted; leave that sentence.
- [ ] `backlog/DECISIONS.md` records the choices taken here: `recipeTitle` and `recipeEmoji` kept on the anonymised suggestion (alternative: null them), and self-suggestions deleted (alternative: anonymise them too).
- [ ] A `backlog/QA.md` entry for the author: the Privacy Policy marker is gone, so re-read "Suggestions and replies" during the RL-046 sign-off; and the runbook table changed, so read it before the next real erasure request.

## Out of scope

- Any change to `firestore.rules`, the client, or `lib/dataExport.ts`.
- Making kept threads reachable in the app without the recipe (a "my suggestions" list).
- The notification a reply in a kept thread sends to `deleted-user` (`lib/suggestions.ts` `replyRecipient` returns the placeholder). It already happens for anonymised suggesters and is a separate fix.
- Other users' favourites of the erased recipes: still deleted, per the accepted RL-055 decision.
- Self-service deletion (RL-057). It will need the same behaviour; that ticket is not edited here.
- Running the script against production.
- Any other wording in the Privacy Policy, Terms or Cookie Policy.
