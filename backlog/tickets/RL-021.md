## Context

`getRecipesByUsers` (`services/firestore.ts` around line 951) queries
`where('createdBy.uid', 'in', chunk), limit(50)` with no `orderBy`, so Firestore returns an
arbitrary 50 by document id and the client then sorts those. Someone following a prolific
cook sees an arbitrary slice, not the latest.

## Acceptance criteria

- [ ] The query adds `orderBy('createdAt', 'desc')` before `limit(50)`.
- [ ] `firestore.indexes.json` gains a `recipes` composite index: `createdBy.uid` ASC, `createdAt` DESC.
- [ ] The client-side sort across chunks stays, since chunks of 30 uids are queried separately.
- [ ] `docs/data-model.md` index list includes the new index.

## Out of scope

Pagination of the Following feed, and the index deploy (RL-022). Until the index is live the
query fails and `useFollowingRecipes` shows an empty list, so RL-022 must deploy indexes
before this client is released.

## Verification

Run the query against the emulator (which does not enforce composite indexes, so also check
`firestore.indexes.json` by reading it). Human QA after RL-022: follow an account with more
than 50 recipes, or confirm on live that the Following filter lists the newest first.

## Notes

- Query now orders by `createdAt` desc before `limit(50)`. New `recipes` index added; none existed before. Not deployed (RL-022).
- Merge is the union of per-chunk results re-sorted newest first, not capped overall (up to 50 per chunk). Sort is correct; left unchanged.
- Added `src/services/firestore.following.test.ts` (mocked SDK). Emulator not run (not quick; it does not enforce composite indexes anyway). Index JSON parses and matches the query field order and directions.
