## Context

The author wants to attach photos (a dish, a fridge or pantry, a handwritten or printed
recipe) as input to recipe generation, on `/create` and `/recipe/:id/vary`, and get a recipe
back as for text. This ticket is the non-UI half: pure validation, the downscale, the request
shape, and the hook. RL-119 adds the attach button and thumbnails and depends on this one.

**Which path serves generation.** Only the client path. `src/services/gemini.ts` calls Gemini
through Firebase AI Logic (`getGenerativeModel`, then `startChat()`), and nothing in `src`
calls the `generateRecipe` callable in `functions/src/index.ts`, which is deliberately
undeployed ([docs/decisions.md](../../docs/decisions.md) "AI path: stay as-is for now
(RL-001)", [docs/operations.md](../../docs/operations.md) "Deploying"). So this ticket
changes the client path only. The AI Logic SDK already accepts images: `ChatSession.sendMessage`
is typed `string | Array<string | Part>` and `InlineDataPart` is `{ inlineData: { mimeType,
data } }` with base64 data. No new dependency.

**Decision 3 ("Photos: no, text-first, permanently").** That decision bans *storing* recipe
photos: Firebase Storage, base64 in Firestore, and a speculative `imageUrl` field on the recipe
or the Zod schema. This ticket stores nothing. Images are generation input only: held in memory
for the length of the chat, sent to Gemini, and never written to Dexie, Firestore, Storage,
`chatHistory`, `prompt`, analytics or telemetry. No schema field, no Dexie version, no rules
change. The groomer reads this as consistent with decision 3; **the author must confirm that
at `/groom`**, and the implementer adds a dated note under decision 3 saying so.

**What gets stored instead.** `ChatMessage` (`src/types/recipe.ts`) is persisted as
`chatHistory` and its first user `content` becomes `prompt`, which is public on a published
recipe. Its type does not change. The user message keeps the typed text. When the user sends
photos with no text, the text sent and stored is the constant `IMAGE_ONLY_PROMPT`, "Suggest a
recipe based on these photos.", so `prompt` stays meaningful text.

**Server-side cap.** There is no project-owned server on this path, so the only server-side
limit is the Gemini API's own request size limit (20 MB of inline data per request) behind the
AI Logic proxy, plus the AI Logic per-user request limit (RL-050, needs-human, not yet set).
The client caps below keep every request far under the Gemini limit. Mirroring the caps in the
undeployed callable is a question for the author, not part of this ticket.

**Rate limit.** One send is still one `chat.sendMessage` call, so one AI Logic request and one
generation however many photos it carries. Do not split photos across calls.

**Multi-turn cost.** The AI Logic `ChatSession` keeps the history in memory and resends it on
every turn, photos included. That is why there is a per-chat cap as well as a per-message cap.

Existing image code: `src/components/profile/AvatarEditor.tsx` (`handleImageUpload`) draws a
`File` onto a canvas through `new Image()` and `URL.createObjectURL`, then `toDataURL('image/jpeg',
0.8)`. Reuse that approach, not the function (it is inline, crops to a square, and never revokes
its object URL). Do not refactor AvatarEditor.

## Decisions (fixed for the implementer)

In `src/lib/imageAttachments.ts`, exported constants:

- `ACCEPTED_IMAGE_TYPES = ['image/jpeg', 'image/png', 'image/webp']`.
- `MAX_IMAGES_PER_MESSAGE = 3`; `MAX_IMAGES_PER_CHAT = 6`.
- `MAX_SOURCE_BYTES = 20 * 1024 * 1024` (rejected before decoding, so a huge file never reaches a canvas).
- `MAX_LONG_SIDE_PX = 1024`; JPEG quality 0.8, one retry at 0.6.
- `MAX_ENCODED_BYTES = 600 * 1024` per image after downscale (decoded bytes, not base64 length).
- `IMAGE_ONLY_PROMPT = 'Suggest a recipe based on these photos.'`.

Pure functions in the same file (no DOM, no `services/` or `hooks/` imports):

- `validateImageFile(file: { type: string; size: number }, counts: { inMessage: number; inChat: number })`
  returns `{ ok: true }` or `{ ok: false, reason }` with `reason` one of `'type' | 'too-large'
  | 'message-limit' | 'chat-limit'`.
- `planDownscale(width, height, maxSide = MAX_LONG_SIDE_PX)` returns integer `{ width, height }`
  scaled so the longest side is at most `maxSide`, aspect kept, never upscaled, minimum 1.
- `base64ByteLength(base64: string)` returns the decoded byte count (accounts for `=` padding).
- `attachmentErrorMessage(reason)` returns the user copy: type: "Use a JPEG, PNG or WebP
  photo."; too-large: "That photo is too large. Try a smaller one."; message-limit: "You can
  add up to 3 photos at a time."; chat-limit: "This chat already has 6 photos. Start a new
  recipe to use more."; `'encode'` (downscale failed or still over the cap): "That photo
  couldn't be read. Try another one."
- Type `ImageAttachment = { mimeType: 'image/jpeg'; base64: string }` (base64 without the
  `data:` prefix).

In `src/services/imageDownscale.ts` (browser only, canvas): `downscaleToJpeg(file: File):
Promise<ImageAttachment>` decodes the file, draws it at `planDownscale` size on a white
background (PNG and WebP transparency becomes white, not black), encodes JPEG at 0.8, retries
at 0.6 if over `MAX_ENCODED_BYTES`, rejects if still over or if decoding fails, and revokes its
object URL in every path.

## Acceptance criteria

- [x] `src/lib/imageAttachments.ts` exists with the constants, functions and copy above, and imports nothing from `services/` or `hooks/`.
- [x] `src/lib/imageAttachments.test.ts` covers: each accepted type passes; `image/heic`, `image/gif` and `''` fail with `type`; a file one byte over `MAX_SOURCE_BYTES` fails with `too-large`; the fourth image in a message fails with `message-limit`; the seventh in a chat fails with `chat-limit`; `planDownscale` for landscape, portrait, square, already-small (unchanged) and extreme ratio (4000x10 keeps a height of at least 1); `base64ByteLength` with zero, one and two padding characters.
- [x] `src/services/imageDownscale.ts` exports `downscaleToJpeg` as specified, and always revokes its object URL (success, decode error, over cap).
- [x] `ChatSession.sendMessage` in `src/services/gemini.ts` takes `(message: string, images?: ImageAttachment[])`. With no images it calls `chat.sendMessage(message)` with the plain string exactly as today. With images it calls `chat.sendMessage([message, ...images.map(i => ({ inlineData: { mimeType: i.mimeType, data: i.base64 } }))])` once.
- [x] `captureAiGeneration` receives the same fields as today, plus nothing derived from the images except, optionally, an `image_count` number. No base64, data URL or file name reaches `analytics.ts` or `telemetry.ts`.

- [x] `useRecipeChat.sendMessage(text, images?)`: when `text` is empty and images are present, the user message and the model text are `IMAGE_ONLY_PROMPT`. The user `ChatMessage` has exactly today's shape (`role`, `content`, `timestamp`); no image data is put in `messages`, so none reaches `buildRecipe`, `chatHistory` or `prompt`.
- [x] The dedup search runs only on typed text: a photos-only first send skips it and goes straight to generation; a first send with text and photos dedups on the text as today.
- [x] `dismissSimilar` ("Create New Anyway") and `retryGeneration` resend the same images as the original send (held in refs, in memory only).
- [x] The hook returns `attachmentPreviews: Record<number, string[]>`: `data:image/jpeg;base64,...` URLs keyed by the user message `timestamp`, in React state only, for RL-119 to render.
- [x] `src/hooks/useRecipeChat.test.tsx` adds: a send with images passes them to the mocked session's `sendMessage`; a photos-only send stores `IMAGE_ONLY_PROMPT` as content and skips dedup; retry after a failure resends the images; after save, the `chatHistory` and `prompt` passed to `buildRecipe` and `publishRecipe` contain no `base64` string and no `data:image`; a send without images calls the session with `(text)` or `(text, undefined)` and behaves as before (the existing tests pass unchanged).
