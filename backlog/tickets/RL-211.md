## Context

Written for RL-210's recommendations; regroom if the author chose otherwise. Rules cannot
iterate list elements (docs/data-model.md), so caps are list sizes and element shapes are the
client's job. Membership is expressed as `memberUids` now so RL-237 only adds the invite path.

## Acceptance criteria

- [x] `match /kitchens/{kitchenId}`: read, update and delete if `verified() && request.auth.uid in resource.data.memberUids`; create if `verified()`, `kitchenId == request.auth.uid`, `memberUids == [request.auth.uid]`, `ownerUid == request.auth.uid`. Keys limited to `memberUids, ownerUid, shopping, pantry, updatedAt`; `shopping` and `pantry` lists of at most 300; `updatedAt == request.time`. In Phase 2 updates may not change `memberUids` or `ownerUid`.
- [x] `match /collections/{collectionId}`: read, update, delete by `ownerUid` (verified); create with own `ownerUid`, `visibility == 'private'`, `name` string 1 to 60, `recipeIds` list of at most 200, `createdAt` and `updatedAt == request.time`; updates may not change `ownerUid`, `createdAt` or `visibility`.
- [x] `KITCHEN_ITEM_CAP = 300` and `COLLECTION_RECIPE_CAP = 200` in `src/lib/kitchen.ts`, with a test reading the rules text like `rateLimit.test.ts` does.
- [x] Emulator probe codes in Notes for each allow and deny, including another user's read (403) and a 301-item list (403).
- [x] `docs/data-model.md` collections table and rules paragraphs, "in the repo, deployed by RL-227".
- [x] `npm test`, `npm run lint`, `npm run build` pass.

## Notes

- Rules in `firestore.rules` after the cookPhotos block; caps as `kitchenItemCap()` (300) and `collectionRecipeCap()` (200), tied to `src/lib/kitchen.ts` by `src/lib/kitchen.test.ts`. No existing match block, client, script or index used a top-level `kitchens` or `collections` collection.
- Every rule is size-only on lists and touches no other document (no `get`/`exists`), so a 300-item list costs one `size()`.
- Delete in both blocks is `signedIn()` plus ownership (`ownerUid`), not `verified()`, matching cooks and cookPhotos so erasure works if verification lapses. For kitchens the AC said "a member"; the owner is the only member in Phase 2, so this is equivalent now and keeps a future RL-237 member from deleting a shared kitchen. RL-237 should confirm.
- Kitchen read also allows `kitchenId == request.auth.uid` (verified), so reading your own not-yet-created kitchen answers 404 instead of 403. Ownership of that id is fixed: create requires `ownerUid == kitchenId == uid` and updates cannot change `ownerUid`.
- All five kitchen keys and all six collection keys are required (`hasAll` and `hasOnly`), as in cooks.
