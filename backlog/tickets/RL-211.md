## Context

Written for RL-210's recommendations; regroom if the author chose otherwise. Rules cannot
iterate list elements (docs/data-model.md), so caps are list sizes and element shapes are the
client's job. Membership is expressed as `memberUids` now so RL-237 only adds the invite path.

## Acceptance criteria

- [ ] `match /kitchens/{kitchenId}`: read, update and delete if `verified() && request.auth.uid in resource.data.memberUids`; create if `verified()`, `kitchenId == request.auth.uid`, `memberUids == [request.auth.uid]`, `ownerUid == request.auth.uid`. Keys limited to `memberUids, ownerUid, shopping, pantry, updatedAt`; `shopping` and `pantry` lists of at most 300; `updatedAt == request.time`. In Phase 2 updates may not change `memberUids` or `ownerUid`.
- [ ] `match /collections/{collectionId}`: read, update, delete by `ownerUid` (verified); create with own `ownerUid`, `visibility == 'private'`, `name` string 1 to 60, `recipeIds` list of at most 200, `createdAt` and `updatedAt == request.time`; updates may not change `ownerUid`, `createdAt` or `visibility`.
- [ ] `KITCHEN_ITEM_CAP = 300` and `COLLECTION_RECIPE_CAP = 200` in `src/lib/kitchen.ts`, with a test reading the rules text like `rateLimit.test.ts` does.
- [ ] Emulator probe codes in Notes for each allow and deny, including another user's read (403) and a 301-item list (403).
- [ ] `docs/data-model.md` collections table and rules paragraphs, "in the repo, deployed by RL-227".
- [ ] `npm test`, `npm run lint`, `npm run build` pass.

## Out of scope

Households and invites (RL-237). Public cookbooks (RL-256). Client.
